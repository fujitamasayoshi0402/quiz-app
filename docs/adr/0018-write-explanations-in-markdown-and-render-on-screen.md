# ADR-0018: 解説は Markdown の原文で持ち、画面で変換する。生の HTML は通さない

- ステータス: Accepted
- 決定日: 2026-09-27

## 背景と課題

解説はプレーンテキストで、見出し・箇条書き・コード・リンク・表を表せない。
管理者が Markdown で書き、利用者の画面（学習モードの正誤と解説、結果画面）で整形して出す（DEV-68）。

守らなければならないこと。

- **管理者が書いたもので、利用者の画面にスクリプトを動かさない。** 誰でもサインアップでき、招待されれば管理者になる。
  管理者を信頼できる相手とは扱わない。解説に仕込んだスクリプトが動くと、見た人の権限で API を呼べる。
  見た人が別のテナントの管理者なら、そのテナントまで届く
- **今ある解説が崩れない。** プレーンテキストで、改行だけで行を分けている
- **出題 API（`/play/quizzes`）が解説を返さない不変条件は変えない**

DB に何を持つかは、後から変えると全件の変換が要る。表示の方式もあわせてここで決める。

## 判断基準

- 利用者の画面でスクリプトが動かないこと。その性質をテストで固定できること
- 管理画面のプレビューと、利用者の画面の表示が同じ結果になること
- 今ある解説が、書き直さずに読めること
- 将来のモバイル（React Native）でも、同じ値から表示できること
- 作る手間

## 検討した選択肢

### A: 原文を持ち、画面で react-markdown が変換する

DB と API は Markdown の原文のまま。web の部品が React の要素に変換する。

- 生の HTML は、rehype-raw を足さない限り文字として出る。URL は既定の変換が `http(s)` / `mailto` など以外を空にする
- プレビューと表示が同じ部品になる
- モバイルは、同じ原文を React Native の Markdown の部品で出せる
- **防御がライブラリの既定の挙動に乗る。** 設定ひとつ（rehype-raw、`urlTransform`）で崩れる
- 変換の処理をブラウザへ送る

### B: API が変換済みの HTML を返す

commonmark-java で変換し、OWASP Java HTML Sanitizer を通して返す。画面は `dangerouslySetInnerHTML` で差し込む。

- 防御の境界がサーバーの 1 か所にまとまる
- **差し込む側は中身を信じるしかない。** サニタイザの設定の誤りが、そのまま XSS になる
- プレビューのたびに API を呼ぶか、画面側にも変換を持つ。持てば、プレビューと表示の結果がずれうる
- モバイルで HTML を出すには WebView が要る

### C: 画面で変換し、パーサを自前で書く

記法を絞って（見出し・箇条書き・コード・リンク）自分で書く。

- 仕組みの理解は深まる
- エスケープの漏れがそのまま XSS になる。記法の端のケースで崩れやすい

### D: 保存するときに HTML にして持つ

- 原文がなければ編集し直せない。両方持つと二重に管理することになる
- 許す書式を後から変えると、保存済みの全件を作り直す

### E: リッチテキストのエディタ（Tiptap など）の形式（JSON）で持つ

- 値の形がエディタに縛られる。CSV / JSON の取り込み（DEV-61）や API から、手で書けない

## 決定

**A を採用する。** 変換はフロントエンドの関心事で、ここは実績のあるライブラリに任せる。
代わりに、防御がライブラリの既定の挙動に乗る点は、web の単体テストで固定する。

### 1. 持ち方

- DB と API は Markdown（GitHub Flavored Markdown）の原文を持つ。列と API の形は変えない
- API 定義の `explanation` に、Markdown であることと表示の決まりを書く。モバイルなど、ほかのクライアントもこれに従う

### 2. 変換

- `apps/web/src/components/markdown.tsx` の 1 つの部品で変換する。管理画面のプレビューも、利用者の画面もこれを使う
- react-markdown に、remark-gfm（表、打ち消し線、タスクリスト、脚注、URL の自動リンク）と remark-breaks を足す

### 3. 許す書式

- **生の HTML は文字として出す。** rehype-raw は入れない
- **URL は、既定の変換（`defaultUrlTransform`）を使う。** `javascript:` や `data:` のリンクは href が空になる
- 外へのリンクは新しいタブで開き、`rel="noopener noreferrer"` を付ける。出題の途中の画面から離れさせず、開いた先にこのページを触らせない
- **画像は出さず、代わりの文字（alt）を出す。** 外部の画像は、読み込むだけで見た人の IP アドレスや見た時刻が相手に渡る。
  図は、署名付き URL で配る解説図（[ADR-0017](0017-deliver-figures-with-cloudfront-signed-urls.md)）で扱う。
  本文の中に図を置く書き方は、DEV-69 で決める
- 見出しは 2 段下げる（`#` を h3 にする）。解説はページの一部で、h1 にすると文書の構造が崩れる

### 4. 改行

**1 つの改行を、そのまま改行として出す**（remark-breaks）。GitHub のコメントと同じ扱い。
CommonMark の既定では段落の中の改行は空白になり、今ある解説の行がつながる。

### 5. テスト

web に Vitest を入れ、次を確かめる。CI の frontend のジョブで流す。

- 生の HTML（`<script>`、`<img onerror>`、`<iframe>` など）が要素にならない
- `javascript:` / `data:` / `vbscript:` の URL がリンクにならない
- 画像を読み込まない。外へのリンクに `target` と `rel` が付く

### 6. シード

**書き直さない。** 今の解説は、そのまま Markdown として読める。
シードは `ON CONFLICT DO NOTHING` で入れるため、書き直しても dev の既存の行は変わらず、ローカルと dev で内容が分かれる。

## 結果

### 良い影響

- 解説に見出し・箇条書き・コード・表・リンクを書ける
- プレビューと利用者の画面が同じ部品で、見た目がずれない
- DB と API の形は変わらない。今ある解説も書き直さずに済む
- モバイルでも同じ原文から表示できる

### 悪い影響・受け入れるリスク

- **防御がライブラリの既定の挙動に乗る。** 設定を変えたり、ライブラリを上げたりして挙動が変わると、XSS になりうる
- 変換の処理（gzip で約 43 KB）をブラウザへ送る。読み込むのは解説を出す画面（出題・結果・クイズの編集）だけ
- 表示がクライアントごとの実装になる。web とモバイルで細部が揃わないことがある
- Markdown の記号として読まれる書き方（行頭の `#`、`-`、`1.`、`>` など）は、見た目が変わる。記号そのものを出すには `\` を前に付ける
- web のアプリ自体に CSP がない。ライブラリの挙動が崩れたとき、止める 2 段目がない

### 緩和策

- 上の性質を単体テストで固定する。ライブラリを上げてテストが落ちたら、そこで気づく
- 管理画面にプレビューを置き、公開する前に見た目を確かめられるようにする
