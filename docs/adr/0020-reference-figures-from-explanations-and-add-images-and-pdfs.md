# ADR-0020: 解説図に画像と PDF を加え、解説の本文から `figure:` の ID で指す

- ステータス: Accepted
- 決定日: 2026-09-27

## 背景と課題

解説図は、draw.io の原本と書き出した SVG の組として置き、CloudFront の署名付き URL で配る仕組みができている
（[ADR-0017](0017-deliver-figures-with-cloudfront-signed-urls.md)）。
これに、スクリーンショットや写真（PNG・JPEG）と、PDF の資料を加える。

あわせて、図を解説のどこに出すかを決める。解説は Markdown の原文で持ち、画像は出さない
（[ADR-0018](0018-write-explanations-in-markdown-and-render-on-screen.md)）。本文の中に図を置く書き方は、DEV-69 で決めることにしていた。

守らなければならないこと。

- **管理者が置いたもので、利用者の画面にスクリプトを動かさない**（ADR-0018 と同じ）。管理者を信頼できる相手とは扱わない
- **外部の画像は読み込まない。** 読み込むだけで、見た人の IP アドレスや見た時刻が相手に渡る
- **テナントの図は、そのテナントの利用者にだけ見せる。回答する前には見せない**（ADR-0017 と同じ）
- **写真は、撮った場所（EXIF の位置情報）を含むことがある。** 管理者が気づかずに上げても、利用者に渡さない

図の指し方は、保存した解説の原文に残る。後から変えると、全件の書き換えが要る。

## 判断基準

- 解説の中の好きな位置に、図をいくつでも置けること
- 解説の API の形を変えずに済むこと。モバイルなど、ほかのクライアントも同じ原文から図を出せること
- 回答する前に図を見せない不変条件が、仕組みとして守られること
- 検査を通る前のファイルを、誰にも配らないこと
- 今の配り方（ADR-0017）をそのまま使えること

## 検討した選択肢

### 本文での指し方

#### A: Markdown の画像とリンクの記法で、`figure:` の ID を指す

`![構成図](figure:<図の ID>)` は本文の中に図を出し、`[資料](figure:<図の ID>)` は新しいタブで開く。
画面の部品が `figure:` を `/api/t/{slug}/play/figures/{id}` に置き換える。

- 位置も数も、書き手が決められる。代替テキストも同じ記法で書ける
- 解説の文字列の中にあるので、API の形は変わらない。解説を返さない出題 API は、図の ID も返さない
- 管理画面のプレビューも、同じ部品で図を出せる
- **DB は、どの解説がどの図を指すかを知らない。** 消した図を指す参照や、どこからも指されない図が残りうる

#### B: クイズに図の並びを持ち、解説の下にまとめて出す

クイズと図を、順番つきの表で結ぶ。

- DB が参照を知っている。使われている図を消させない、といった制約を掛けられる
- **本文の中の位置を指せない。** 「次の図のとおり」と書いた文の近くに図を置けない
- 解説とは別の項目になり、保存・一括取り込み（DEV-61）・回答の結果の API の形が変わる

#### C: 独自の記法（`::figure{#<ID>}` など）

- 画像と区別でき、属性（幅など）を足しやすい
- GitHub Flavored Markdown ではない。ほかのクライアントや、ほかのツールで書いた原文と噛み合わない

#### D: 配信の URL（`/api/t/{slug}/play/figures/{id}`）を本文に直接書く

- 変換が要らない
- **テナントの slug が本文に残る。** slug を変えると壊れる。URL で画像を指せるようにすると、外部の画像を止める線が引きにくい

### 画像と PDF の受け取り方

#### E: 今の図と同じく、API が本体を受け取る

- 今の経路（web の proxy → quiz-service → S3）のまま作れる
- **大きなファイルが、web の proxy（Amplify の SSR）と quiz-service を通る。** 写真や PDF は、今の上限（1 MB）を大きく超える

#### F: API が S3 の署名付き POST を出し、ブラウザが S3 へ直接上げる

キー・大きさ・期限を固定した署名付き POST を API が出す。上がったものは、検査を通ってから配る場所へ移す。

- 大きなファイルが web と quiz-service を通らない
- **検査を別の段として持つ。** 上がってから検査が終わるまで、配れない状態がある
- バケットに CORS を設定する

## 決定

**本文の指し方は A、受け取り方は F を採用する。**

B は位置を指せない。C は標準の記法から外れる。D は外部の画像との線引きが崩れる。
A の弱み（DB が参照を知らない）は、保存するときの確かめで補う。
E は、写真や PDF の大きさに対して、途中の経路が細い。

```
管理者 → API（署名付き POST を出す）
       → ブラウザ → S3 の incoming/（検査の前。誰にも配らない）
       → 検査（中身で種類を確かめ、画像は読み直す）→ S3 の img/ または pdf/ と、quiz.figures の行

解説の原文: 「この構成は次のとおり。\n![構成図](figure:<図の ID>)」
利用者 → 画面の部品が figure: を /api/t/{slug}/play/figures/{id} に置き換える → 以降は ADR-0017 のとおり
```

### 1. 本文での指し方

- **`![代替テキスト](figure:<図の ID>)` は、本文の中に図を出す。** SVG（draw.io）と画像に使う
- **`[文字](figure:<図の ID>)` は、図を新しいタブで開くリンクになる。** PDF に使う。`rel="noopener noreferrer"` を付ける
- `figure:` のあとが UUID でなければ、ほかの画像と同じく出さない
- **`figure:` 以外の画像は、これまでどおり出さない**（ADR-0018 の決定 3）。外部の画像を許す道は作らない
- 図を取れないとき（消された、配信の失敗）は、代替テキストを出す。解説の文は表示する
- 管理画面の「図を挿入」で、この記法を本文に入れる。書き手が ID を手で書かなくて済む
- API 定義の `explanation` の説明に、`figure:` の書き方を足す。ほかのクライアントもこれに従う

### 2. 保存するときの確かめ

- クイズを保存するとき（作成・更新・一括取り込み）、**API が本文から `figure:` の ID を拾い、テナントにある図かを確かめる。** 無ければ 400
- 別テナントの図は、行レベルセキュリティで見えないため、無い図として扱われる
- Markdown としては読まず、文字列から拾う。コードブロックの中の `figure:` も確かめの対象になる

### 3. 種類

| 種類 | 受け付けるもの | 配るもの | 本文での指し方 |
| --- | --- | --- | --- |
| draw.io | 原本（`.drawio`）と SVG。API が JSON で受け取る（ADR-0017） | `svg/` の SVG | 画像の記法 |
| 画像 | PNG、JPEG | `img/` の画像（読み直したもの） | 画像の記法 |
| PDF | PDF | `pdf/` の PDF | リンクの記法 |

- `quiz.figures` に種類を持つ。今ある行は draw.io
- **図は書き換えない**（ADR-0017 の決定 3）は、すべての種類に当てはめる

### 4. 受け取りと検査

- API が、キー（`incoming/{テナントの ID}/{図の ID}`）・大きさの上限・期限を固定した署名付き POST を出す
- **検査を通るまで、配る場所に置かない。** CloudFront は `incoming/` を読めない
- 種類は、ファイル名や申告された Content-Type ではなく、**中身の先頭のバイト**で決める。配るときの Content-Type も、検査の結果から付ける
- **画像は、画像として読み直して保存する。** EXIF などのメタデータ（位置情報を含む）が落ちる。画像に別の形式を重ねたファイルも、ここで画像だけになる
- 画像を展開する前に、ヘッダで画素数を確かめる。小さなファイルが巨大な画像に展開されるのを防ぐ
- 検査をどこで行うか（quiz-service か、S3 のイベントで動く Lambda か）は、DEV-81 で決める
- バケットの CORS は、アプリのオリジン（`dev.<ドメイン>` と `http://localhost:3000`）からの POST だけを許す

### 5. 配信

- ADR-0017 の配り方をそのまま使う。CloudFront の署名付き URL、応答ヘッダ（CSP の `sandbox`、`nosniff`）、1 年のキャッシュ
- CloudFront が読める場所を、`svg/` に加えて `img/` と `pdf/` に広げる。原本（`drawio/`）と、検査の前（`incoming/`）は読ませない
- PDF をどう見せるか（リンクで開く、ページを画像にする、画面の中に描く）は DEV-82 で決める。リンクで開く形は、この ADR の記法だけで成り立つ

## 結果

### 良い影響

- 解説の好きな位置に、図や画像を置ける。PDF の資料も本文から開ける
- 解説の API の形は変わらない。出題 API が解説を返さない限り、図の ID も返らない
- 外部の画像は、これまでどおり読み込まない
- 利用者に渡る画像から、位置情報などのメタデータが落ちる

### 悪い影響・受け入れるリスク

- **DB は、どの図がどこから指されているかを知らない。** 図を消しても、指している解説は残る（代替テキストが出る）。
  どこからも指されない図は、S3 に残り続ける
- 保存の確かめは文字列から拾うため、コードブロックの中に書いた `figure:` も、ある図を指していなければ保存できない
- JPEG は読み直すと、画質が少し落ちる
- 署名付き POST は、期限までは誰が使っても上げられる。置けるのは `incoming/` の決まったキーだけで、検査を通るまで配られない
- PDF は、ブラウザの PDF ビューアで開く。PDF の中のスクリプトやリンクは、アプリと別のオリジン（図のドメイン）で扱われる

### 緩和策

- 図の一覧を作るとき、どこからも指されない図を見つけて消せるようにする
- `figure:` の置き換えと、それ以外の画像を出さないことは、web の単体テストで固定する
- `incoming/` にライフサイクルのルールを置き、検査されずに残ったものを消す

## 検証事項

- 図の配信に付けている CSP（`sandbox`）の下で、ブラウザの PDF ビューアが PDF を開けること（DEV-82）
- LocalStack の S3 が、署名付き POST の条件（大きさの上限など）を AWS と同じに扱うこと（DEV-81）
