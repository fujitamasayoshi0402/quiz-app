# ADR-0014: Aurora へは IAM 認証で接続し、ロールは Data API で作る

- ステータス: Accepted
- 決定日: 2026-09-24

## 背景と課題

ローカルでは、DB のロールを 2 つに分けている。

- `quiz` … スキーマの所有者。マイグレーション（DDL）を実行する
- `quiz_app` … アプリの接続先。所有者でもスーパーユーザーでもないため、行レベルセキュリティ（RLS）が効く

Aurora でも同じ分離を再現する。そのために 2 つを決める必要がある。

1. **ロールを作る SQL を、どこから流すか。** Aurora はインターネットへの経路がないプライベートサブネットにあり（ADR-0013）、手元から直接は届かない
2. **アプリとマイグレーションが、どう認証するか**

制約として、**Terraform の state にパスワードを入れない**（ADR-0011）。リポジトリは Public である。

## 判断基準

- パスワードがリポジトリ・state・ログのどこにも残らない
- 踏み台のような、常時動くものや面倒を見るものを増やさない
- 所有者（DDL の権限）として接続できるのを、マイグレーションのタスクだけに限れる
- アプリの変更が小さい

## 検討した選択肢

### ロールを作る経路

**A: Data API**。Aurora の HTTP エンドポイントを有効にし、`aws rds-data execute-statement` で SQL を流す。
IAM で認可され、VPC の中に経路が要らない。Terraform の `local-exec` から呼べる。追加の費用はない。
一方で、Data API とマスターユーザーの認証情報を読める IAM の主体は、誰でもマスターとして SQL を流せる。

**B: 踏み台 + Terraform の PostgreSQL provider**。EC2 を置き、SSM のポートフォワードで接続する。
ロールを Terraform のリソースとして持てる。plan のたびにトンネルが要り、踏み台の費用と更新の手間がかかる。

**C: ECS の単発タスク**。psql を入れたイメージで流す。ECS ができる（DEV-45）まで作れない。

### アプリとマイグレーションの認証

**D: パスワードを Secrets Manager に置く**。ECS がタスクの起動時に環境変数へ注入する。アプリの変更は要らない。

- パスワードを設定する SQL（`CREATE ROLE ... PASSWORD '...'`）に平文が入る。A で流すと、API のリクエストに乗る
- state に残さないよう、ephemeral な乱数と write-only の属性を組み合わせる必要がある
- シークレット 1 つにつき月 0.4 ドル

**E: IAM データベース認証**。ロールに `rds_iam` を与え、接続のたびに IAM の署名から作る 15 分のトークンをパスワードとして使う。
タスクロールに `rds-db:connect` を与えた相手だけが、そのロールとして接続できる。

- パスワードが存在しない。SQL にも state にも秘密が乗らない
- 「どのタスクがどのロールで接続できるか」を IAM のポリシーで表せる
- アプリに AWS Advanced JDBC Wrapper（IAM のプラグイン）が要る。ローカルはパスワードのままなので、接続の設定が環境で分かれる
- 新しい接続の頻度に上限がある（毎秒数百程度）。接続プールを使うので、この規模では当たらない

## 決定

**A と E を採用する。**

- ロールは `infra/terraform/modules/database/sql/bootstrap_roles.sql` に書き、Terraform が Data API で流す。
  SQL は何度流しても同じ結果になるように書き、中身を変えると次の apply で再び流れる
- マスターユーザー（`quiz_admin`）のパスワードは RDS が作って Secrets Manager で管理する（`manage_master_user_password`）。
  使うのはロールの作成だけで、アプリもマイグレーションもマスターでは接続しない
- `quiz` と `quiz_app` はパスワードを持たず、IAM 認証で接続する
  - `quiz` への `rds-db:connect` は、マイグレーションの単発タスクのロールにだけ与える
  - `quiz_app` への `rds-db:connect` は、quiz-service のタスクロールに与える

A を選んだのは、踏み台なしで済み、ECS を待たずにロールまで作れるため。
E を選んだのは、D ではパスワードを SQL に書かざるを得ず、A と組み合わせると平文が API のリクエストに乗るため。
E ならパスワードそのものがなくなり、「所有者の権限をアプリに持たせない」を IAM のポリシーで表せる。

## 結果

### 良い影響

- アプリ用とマイグレーション用のパスワードが存在しない。漏れるもの・入れ替えるものがない
- 所有者として接続できる相手が、IAM のポリシーで読める
- 踏み台も、アプリ用のシークレットも持たない

### 悪い影響・受け入れるリスク

- アプリに AWS Advanced JDBC Wrapper を入れる。AWS とローカルで接続の設定が分かれる
- Data API が有効なため、SecurityGroup を通らずに SQL を流せる経路がある。守りは IAM だけになる
- ロールの作成は `local-exec` なので、apply する環境に AWS CLI が要る。ロールが Terraform のリソースとしては見えない

### 緩和策

- Data API とマスターユーザーのシークレットを使えるのは、管理者の SSO ロールだけにする。
  CI のロール（DEV-48）やタスクロールには与えない
- 接続の設定の差は Spring のプロファイルと環境変数に閉じ込め、コードの分岐にしない
- ロールの属性は、作成後に `pg_roles` で確かめる（NOSUPERUSER / NOBYPASSRLS）

## 検証事項

- Flyway と Spring Boot が、AWS Advanced JDBC Wrapper の IAM プラグイン経由で接続できること（DEV-45）
- AWS 上で、`quiz_app` として接続したときに別テナントの行が返らないこと。マイグレーションを流した後でないと確かめられない（DEV-45）
