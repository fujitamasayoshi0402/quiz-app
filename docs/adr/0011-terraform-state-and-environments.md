# ADR-0011: tfstate は 1 つの S3 バケットにキーで分けて置き、環境はルートモジュールで分ける

- ステータス: Accepted
- 決定日: 2026-09-24

## 背景と課題

Phase 2 から AWS のリソースをすべて Terraform で管理する。その前に、次の 3 つを決める必要がある。

- state をどこに置き、同時実行をどう防ぐか
- state を置く場所そのものを、どう作るか
- dev と prod をどう分けるか

**どれも後から変えると state の移行が伴う。** 移行を誤ると、作ったリソースが Terraform の管理から外れる。
課題が 1 つ目のリソースを作る前に決める。

前提として、AWS アカウントは 1 つ（IAM Identity Center で SSO）、運用するのは 1 人。
常時かかる費用は最小にする（[開発ガイドライン](../development-guidelines.md) のコスト方針）。

## 判断基準

- state を失わない。壊しても戻せる
- 同時に apply しても state が壊れない
- 手作業の手順を残さない。「最初の 1 回だけコンソールで作った」ものを作らない
- 常時かかる費用と、管理するものの数が少ない

## 検討した選択肢

### 同時実行の防ぎ方

**A-1: S3 ネイティブのロック（`use_lockfile`）**。Terraform 1.10 で入った。state の隣にロック用のオブジェクトを置く。
追加のリソースが要らない。

**A-2: DynamoDB のテーブルでロック**。以前の標準。Terraform 側で非推奨になっており、将来外される。
テーブルが 1 つ増える（オンデマンドなら費用はほぼ無い）。

### state バケットの作り方

**B-1: Terraform の bootstrap 用ルートモジュール**。最初はローカル state でバケットを作り、
そのあと自分の state もそのバケットへ移す。すべて Terraform で完結する。
一方で、作り直すときだけ手順が特殊になる（backend の設定を一時的に外す）。

**B-2: CloudFormation のスタック**。state の置き場所に悩まずに済む。IaC の道具が 2 つになる。

**B-3: bootstrap の state をローカルに残す**。手順は最も単純。PC を失うと、バケットが Terraform の管理外になる。

### 環境の分け方

**C-1: 1 アカウント・1 バケット、キーで分ける**（`dev/`、`prod/`、`bootstrap/`）。追加の費用も管理も無い。
dev の作業者が prod の state を読み書きできることを、権限で防げない。

**C-2: 1 アカウント、環境ごとにバケットを分ける**。バケットポリシーで境界を引きやすい。バケットが増える。

**C-3: 環境ごとに AWS アカウントを分ける**（AWS Organizations）。事故の影響範囲を最も小さくできる。
アカウント・SSO の割り当て・請求の管理が増える。

### 環境をどう表すか

**D-1: 環境ごとのルートモジュール**（`envs/dev`、`envs/prod`）。共通部品は `modules/` に置く。
環境の差がコードの差分として読める。

**D-2: 1 つのルートモジュールを workspace で切り替える**。コードは 1 つで済む。
いまどの環境を触っているかがコードに現れず、切り替え忘れがそのまま prod への apply になる。

## 決定

**A-1、B-1、C-1、D-1 を採用する。**

- state は `quiz-app-tfstate-a0139cba` に置く。キーは `bootstrap/`、`dev/`、`prod/`
- ロックは S3 ネイティブ（`use_lockfile = true`）
- バケットは `infra/terraform/bootstrap` で作り、その state も同じバケットに置く
- 環境は `infra/terraform/envs/{dev,prod}` の別々のルートモジュールで表す
- 全リソースに `default_tags`（`Project` / `Env` / `ManagedBy`）を付ける

バケットには次を設定する。

| 設定 | 理由 |
| --- | --- |
| バージョニング | 壊した state を 1 つ前に戻す |
| 古い版を 90 日で削除 | ロックのオブジェクトも作っては消すため、古い版がたまる |
| SSE-S3 で暗号化 | カスタマー管理キーは月額がかかる。state にパスワードを入れない方針（DB のパスワードは Secrets Manager） |
| パブリックアクセスのブロック、ACL の無効化 | アクセスの制御をポリシーだけにする |
| TLS 以外の通信を拒否 | |
| `prevent_destroy` | 誤って消すと、全環境のリソースが管理外になる |

バケット名の末尾は乱数にした。バケット名は全世界で一意である必要があり、
アカウント ID を公開リポジトリに出さないため。

## 結果

### 良い影響

- 追加のリソースはバケット 1 つだけ。費用は state の容量分（数円）に収まる
- 手作業の手順が残らない。バケットの設定もコードで読める
- dev と prod の差が、ディレクトリの差分としてレビューできる

### 悪い影響・受け入れるリスク

- dev と prod が同じアカウントにある。dev の作業で prod のリソースに触れうる
- state のバケットを権限で環境ごとに分けていない
- bootstrap を作り直すときだけ、backend の設定を一時的に外す手順が要る

### 緩和策

- apply はルートモジュールのディレクトリで実行する。どの環境を触っているかがパスに現れる
- prod を作るのは dev が安定してから。CI からの apply（OIDC）を入れるときに、環境ごとのロールで権限を分ける
- 公開後に事故の影響を切り分ける必要が出たら、C-3（アカウント分割）へ移る。state はキーごとに移せる
