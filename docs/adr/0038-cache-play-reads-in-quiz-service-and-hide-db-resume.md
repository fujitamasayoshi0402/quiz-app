# ADR-0038: 出題の読み取りを quiz-service のメモリに持ち、DB の起動待ちを操作の裏に隠す

- ステータス: Accepted
- 決定日: 2026-11-19

## 背景と課題

Aurora Serverless v2 は、使われないと一時停止する（min 0 ACU、prod は 15 分）。止まっている DB への最初の要求は、復帰を待って 15〜28 秒かかる（DEV-226）。
見に来た人の最初の操作は、たいていこの待ちに当たる。画面は 3 秒を過ぎると案内を出すが（DEV-90、DEV-226）、待つことは変わらない。

はじめは、公開したクイズを JSON にして CloudFront から配り、一覧と出題で DB を起こさない案を考えた（DEV-233）。
調べると、それだけでは待ちが消えないことが分かった。

- **ログインした人の要求は、どれも先に DB を 3 回引く。** 利用者（`UserAccounts.findIdByExternalId`）、テナント（`TenantResolutionFilter`）、
  所属とロール（`TenantMemberships.findRole`）。一覧だけを別の場所から配っても、同じ画面の「中断中」「今日の復習」「あとで見直す」の要求が DB を起こす
- **「始める」は DB に書く。** 挑戦を作り、出す問題を選んで残す。デモの入口の「おすすめの5問を始める」は、押した瞬間に復帰を待つ
- **prod で DB を起こしたのは、ほぼ見に来た人の操作だった**（DEV-232）。いちばん多い最初の要求は `GET /api/me/tenants`。配り方を変えても、見に来るたびに DB は起きる

## 判断基準

- 一覧と最初の問題が、DB が止まっていてもすぐ出ること
- テナントの境界（所属していないテナントは読めない）を、今と同じ場所（quiz-service）で守ること
- 費用を増やさないこと。Terraform を足さずに済むなら、そのほうがよい
- 公開・編集・所属の変更が、すぐ（遅くとも数分で）反映されること

## 検討した選択肢

| 選択肢 | 待ち | 費用 | 良い点 | 悪い点 |
| --- | --- | --- | --- | --- |
| **A. quiz-service のメモリに読み取りを持ち、DB の復帰を操作の裏で進める（採用）** | 一覧と最初の問題はすぐ出る。復帰は、選んだり読んだりしている間に済ませる | 変わらない | Terraform が要らない。境界の検査は今のまま | メモリの中身を、変更に合わせて消す必要がある。タスクが 1 つであることを前提にする |
| B. 公開したクイズを S3 に置き、CloudFront から配る | 一覧はすぐ出る。「始める」で待つ | 変わらない | 配る仕組みはアプリと切り離せる | テナントごとの署名付き Cookie が要り、出すには所属を DB で確かめる。S3・CloudFront・無効化の Terraform、web と mobile が 2 か所から読む |
| C. A に加え、回答の記録も後でまとめて書く | どこでも待たない | 月 2〜3 ドル減る | DB を起こす回数そのものが減る | 履歴・復習・ランキングの反映が遅れる。書き損じたときの扱いまで持つ。減る額に比べて大きい |
| D. DB を一時停止させない（min 0.5 ACU） | 待たない | 月 約 50 ドル増える（0.5 ACU × 730 時間） | 何も作らない | 予算（月 30 ドル）を超える |

## 決定

**A を採る。** prod の quiz-service はタスク 1 つで常に動いている（[ADR-0024](0024-run-prod-in-same-account-and-launch-at-release.md)）。
DB が一時停止している間も、タスクのメモリは消えない。読むものをメモリに持てば、DB が止まっていても答えられる。

### 1. 読み取りをメモリに持つ（DEV-233）

| 持つもの | 鍵 | 消すとき |
| --- | --- | --- |
| 利用者の ID（`external_id` → `core.users.id`） | 認証基盤の ID | 対応を書き換えたとき（メールでの引き継ぎ） |
| テナントの ID（slug → ID） | slug | テナントを消したとき |
| 所属とロール | テナント × 利用者 | 参加・招待の受諾・ロールの変更・退会・削除のとき |
| 所属するテナントの一覧（`/api/me/tenants`） | 利用者 | 同上 |
| 出題できるカテゴリの一覧（問題数・代表の図を含む） | テナント | クイズ・カテゴリ・難易度・図を変えたとき（パックの流し込みも API を通るので同じ） |
| 解説図の保存先（図の ID → オブジェクトのキー） | テナント × 図 | 図を差し替え・消したとき |

- **消すのは、変更を受けたその場で行う。** 変更はすべてこのタスクの API を通る。念のため、どれにも数分の期限を付ける。DB を直接書き換えたとき（マイグレーション、運用の作業）も、期限で追いつく
- **テナントで分けて持つ。** DB では行レベルセキュリティがテナントを分けている（[ADR-0006](0006-row-level-multi-tenancy.md)）。メモリには RLS が効かないため、鍵に必ずテナントを含め、テナントを決めずに引ける形にしない
- **持つのは読み取りだけ。** 回答の記録・挑戦・履歴・復習・ランキングは、今どおり DB を読み書きする
- 出題の画面は、カテゴリの一覧だけを待って表示している。一覧がメモリから返れば画面はすぐ出る。同じ画面の「中断中」「今日の復習」「あとで見直す」は DB を読みに行き、それが復帰の合図になる。待っている間も画面は使える

### 2. 「始める」の待ちを、最初の問題を読む時間に隠す（DEV-240。DEV-239 のあと）

- 出す問題の中身をメモリに持ち、「始める」はメモリから問題を選んで、挑戦をすぐ返す。DB への書き込みは裏で続け、復帰を待つ
- 回答を受けたとき、挑戦がまだ DB に書けていなければ、書けるまでその要求を待たせる。最初の問題を読んでいる間（10 秒以上）に、たいてい復帰は終わる
- 中断中の挑戦があるかは、メモリの状態で判断する。挑戦の開始・完了・破棄はこのタスクを通るため、メモリが正しい。起動の直後だけは DB から読み込む
- 中断中の挑戦は勝手に破棄しない（DEV-224）。重なったときは、今どおり 409 を返して再開か破棄かを選ばせる
- 「間違えた問題」「あとで見直す」「今日の復習」から出すときは、選ぶのに DB が要る。これらは今どおり DB を待つ（同じ画面の読み込みで、すでに起きていることが多い）

## 結果

### 良くなること

- 見に来た人は、一覧と最初の問題を待たずに見られる。復帰の 15〜28 秒は、選んだり読んだりしている間に過ぎる
- Terraform と新しい AWS のリソースが要らない。テナントの境界は、今と同じ quiz-service の検査で守る

### 引き受けること

- **タスクが 1 つであることを前提にする。** 2 つ以上にすると、ほかのタスクのメモリを消す仕組み（イベントでの通知など）が要る。増やすときは、この ADR を見直す
- タスクが替わった直後（デプロイ、dev の起動）は、メモリが空で、最初の要求は今どおり DB を待つ
- 所属を外しても、外した操作がこのタスクを通らない場合は、期限が切れるまで（数分）前のロールで読める
- 費用は下がらない。見に来るたびに DB が起きることは変わらない（下げる案は C。今は採らない）
- 新しい依存（キャッシュのライブラリ）が増える
