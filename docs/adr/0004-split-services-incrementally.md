# ADR-0004: マイクロサービスへの分割は段階的に行う

- ステータス: Accepted
- 決定日: 2026-09-21

## 背景と課題

本プロジェクトの目的のひとつは、マイクロサービスアーキテクチャと非同期連携を実際に構築することにある。
一方で、扱うドメインは「クイズ」「カテゴリ」「難易度」「回答」「通知」であり、
現時点ではそれぞれの境界がどこにあるかを確信を持って言えない。

分割の判断を誤った場合のコストは非対称である。
分割しすぎた場合は、ひとつの機能追加が複数サービスの同時変更を要求し、
サービス間のバージョン整合やローカル環境の複雑化が恒常的な負担になる。
一方、分割が足りない場合は、後から切り出す作業が発生するだけで済む。

## 判断基準

- ドメイン境界が誤っていた場合の修正コストが小さいこと
- 早い段階で「動くもの」に到達できること
- マイクロサービスとして説明できる構成に最終的に到達すること

## 検討した選択肢

### 選択肢 A: 最初からサービスを分割する

quiz / answer / notification を最初から独立したデプロイ単位にする。
目的には最短で到達するが、境界が固まる前に分割線を引くことになる。
インフラ・CI・ローカル環境の構築コストが機能実装より先に発生し、
「動くもの」に到達するまでの時間が長くなる。

### 選択肢 B: 単一デプロイ単位で始め、境界のみ先に引く

ひとつのサービス内でモジュールとして実装しつつ、以下の 2 点で境界を明示しておく。

- **DB スキーマを分ける**。モジュールをまたぐテーブル結合を禁止する
- **状態変化をドメインイベントとして発行する**。モジュール間の直接呼び出しを避ける

この 2 つを守っていれば、分割時の作業は「モジュールを別プロセスに移し、
イベントの配送をインメモリから EventBridge に差し替える」ことに限定される。

### 選択肢 C: モノリスのまま完成させる

最も速いが、本プロジェクトの目的のひとつを満たさない。

## 決定

**選択肢 B を採用する。**

- Phase 1〜4 は `quiz-service` 単一のデプロイ単位で実装する。
  回答・採点は同一サービス内の独立したモジュールとし、スキーマを分ける
- 通知のみ Phase 5 で `notification-service`（Lambda）として最初から独立させる。
  通知は他モジュールから参照されず、境界が明確なため
- 回答・採点の物理分割は、境界が安定したと判断できた段階で実施する。
  分割しないという判断もあり得る

「マイクロサービスにする」こと自体を目的とせず、**分割によって得られるものと失うものを
判断した過程**を残すことを重視する。

## 結果

### 良い影響

- 早い段階で動作するアプリケーションに到達できる
- ドメインの理解が進んだ状態で分割の判断ができる
- 分割の前後を同じリポジトリで比較でき、判断の過程が記録として残る

### 悪い影響・受け入れるリスク

- 分割作業が後工程に残る
- スキーマ分離とイベント経由の呼び出しを規律として守り続ける必要がある。
  守れていないと、分割時に想定以上の作業が発生する

### 緩和策

- モジュールをまたぐテーブル結合を禁止し、レビュー時に確認する
- モジュール間の呼び出しはイベント経由に統一する。Phase 1 ではインメモリのイベントバスで実装し、
  Phase 5 で EventBridge に差し替える。このときアプリケーションコードの変更が最小になるよう、
  発行側はインターフェースに依存させる

## 検証事項

- インメモリのイベントバスから EventBridge への差し替えが、実装の変更をどの程度で済ませられるか
- 回答・採点モジュールが、クイズ本体と独立してスケールさせるべき負荷特性を持つか（Phase 6 の負荷試験で計測）
