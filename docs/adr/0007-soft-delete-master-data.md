# ADR-0007: マスタデータを論理削除する

- ステータス: Accepted
- 決定日: 2026-09-22

## 背景と課題

カテゴリ・難易度・クイズを削除したとき、それらを参照している回答履歴が残る。
物理削除すると、履歴から「何のクイズに答えたのか」を辿れなくなる。
過去のスコアは残るのに、その中身が失われた状態になる。

もうひとつの問題は復旧手段である。管理者は各テナントに少数しかおらず、
誤って削除したときに気づいて戻してくれる相手がいない。
とくにカテゴリの削除は配下の難易度とクイズに波及するため、影響が大きい。

## 判断基準

- 誤削除から復旧できること
- 削除後も回答履歴が意味を保つこと
- 削除済みを見せてしまう事故が起きにくいこと
- 実装量が個人で運用できる範囲に収まること

## 検討した選択肢

### 選択肢 A: 物理削除し、参照があれば削除を拒否する

回答されたことのあるクイズは削除できない、という制約を課す。
実装は単純で、履歴の整合性も保たれる。

しかし**一度でも回答されたクイズは永久に消せない**。
出題をやめたクイズも管理画面に残り続け、クイズ一覧が使われないデータで埋まっていく。
「消したいが消せない」状態は、いずれ別の回避策（非公開フラグなど）を生み、
結局は論理削除に似た仕組みを後から作ることになる。

### 選択肢 B: 物理削除し、回答時に問題文を履歴へコピーする

回答した時点の問題文と選択肢を `answers` に保存しておく。
クイズを削除しても履歴は読める。
クイズを修正しても過去の履歴は当時の内容を保つため、
「出題時点の問題」を正確に残せるという利点もある。

ただし削除したものを**復旧できない**。
また同じ問題文が回答のたびに複製され、データ量が回答数に比例して増える。

### 選択肢 C: 論理削除する

削除フラグを立てるだけで、行は残す。
履歴からの参照は保たれ、復旧もできる。

代償として、**すべてのクエリに「削除済みを除く」条件が必要**になる。
書き漏らせば削除済みのカテゴリが選択肢に現れる。
ユニーク制約も素直には効かない。カテゴリ「AWS」を削除したあと、
同じ名前で作り直そうとすると、削除済みの行と衝突する。

## 決定

**選択肢 C を採用する。**

### 対象

| テーブル | 論理削除 | 理由 |
| --- | --- | --- |
| `tenants` / `categories` / `difficulties` / `quizzes` | する | 管理者が削除でき、履歴から参照される |
| `choices` | しない | クイズに完全に従属する。クイズの `deleted_at` が見え方を決める |
| `answers` | しない | 履歴そのもの。削除する操作を設けない |
| `tenant_members` | する | 所属の解除を取り消せるようにする |

### 実装方針

- `deleted_at`（NULL 許容のタイムスタンプ）を持たせる。NULL が生存
- ユニーク制約は**部分インデックス**にする
  （PostgreSQL の `UNIQUE (tenant_id, name) WHERE deleted_at IS NULL`）。
  これにより、削除済みと同じ名前で作り直せる
- **カテゴリの削除は配下の難易度とクイズに連鎖する。** 復活も連鎖する
- 連鎖の単位は削除操作ごとの ID（`deletion_batch_id`）で表す。
  `deleted_at` の一致で判定すると、**同じ時刻になったのが偶然か意図かを区別できない**
- 削除の前に影響範囲（配下のクイズ数）を提示して確認を求める
- 管理画面に「削除済み」の一覧を設け、そこから復活できる

### 物理削除を設けない

削除済みを完全に消す操作は作らない。
個人で運用する規模では、テーブルの肥大化よりも、誤って完全削除する危険の方が大きい。
必要になれば、保持期間を決めたバッチ処理として後から追加する。

## 結果

### 良い影響

- 誤削除から復旧できる
- 削除後も回答履歴が意味を保つ
- 「使わなくなったから消す」判断を気軽にできる。戻せるため

### 悪い影響・受け入れるリスク

- **すべてのクエリに削除条件が必要になる。** 書き漏らすと削除済みが表示される。
  テナント絞り込みと同じ構造の危険だが、こちらは情報漏洩ではなく表示の不整合にとどまる
- ユニーク制約が部分インデックスになり、通常の制約より読み取りにくい
- 行が単調増加する
- **連鎖削除の実装が必要になる。** カテゴリ 1 件の削除が、配下の難易度・クイズ・選択肢に波及する

### 緩和策

- リポジトリ層の共通機構で削除条件を強制する。テナント絞り込みと同じ仕組みに乗せる
- 削除済みを取得する操作は、管理画面の復活機能専用のメソッドに限定する。
  通常の取得メソッドからは決して削除済みが返らないようにする
- 連鎖の対象と順序をドメイン層に閉じ込め、呼び出し側が個別に消して回らないようにする

## 検証事項

- ~~**RLS ポリシーに `deleted_at IS NULL` を含めるべきか。**~~ → **含めない**（DEV-35 で決定）。
  含めると削除済み一覧を取得できず、復活機能が作れない。
  復活用に別のポリシーやロールを足すと、テナント分離の仕組みが二重になり、
  **どちらが効いているのか追いにくくなる**。分離の仕組みは 1 つに保つ。
  削除条件の書き漏らしは情報漏洩ではなく表示の不整合にとどまるため、
  アプリケーション層と、通常の API が削除済みを返さないことを確かめるテストで担保する
- ~~連鎖削除をアプリケーション側のループで行うか、DB のトリガーや外部キーの挙動に委ねる~~
  → **アプリケーション層で行う**（[DB 設計](../db-schema.md#連鎖削除と連鎖復活)で決定、DEV-35 で実装）。
  トリガーに委ねると、削除が起きたことがコードから見えなくなる。
  ただし 1 行ずつのループにはせず、テーブルごとに 1 文の `UPDATE` で消す。件数が増えても本数が変わらない。
  配下から先に消す順序にしている。途中で失敗したときに「親だけ消えて子が残る」順序を選ばないため
- 論理削除されたクイズを参照する回答履歴を、画面上でどう表示するか（「削除されたクイズ」と示すか、通常どおり表示するか）
- 復活時の名前の衝突をどう案内するか。いまは 409 と理由（`obstacle`）を返すだけで、
  改名して復活させる導線は用意していない
