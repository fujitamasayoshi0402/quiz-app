# ADR-0031: 公式の技術ニュースから、AI（Bedrock）が毎日クイズの下書きを作る。Lambda が S3 に置き、quiz-service が使われたときに取り込む

- ステータス: Accepted
- 決定日: 2026-10-15

## 背景と課題

デモのテナントのクイズは、シード（`R__demo_data.sql`）で入れたものから増えない。
公式の技術ニュースから、AI がクイズの下書きを毎日作り、管理者が確かめて公開する流れを作る。

画面から管理者が呼ぶ下書きの機能も考えたが、後に回す。サインアップは誰でもでき、テナントは 1 人 1 つ作れる（[ADR-0028](0028-let-signed-in-users-create-their-own-tenant.md)）。
テナントごとの回数の上限だけでは、アカウントを増やされると費用に天井がない。毎日決まった数を作るバッチなら、費用は件数だけで決まる。

決めること。

- **情報源。** どこから、何を読むか。記事の本文を取り込むと、著作権が問題になる
- **AI の誤り。** 技術クイズで誤った正解を出すと、アプリそのものの信頼を損ねる
- **動かし方。** quiz-service と Aurora は、使われていないときに止まっている（夜間の停止、Aurora の自動一時停止）
- **費用の上限**と、Bedrock の権限

## 判断基準

- **費用に天井があること。** 予算は月 30 ドル（開発ガイドライン「コスト方針」）。Aurora を、このために起こさない
- **人が確かめるまで、解く人に出さないこと**
- 公式の発表の事実だけを使い、文章を写さないこと
- 認証の経路と、テナントの境界の外を増やさないこと

## 検討した選択肢

### 動かし方

#### A. Lambda が下書きを作って S3 に置き、quiz-service が使われたときに取り込む

EventBridge Scheduler が毎日 Lambda を起動する。Lambda は RSS と Bedrock で下書きを作り、取り込みの形式の JSON を S3 に置くだけ。
quiz-service は、利用者の要求で DB を使ったあとに S3 を見て、置かれたものを取り込む（Outbox の拾い直しと同じ動き方。開発ガイドライン「イベント」）。

- 利点: Aurora を起こさない。quiz-service が止まっていても失敗しない。ボット用のログインの情報が要らない
- 欠点: quiz-service に、S3 を見て取り込む処理が加わる。取り込まれるのは、次に誰かが使ったとき

#### B. Lambda が取り込みの API を呼ぶ

既存の取り込みの API（`POST /api/t/{slug}/admin/quizzes/import`）を、ボットの管理者として呼ぶ。トークンはスモークテストと同じ方式で取る。

- 利点: quiz-service を変えずに済む。検証も行レベルセキュリティも、いまの取り込みのまま
- 欠点: quiz-service が止まっていると失敗する。毎日 Aurora を起こす（月 1 ドルほど）。ボットのパスワードを管理し、管理者として振る舞う利用者が 1 人増える

#### C. quiz-service の中で全部行う

使われたときに、quiz-service 自身が RSS と Bedrock を呼ぶ。

- 利点: 部品を増やさない
- 欠点: アプリのロールに Bedrock の権限が付く。数十秒かかる AI の呼び出しが本体の中で動き、夜間の停止で途中で止まりうる

### モデル

| モデル | 100 万トークンあたり（東京、グローバル） | 向き |
| --- | --- | --- |
| Claude Haiku 4.5 | 入力 1 ドル / 出力 5 ドル | 日本語の文章と、決まった形の出力に十分 |
| Claude Sonnet 4.6 | 入力 3 ドル / 出力 15 ドル | 質は上がるが、3 倍 |
| Amazon Nova Lite | 入力 0.06 ドル / 出力 0.24 ドル | 安いが、日本語の解説の質が足りるか分からない |

Haiku 4.5 の値は、AWS の Price List API（`AmazonBedrockFoundationModels`、`ap-northeast-1`）で確かめた。Sonnet と Nova は公開されている情報による。
日本の中に限って処理する呼び方（`jp.` の推論プロファイル）は 1 割高い（Haiku 4.5 は入力 1.1 ドル / 出力 5.5 ドル）。

## 決定

**動かし方は A（Lambda が S3 に置き、quiz-service が取り込む）、モデルは Claude Haiku 4.5（グローバルの推論プロファイル）を採用する。**

```
EventBridge Scheduler（毎日）→ Lambda（news-quiz-drafter）
  ├ AWS の What's New の RSS を読む
  ├ Bedrock（Haiku 4.5）: 選ぶ → 作る → 確かめる
  └ S3 の受け箱（inbox/）に、取り込みの形式の JSON を置く
quiz-service（利用者の要求で DB を使ったあとに見る）→ S3 の受け箱 → デモのテナントに下書きとして入れる → 取り込んだものを受け箱から消す
```

### 情報源

| 項目 | 決めたこと |
| --- | --- |
| 読むもの | AWS の What's New の RSS（`aws.amazon.com/about-aws/whats-new/recent/feed/`）。公式の発表で、1 日に数十件ある |
| 使う部分 | RSS の見出しと説明（1 件 1,000〜1,600 文字ほど）だけ。リンク先のページは読まない |
| 写さない | 説明の文章を、クイズにそのまま入れない。事実をもとに、日本語で問題と解説を書かせる |
| 出典 | 解説の最後に、元の発表へのリンクを付ける。クイズの行にも元の発表の URL を持つ |

ほかの情報源（各製品のリリースノートなど）は、同じ形で足せるようにしておくが、いまは足さない。

### AI の使い方

1 回の起動で、Bedrock を 3 段で呼ぶ。

1. **選ぶ**: 前の回より新しい発表の見出しから、クイズにできる（事実がはっきりした）ものを最大 3 件選ぶ
2. **作る**: 1 件ずつ、問題・4 つの選択肢・正解・解説（Markdown）を、決まった形（JSON）で書かせる
3. **確かめる**: 作ったクイズと元の説明を渡し、正解が説明と食い違っていないか、ほかの選択肢が正解になりえないかを判定させる。食い違えば捨てる

- 出力は、quiz-service の取り込みと同じ決まり（選択肢 4 つ、正解 1 つ、長さの上限）で確かめ、満たさないものは捨てる
- 一度読んだ発表（RSS の `guid`）は、S3 に 30 日残し、二度使わない
- 呼び出しごとに、出力のトークンの上限を決めておく

### 入れる先と、人の確認

| 項目 | 決めたこと |
| --- | --- |
| テナント | デモのテナント。設定（`app.news-quizzes.*`）で決め、slug をコードに書かない |
| カテゴリと難易度 | 「AWS の最新情報」と「ニュース」（レベル 1）。シードが作る |
| 状態 | **下書き。** 管理者が確かめて公開するまで、出題されない |
| 印 | クイズに、元にした発表の URL（`source_url`）を持たせる。空でないものが、AI が作ったもの。公開したあとも残し、解く人にも出典を示す |
| 取り込むとき | 取り込みの API と同じユースケースを使う。全部か無しか |
| 確かめられていないものがたまったとき | デモのテナントに、AI が作った下書きが 30 件あれば取り込まない。受け箱に 30 件たまれば、Lambda は Bedrock を呼ばずに終わる。確かめない間は、費用もかからない |

### quiz-service の取り込み

- **利用者の要求で DB を使ってから 5 分の間に、前に見てから 1 時間たっていれば受け箱を見る**（Outbox の拾い直しと同じ）。決まった時刻には動かさない。Aurora を起こさない
- 対象のテナントを設定して書く。テナントをまたぐ印は作らない（データの整合性の確認と同じ。開発ガイドライン「データの整合性」）
- アプリのロールに足すのは、受け箱のバケットの `inbox/` を読む・消す権限だけ

### 費用の上限と権限

| 項目 | 決めたこと |
| --- | --- |
| 1 日の件数 | 最大 3 件 |
| 1 回の費用（見込み） | 選ぶ 約 0.004 ドル、作る・確かめる 1 件 約 0.01 ドル。1 日 約 0.035 ドル、**月 約 1 ドル** |
| Bedrock を呼べるロール | この Lambda のロールだけ。モデルは Haiku 4.5 の推論プロファイルに限る |
| 失敗したとき | Lambda のエラーで、既存のアラーム（SNS）に知らせる。その日は作らない。次の日に、前の回より新しいものから作る |
| 予算 | 既存の予算（月 30 ドル）のアラートで見る |

- Lambda は notification-service と同じく Kotlin で書き、Spring は使わない（開発ガイドライン「通知」）
- dev だけで動かす。prod は、公開のときに決める

## 結果

### 良い影響

- デモのテナントに、新しいクイズが毎日（確かめた分だけ）増える
- 費用は件数だけで決まり、月 1 ドルほど。誰が叩いても増えない
- Aurora を起こさない。quiz-service が止まっていても、作ることは続く

### 悪い影響・受け入れるリスク

- **AI の誤りは、確かめる人が見落とすと公開される。** 確かめる段で減らすが、0 にはならない。解く人に、AI が作ったものであることと出典を示す
- 取り込まれるのは、次に誰かが使ったとき。使われない日が続くと、受け箱にたまる
- 管理者が確かめないと、30 件で止まる。止まっている間は、新しい発表を飛ばす（あとから作り直さない）
- RSS の説明に、AI への指示のような文が紛れ込む余地がある（プロンプトインジェクション）。読むのは AWS の公式の発表だけで、出力は下書きにしかならず、人が確かめる。解説は Markdown として表示し、生の HTML は通さない（[ADR-0018](0018-write-explanations-in-markdown-and-render-on-screen.md)）

## 検証事項

- 確かめる段で捨てた割合と、人が直した割合。高ければ、モデル（Sonnet）を見直す
- 1 回の費用を、Lambda のログ（入力と出力のトークン数）で確かめ、この試算と比べる
- 画面から管理者が呼ぶ下書きの機能は、全体の回数の上限を掛ける形で、求められてから決める
