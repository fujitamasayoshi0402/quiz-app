# ADR-0035: 共有のデモのアカウントに「見学者」のロールを与え、管理画面を読むだけで使えるようにする

- ステータス: Accepted
- 決定日: 2026-10-27

## 背景と課題

管理画面には、見せたい機能が多い。クイズの編集、draw.io の図、AI の下書きの確認、削除済みからの復活、通知の設定がある。
しかし共有のデモのアカウント（[ADR-0029](0029-let-visitors-sign-in-as-shared-demo-account-without-login-screen.md)）は、デモのテナントの一般ユーザーで、管理画面を開けない。
管理画面を見るには、サインアップして自分のテナントを作る必要がある（[ADR-0028](0028-let-signed-in-users-create-their-own-tenant.md)）。そのため、見に来た人の多くは管理画面を見ないまま帰る。

見に来た人が、サインアップせずに管理画面の主な機能を見られるようにする。決めることは次のとおり。

- **見せ方。** 誰として、どのテナントの管理画面を見せるか
- **どこまで見せるか。** 管理の API には、正解や、人のメールアドレスを返すものがある
- **変えようとしたときの画面**

## 判断基準

- **パスワードを公開したアカウントで、データを変えられないようにする。** 変えられると、誰かが不適切な文や画像を置いたとき、ほかの見た人がそれを見る
- 認可の仕組みを増やさない。いまの「パスで判定し、ロールは DB に持つ」（`TenantAccessInterceptor`）の延長に収める
- **管理の API を足したとき、書き忘れても見学者に見えないようにする。** 既定で閉じる
- 定期的に動く処理を増やさない。Aurora の一時停止を妨げない（開発ガイドライン「コスト方針」）

## 検討した選択肢

### 見せ方

#### A. 見学者のロールを足し、管理の API は読むだけ許す

所属のロールに `viewer` を足す。デモのアカウントは、デモのテナントで `viewer` として所属する。
見学者は、管理の API の読み取りを使え、変更は 403 になる。出題の API は一般ユーザーと同じく使える。

- 利点: いまの認可の判定に、ロールを 1 つ足すだけで済む。デモのテナントの中身は運用者のパックのまま変わらない
- 欠点: 保存や削除を試せない。どの API を読ませるかを、API ごとに決める必要がある

#### B. 見学用のテナントを別に作り、共有の管理者として触らせる。毎晩パックから作り直す

- 利点: 管理を実際に試せる
- 欠点: パスワードを公開したアカウントで、誰でも文や画像を置ける。荒らされると次に作り直すまで残り、その間に来た人が見る。
  作り直す処理を定期的に動かすと、そのたびに Aurora を起こす

#### C. 管理画面の画面例（スクリーンショットと GIF）だけで済ませる

- 利点: 作るものも、増える危険もない
- 欠点: 見に来た人は管理画面を操作できない。README とトップの画面例はすでにあり、それだけでは管理画面まで見に来なかった

### 読ませる API の決め方

#### A. 読ませる GET に印（`@VisibleToViewers`）を付ける

- 利点: 印のない API は見学者に 403 になる。管理の API を足して書き忘れても、見学者に見えない
- 欠点: 読ませる GET のすべてに印が要る

#### B. 管理の GET はすべて読ませ、見せないものだけを除く

- 利点: 印を付ける手間がない
- 欠点: 人のメールアドレスを返す API を足したとき、除き忘れるとそのまま公開される

### 変えようとしたときの画面

#### A. 管理画面の上に見学中であることを出し、変更はバックエンドが断る

保存や削除のボタンは押せる。押すとバックエンドが 403 を返し、画面はその理由（見学では変更できない）をエラーとして出す。

- 利点: 管理画面の部品に手を入れずに済む。画面を足しても、同じ配慮は要らない
- 欠点: 入力してから保存を押すまで、変えられないことに気づかない人がいる

#### B. 見学中は、変更のボタンを押せなくする

- 利点: 変えられないことが、押す前に分かる
- 欠点: 管理画面の部品（17 ほど）すべてに手が入る。画面を足すたびに同じ配慮が要り、漏れると A と同じ表示になる

## 決定

**見せ方は A（見学者のロール）、読ませる API の決め方は A（印を付ける）、画面は A（見学中であることを出し、バックエンドが断る）を採用する。**

| 項目 | 決めたこと |
| --- | --- |
| ロール | `core.tenant_members.role` に `viewer` を足す。招待では渡せない（招待のロールは `admin` と `member` のまま）。見学者にするのは運用者で、シードで入れる |
| デモのアカウント | デモのテナントで `viewer` として所属する（`db/demo/R__demo_base.sql`）。すでに `member` で入っている DB は、シードが `viewer` に替える |
| 管理の API | 見学者が使えるのは、`@VisibleToViewers` を付けた GET だけ。それ以外の管理の API（変更と、印のない GET）は 403 |
| 出題の API | 一般ユーザーと同じ |
| 見せない API | 招待の一覧。招待した人のメールアドレスが載る。prod のデモで運用者が誰かを招待すると、そのアドレスを誰でも見られることになる |
| 正解 | 見せる。管理のクイズの API は正解を含む。デモの履歴とランキングは見た人どうしで共有していて、正解が見えても守るものがない |
| 403 の理由 | 変更と、見せない API を読もうとしたときで、理由（`title` と `detail`）を分ける。どちらも、自分のアカウントを作れば試せることを伝える |
| 画面 | ヘッダの「管理」を出す。管理画面の上に「見学中です」と、アカウントを作って試す入口を出す。招待の画面は、一覧を取りに行かずに理由を出す |
| 決め忘れの検出 | `ViewerAccessApiTest` が管理の GET を Spring から列挙し、印のないものが、見せない理由を書いた一覧と一致しなければ落ちる |

## 結果

### 良い影響

- 見に来た人が、ボタン 1 つで管理画面まで見られる
- 認可の判定は 1 か所（`TenantAccessInterceptor`）のまま。ロールが 1 つ増えるだけ
- 管理の API を足したとき、印を付けなければ見学者に見えない。見せるかどうかを決めないまま足すと、テストが落ちる

### 悪い影響・受け入れるリスク

- **デモのクイズの正解を、見学者が見られる。** 共有のランキングで、正解を見てから解く人が出る
- **下書き（AI の下書きを含む）と削除済みの項目も見える。** 運用者が確かめる前の AI の下書きを、見に来た人が読む
- 保存を押すまで、変えられないことに気づかない人がいる。管理画面の上の案内で補う
- 見学者が管理画面を開くと、出題の画面と同じく Aurora を起こす。増える費用は、見に来た人が出題の画面を開いたときと変わらない

## 検証事項

- 見に来た人が、管理画面まで見ているか。見ていないなら、トップや出題の画面から管理画面への案内を足す
- 見学者に見せたくない情報を返す管理の API が増えていないか。増えたら、印を付けずに見せない一覧に理由を書く
