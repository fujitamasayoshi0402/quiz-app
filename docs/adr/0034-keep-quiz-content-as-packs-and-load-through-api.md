# ADR-0034: クイズの中身は図ごと「パック」にまとめ、アプリの API で流し込む。デモのパックはリポジトリに、自分の題材は非公開の場所に置く

- ステータス: Accepted
- 決定日: 2026-10-16

## 背景と課題

デモのテナントのクイズは、シード（`db/seed/R__demo_data.sql`）に文章だけで入っている。図は dev の画面で足したものしかなく、ローカルにも prod にも再現できない。
これから、デモを図解の多い一般教養のクイズに替え、自分で作ったテナント（dev の `my-quiz`）にも技術のクイズを分野ごとに入れていく（DEV-184）。

図がシードに入らないのは、置き場所が DB だけではないため。図は S3 に原本と SVG を置き、`quiz.figures` に行を作る（[ADR-0017](0017-deliver-figures-with-cloudfront-signed-urls.md)）。
draw.io の SVG は、置くときに明るい色で描かれるよう書き換える。マイグレーション（Flyway）は DB にしか触れない。

一括取り込み（`POST /admin/quizzes/import`）は、文章だけでなく図を指す解説も受け付ける。指している図がテナントにあることを、1 問ずつ確かめる。
カテゴリと難易度は名前で引くので、先に作っておく必要がある。

決めること。

- **デモのクイズの置き場所と、流し込み方。** 図ごと、ローカル・dev・prod に同じものを入れたい
- **流し直したときの扱い。** 同じものを重ねて入れない。パックで直したものを反映する
- **シードに残すもの。** E2E（`demo.spec.ts`）、画面の撮影（`tests/e2e/capture/`）、`DemoSeedTest` が、いまのシードのカテゴリに頼っている
- **自分の題材の置き場所。** 公開のリポジトリに置くか
- **`my-quiz` の量の上限。** 利用者が作ったテナントには、クイズ 100・図 50 の上限が掛かる（[ADR-0028](0028-let-signed-in-users-create-their-own-tenant.md)）
- **書き方の決まり。** 中身の質をそろえる

## 判断基準

- 図を含めて、どの環境にも同じものを入れられること。手で画面から足したものだけが dev に残る、という状態をなくす
- アプリと同じ検証（選択肢の数、正解、図の参照、テナントの境界）を通ること。中身のために、検証の抜け道を作らない
- 新しく持つ権限と仕組みを増やしすぎないこと。CI やマイグレーションに、テナントの管理者の権限や S3 を持たせない
- 何度流しても同じ状態になること
- 見る人に向けた中身（デモ）と、公開しない中身（自分のテナント）を、置き場所で分けられること

## 検討した選択肢

### 置き場所と流し込み方

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **A. 図ごと「パック」（クイズの JSON、`.drawio`、書き出した SVG）にまとめ、管理者のトークンで API を呼んで流し込む（採用）** | アプリの検証をそのまま通る。図の作成（`POST /admin/figures`）と一括取り込み（`POST /admin/quizzes/import`）は、いまある API。どの環境にも、同じスクリプトで流せる。自分の題材にも同じ形が使える | 流すのは人の操作。パックを直したあと、dev に流し忘れることがある。管理者のトークンが要る |
| B. シードに入れ、図を S3 に置く仕組みをマイグレーションに足す | デプロイのたびに自動で流れる | マイグレーションのタスクに S3 の書き込みと、SVG の書き換えを持たせる。マイグレーションは DB の形を変えるもので、中身の配り方まで負わせると、失敗したときにデプロイ全体が止まる。シードはドメインを通らない |
| C. quiz-service に「中身を入れる」単発のタスクを作り、デプロイで流す（マイグレーションと同じ形） | 自動で流れ、トークンも要らない。ドメインのユースケースを通せる | 単発のタスクの定義、デプロイの手順、デプロイのロールの権限（Terraform）が増える。中身のための仕組みとしては大きい。自分の題材（公開のリポジトリに置かない）には使えず、結局 A も要る |

A は、いまある API を順に呼ぶだけで、作るのはスクリプト 1 つ（マネージドに寄せた形）。C は、中身の配り方まで自前の仕組みで持つ形で、流し忘れはなくなるが、作るものと権限が増える。
**流し忘れは、パックを変えたときにだけ起きる。** パックの変更は月に数回の想定で、手で流す手間より、C の仕組みを持ち続ける手間のほうが大きい。

### 流し直したときの扱い

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **A. 問題文で同じものかを決める。パックにあってテナントにないものだけを入れる（採用）** | API に手を入れずに済む。画面で直したものを、流し直しで上書きしない | 問題文を直すと、別の問題として入る。前のものは手で消す（スクリプトに、パックにないものを消す指定を付ける） |
| B. パックに固定の識別子を書き、クイズにも持たせる | 問題文を直しても、同じ問題として更新できる | クイズに外からの識別子の列を足し、取り込みの API も変える。中身のために、ドメインの形を変える |

### シードに残すもの

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **A. シードは、デモのテナント・利用者・所属・AI の受け箱のカテゴリだけにする。クイズはパックから入れ、E2E もテストの前にパックを流す（採用）** | ローカルも dev も同じ中身になる。E2E で流し込みのスクリプトも確かめられる | E2E の準備に、図の作成と取り込みの時間（数秒〜十数秒）が足される。E2E が、パックの中身（カテゴリの名前）に頼る |
| B. シードに文章だけの最小の見本を残し、パックはその上に足す | E2E とシードのテストは、いまのまま | dev のデモに、見本とパックの両方が並ぶ。見本だけのローカルと、図の入った dev で、見え方が分かれる |

## 決定

**置き場所と流し込み方は A（パックと API）、流し直しは A（問題文で決める）、シードは A（構造だけ）を採用する。**

| 項目 | 決めたこと |
| --- | --- |
| パックの形 | カテゴリと難易度、クイズ（いまの一括取り込みの JSON と同じ項目）、図（`.drawio` と、書き出した SVG）。解説の中では、図をファイルの名前で指す（`figure:world-map`）。流すときに、作った図の ID に差し替える |
| デモのパック | リポジトリの `content/demo/` に置く。見る人に向けた中身で、公開してよいもの |
| 流し込み | スクリプトが、管理者のアクセストークンで API を呼ぶ。カテゴリと難易度がなければ作り、図を作り、解説の参照を差し替えて、クイズを取り込む。形は DEV-186 で決める |
| 同じものかの判断 | クイズは、カテゴリと問題文。図は、原本（`.drawio`）が同じものを使い回す。図は変えられない（[ADR-0020](0020-reference-figures-from-explanations-and-add-images-and-pdfs.md)）ので、描き直したら新しい図になり、前の図は使われなくなる（図の一覧から消せる。DEV-166） |
| パックから消したもの | 指定したときだけ、パックのカテゴリにあってパックにないクイズを消す（論理削除。ゴミ箱に入る）。指定しなければ消さない |
| シード | デモのテナント、利用者、所属、AI の受け箱のカテゴリ（「AWS の最新情報」）だけ。デモのクイズは入れない（DEV-188 で移す）。`DemoSeedTest` は、構造と、何度流しても増えないことを見る |
| E2E と画面の撮影 | テストの前に、ローカルのデモのテナントへパックを流す。E2E の管理者を、デモのテナントの管理者にもする（`fixtures.sql`）。CI でも流し込みのスクリプトが動く |
| dev への反映 | パックを変えた PR をマージしたら、手で流す。**デプロイには組み込まない。** CI にデモのテナントの管理者のトークンを持たせないため |
| トークン | 流す人の Cognito の利用者で取る（スモークテストと同じ `InitiateAuth`）。パスワードは画面に出さずに受け、トークンはファイルに残さない |
| prod | デモを prod に出すと決めたら、同じパックを流す（[ADR-0024](0024-run-prod-in-same-account-and-launch-at-release.md)） |
| 自分の題材 | **公開のリポジトリには置かない。** 非公開のリポジトリに、同じパックの形で置き、同じスクリプトで流す。クローンは iCloud で同期する場所の外に置く |
| `my-quiz` の上限 | 運用者が、このテナントの上限を外す（`core.tenants` の `quiz_limit` と `figure_limit` を空にする）。Data API で 1 行だけ書き換え、手順は Runbook に残す。ほかの、利用者が作ったテナントの上限は変えない |
| 書き方 | [クイズの書き方](../content-guide.md)に従う。デモも自分の題材も同じ決まりにする |

## 結果

### 良い影響

- 図の入ったデモを、ローカル・dev・prod に同じ形で再現できる。画面から足した図が dev にだけ残る状態がなくなる
- 中身は、画面から入れたものと同じ検証を通る。中身のための抜け道（シードはドメインを通らない）が、クイズについてはなくなる
- E2E が、流し込みのスクリプトも確かめる
- 見る人に向けた中身（デモ）と、公開しない中身（自分のテナント）を、同じ形で、別の場所に置ける

### 悪い影響・受け入れるリスク

- **dev への反映は手で行う。** パックを変えたのに流し忘れると、リポジトリと dev のデモがずれる
- 問題文を直すと、別の問題として入る。前のものは、消す指定を付けて流すか、画面で消す
- E2E の準備が数秒〜十数秒延びる。E2E が、デモのパックのカテゴリの名前に頼る
- Data API での書き込みは、開発ガイドラインの「確認のための読み取りにとどめる」の例外になる。対象は RLS のない `core.tenants` の 1 行に限る
- 自分の題材は公開のリポジトリにないため、見に来た人からは、どれだけ入れたかが見えない（`my-quiz` は非公開のテナントでもある）

### 緩和策

- パックを変える PR の説明に、マージのあと dev に流すことを書く。流したかは、デモの画面と、スクリプトが出す作ったものの一覧で確かめる
- スクリプトは、流す前に何を作り何を消すかを出す（実際には流さない指定）
- Data API で書き換える手順は Runbook に置き、書き換える前と後に、同じ行を読んで確かめる

## 検証事項

- 図の作成と取り込みを続けて呼んだとき、利用者ごとの流量の上限（重い操作は 1 分に 20 件。開発ガイドライン「ECS」）に当たらないか。当たるなら、スクリプトが待ってやり直す
- draw.io のデスクトップの CLI で書き出した SVG が、画面の「図を描く」で書き出したものと同じように表示されるか（明るい色への書き換えを含む）
