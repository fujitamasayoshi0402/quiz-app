# ADR-0023: 回答・採点は quiz-service の中のモジュールのまま分けない。分けるときの通信の使い分けを先に決めておく

- ステータス: Accepted
- 決定日: 2026-10-01

## 背景と課題

[ADR-0004](0004-split-services-incrementally.md) は、回答・採点（answer）を quiz-service の中のモジュールとして作り、
「境界が安定したと判断できた段階で物理分割する。分割しない判断もありうる」とした。
Phase 5 で通知を別のサービス（notification-service）にし、クイズの変更をイベントとして外へ出す仕組みもできた（[ADR-0022](0022-publish-quiz-events-through-outbox-and-notify-slack-per-tenant.md)）。
ここで、answer を分けるかを決める。

いまの境界は次のとおり。

- **DB のスキーマは分かれている。** answer の SQL は `quiz` のスキーマに触れず、quiz の SQL も `answer` のスキーマに触れない
- **呼び合いは、呼ぶ側が持つインターフェース 2 つだけ。** 実装は呼ばれる側にある（ADR-0004 の検証事項）

| 向き | インターフェース | 使うところ |
| --- | --- | --- |
| answer → quiz | `QuizCatalog` | 出題（`select`）、再開（`findDeliverable`）、採点の正解（`findAnswerKeys`）、履歴とランキングの集計（`findPlayableCategories`、`findCategoryIds`、`findPlayableQuizIds`） |
| quiz → answer | `AnsweredQuizzes` | 未回答を優先する出題（`filterAnswered`） |

- **型は共有している。** answer は quiz の domain の型（`DeliveredQuiz`、`DeliveryCriteria`、`AnswerKey` など）を直接使う
- **挑戦の開始は往復する。** answer が quiz に出題を頼み、quiz は選ぶために answer に回答済みかを聞く
- すべての呼び出しが、1 つのトランザクションと 1 つのテナントの設定（`app.tenant_id`）の中で動く

決めること。

- 分けて得るものと、失うもの
- 同期の呼び出しと、非同期のイベントの使い分け。いま決めるのは、分けるときにどちらにするか
- 分けないなら、どうなったら分けるか

## 判断基準

- 分けて得るものが、失うものを上回ること
- **予算（月 30 ドル）に収まること。** dev の定常の月額は約 20 ドルの見込み（ECS のタスク 13.5 ドル、パブリック IPv4 2.7 ドル、ほか数ドル）
- **正解を quiz-service の外に出さないこと**（ADR-0022。バス、アーカイブ、ログに載せない）
- テナントの境界を確かめる場所を増やさないこと（[ADR-0006](0006-row-level-multi-tenancy.md)。いまは `TenantBoundaryApiTest` の 1 か所）
- 「マイクロサービスにする」こと自体を目的にしないこと（ADR-0004）

## 検討した選択肢

### A: 別の ECS サービスに分ける

answer を別のコンテナにし、API Gateway で `/api/t/{slug}/play/attempts` などをそちらへ送る。2 つのインターフェースの実装を HTTP の呼び出しに替える。

得るもの。

- answer だけをデプロイし、answer だけのタスクを増やせる
- 片方の障害が、もう片方に及びにくい

失うもの。

- **費用が予算を超える。** 2 つ目のサービスで、タスク（0.5 vCPU / 1 GB、深夜は止める）に月 13.5 ドル、パブリック IPv4 に 2.7 ドル。合わせて月 36 ドルほどになる。
  0.25 vCPU に絞っても、Spring Boot の起動が遅くなり、デプロイのたびに待たされる（ECS の設定で 0.5 vCPU にした理由と同じ）
- **挑戦の開始で、ネットワークを 2 往復する**（answer → quiz → answer）。出題の選び方を、answer が候補を絞ってから quiz に渡す形に変えれば 1 往復にできるが、出題の仕組みを作り直すことになる
- **1 つのトランザクションでなくなる。** 出題と挑戦の保存の間に、クイズが非公開になりうる。これは今も回答のときに確かめている（`QuizNoLongerAvailableException`）ので、壊れはしない
- **認証と所属の判定が 2 か所になる。** answer-service も JWT を検証し、所属（`core.tenant_members`）を引く。`core` のスキーマを 2 つのサービスで読むか、quiz-service に問い合わせることになる。テナントの境界のテストも 2 つ要る
- 共有する型を、契約のモジュール（`libs/quiz-events` と同じ形）に移す。API Gateway の経路、CI のジョブ、デプロイ、ローカルの docker compose も 1 つずつ増える

### B: Lambda に分ける

notification-service と同じく Lambda にする。常駐の費用はかからない。

- **採点は、利用者を待たせる同期の操作。** JVM の起動（数秒）が、回答のたびの応答に乗りうる。非同期で急がない通知とは事情が違う
- Lambda から Aurora へ届くには VPC に入れる。そのうえで JWT の検証に Cognito の公開鍵（JWKS）を取りに外へ出るには、NAT Gateway か VPC Endpoint が要る（[ADR-0013](0013-run-ecs-tasks-in-public-subnets.md) で避けた費用）
- A の「失うもの」のうち、費用以外はすべて残る

### C: 分けない

answer を quiz-service の中のモジュールのまま保つ。境界（スキーマとインターフェース）は今のまま守る。

- 費用も往復も増えない。1 つのトランザクションのまま
- 独立したデプロイとスケールは得られない。answer の負荷が大きくなったら、quiz-service ごとタスクを増やす。どちらもステートレスなので、それで足りる
- 境界は規律で守ることになる。破られても、いまは気づく仕組みがない

### D: Phase 6 の負荷試験まで保留する

k6 で、回答・採点に別のスケールが要るかを測ってから決める。

- 計測で分かるのは、スケールの特性だけ。費用、往復、境界の確かめの重複は、計測を待たずに分かる
- 負荷の特性が違っても、quiz-service ごと増やせば足りる。それより重い理由が要る
- 保留している間、ROADMAP の項目と ADR-0004 の検証事項が開いたままになる

## 決定

**C を採用する。answer は quiz-service の中のモジュールのまま、分けない。**

分けて得られる独立したデプロイとスケールは、いまの規模では使い道がない。
一方で失うもの（予算を超える費用、2 往復、認証とテナントの境界の確かめの重複）は、計測を待たずに確かだと分かる。
D は、測っても判断が変わる見込みが小さいため採らない。計測は検証事項に残す。

### モジュール間の呼び出しは、同期のまま

モジュール間の呼び出しは、いまのインターフェース（同じプロセスの中の同期の呼び出し）のままにする。
ADR-0004 は「モジュール間の呼び出しはイベント経由に統一する」としていたが、これは採らない。
**イベントは、サービスの外へ出すもの**に限る（ADR-0022）。

### 分けるときの使い分け

いつか分けるときのために、どの呼び出しを何にするかを先に決めておく。基準は 1 つ。

- **利用者を待たせる操作で、その瞬間の正しさが要るもの → 同期の呼び出し**
- **集計の材料で、少し遅れてよいもの → イベントで写しを持つ**

| 呼び出し | 分けたとき | 理由 |
| --- | --- | --- |
| 出題（`select`、`findDeliverable`） | 同期 | 利用者が待っている。いま公開されているものを出す |
| 採点の正解（`findAnswerKeys`） | 同期 | **正解をイベントに載せない**（ADR-0022）。answer に正解の写しを持たせられない。回答した瞬間の正解で採点する |
| 回答済みか（`filterAnswered`） | 同期 | 出題の選び方の一部。往復をなくすなら、出題の選び方を answer 側へ寄せる |
| 履歴とランキングの集計（`findPlayableCategories`、`findCategoryIds`、`findPlayableQuizIds`） | イベントで写しを持つ | クイズの状態とカテゴリは、`QuizCreated` などに載っている。少し遅れても困らない。ただし削除・復活・カテゴリの変更のイベントを足す必要がある（ADR-0022 では送っていない） |

### 分けたくなる条件

次のどれかに当たったら、この ADR を見直す。

- 負荷試験（Phase 6）で、回答・採点だけがタスクを増やす理由になる。CPU やメモリの使い方が、quiz と大きく違う
- 回答・採点だけを、quiz と違う頻度でデプロイしたくなる
- 回答・採点を、別の人が持つようになる
- 予算の前提が変わる

## 結果

### 良い影響

- 費用が増えない。予算（月 30 ドル）に収まる
- 出題・回答・採点は、1 つのトランザクションとテナントの設定の中で動き続ける
- テナントの境界を確かめる場所は 1 つのまま
- 分けるときの通信の使い分けが決まっている。そのときに迷わない

### 悪い影響・受け入れるリスク

- サービスは quiz-service と notification-service の 2 つにとどまる。answer の物理分割は示さない
- **境界は規律で守ることになる。** answer の SQL が `quiz` のスキーマを読む、answer が quiz の型を無制限に使う、といった崩れに、いまは気づく仕組みがない
- ADR-0004 の「モジュール間の呼び出しはイベント経由に統一する」を採らない。モジュール間は同期で、イベントはサービスの外へ出すものに限る

### 緩和策

- **境界を構造のテストで守る**（DEV-105）。`TenantIsolationTest` と同じく、崩れたら落ちるようにする
  - answer の SQL が `quiz` のスキーマに、quiz の SQL が `answer` のスキーマに触れないこと
  - answer が使ってよい quiz の型を、2 つのインターフェースに出るものに限ること（いまは API の説明に使う定数 `Quiz.EXPLANATION_FORMAT` も読んでいる。テストを足すときに整理する）
- 呼び合いは、呼ぶ側が持つインターフェースに限る（ADR-0004 の検証事項のまま）。分けるときは、実装を HTTP の呼び出しに替えるだけで済む
