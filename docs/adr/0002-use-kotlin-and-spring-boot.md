# ADR-0002: バックエンドに Kotlin + Spring Boot を採用する

- ステータス: Accepted
- 決定日: 2026-09-21

## 背景と課題

クイズの CRUD、出題、採点を担うバックエンドの言語とフレームワークを決める必要がある。
本アプリは将来的に複数サービスへ分割する方針（[ADR-0004](0004-split-services-incrementally.md)）であり、
データストアは Aurora PostgreSQL、実行基盤は ECS Fargate を想定している。

## 判断基準

- 型安全性。クイズの正誤判定や権限制御など、誤りが機能不全に直結する処理を静的に守れること
- エコシステムの成熟度。認証、DB アクセス、マイグレーション、テストが標準的な方法で揃うこと
- コンテナ環境での実行に無理がないこと
- 学習の投資対効果。実務で使われている構成であること

## 検討した選択肢

### 選択肢 A: Kotlin + Spring Boot 3 (Java 21)

Spring のエコシステムをそのまま利用でき、null 安全・データクラス・拡張関数により Java より記述量が少ない。
Java のライブラリをそのまま呼べるため、資産が無駄にならない。

### 選択肢 B: Java 21 + Spring Boot 3

最も情報量が多く、採用事例も多い。一方で同じ処理に対する記述量が Kotlin より多く、
null 安全は言語仕様として保証されない。

### 選択肢 C: Kotlin + Ktor

軽量で起動が速く、コルーチン前提の設計が素直。ただし認証・バリデーション・トランザクションなどを
個別に組み合わせる必要があり、Spring ほど「標準的な作り方」が確立していない。

### 選択肢 D: TypeScript + NestJS

フロントエンドと言語を統一でき、型定義を共有できる。ただしバックエンド設計の学習という観点では、
JVM 系の設計様式（DI、トランザクション境界、レイヤー分離）に触れる機会を失う。

## 決定

**選択肢 A（Kotlin + Spring Boot 3 / Java 21）を採用する。**

Spring Boot の「標準的な作り方が確立している」という性質を重視した。本プロジェクトでは
認証・非同期連携・DB アクセスなど周辺要素が多く、フレームワーク側の設計に悩む時間を減らしたい。
その上で Kotlin を選ぶことで、Java に対する記述量と null 安全の優位を得る。

Java ではなく Kotlin を選んだ理由は、Java のライブラリをそのまま利用できるため実質的な欠点がなく、
型システムによって防げる不具合の範囲が広いこと。

## 結果

### 良い影響

- Spring Data JPA / Flyway / Spring Security が標準的な方法で組み合わせられる
- Testcontainers による統合テストが容易で、実際の PostgreSQL に対してテストできる
- null 安全により、クイズの選択肢や正解 ID まわりの欠損を型で検出できる

### 悪い影響・受け入れるリスク

- JVM の起動時間とメモリ消費が、Go や Node.js に比べて大きい
- ECS Fargate のタスクサイズが大きくなり、コストに影響する
- Kotlin + Spring 固有の情報は、Java + Spring に比べると少ない

### 緩和策

- ECS はタスクを常駐させる構成のため、起動時間はリクエストのレイテンシに影響しない
- 起動時間が問題になる場面（Lambda での実装が必要になった場合）は、その部分のみ別の選択肢を検討する。
  通知処理は Lambda で実装するが、ここは Kotlin に限定しない
- メモリは最小構成（0.5 vCPU / 1GB）から始め、実測してから調整する

## 検証事項

- Aurora が min 0 ACU から復帰する際、コネクションプールが正しくリトライするか
