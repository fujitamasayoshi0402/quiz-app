# ADR-0009: データアクセスに Spring Data JDBC を採用する

- ステータス: Accepted
- 決定日: 2026-09-22

## 背景と課題

最初の API を実装するにあたり、データアクセスの方式を決める必要がある。

本プロジェクトの DB 設計は、**PostgreSQL の機能に強く依存している**。

- 行レベルセキュリティによるテナント分離（[ADR-0006](0006-row-level-multi-tenancy.md)）
- 複合外部キーによるカテゴリと難易度の整合性保証
- 部分ユニークインデックスによる論理削除との両立（[ADR-0007](0007-soft-delete-master-data.md)）
- セッション変数と連動した絞り込み

これらは「ORM が隠蔽してくれる範囲」の外側にある。
方式を誤ると、フレームワークの想定と DB の挙動が噛み合わず、回避策を積み重ねることになる。

またデータアクセスの選択は、すべてのリポジトリ実装に波及する。
**後から変えるには全リポジトリとテストの書き換えが必要**で、実装が進むほど高くつく。

## 判断基準

- DB の機能と衝突しないこと
- **発行される SQL が予測できること**。RLS が絡む不具合の切り分けに直結する
- 集約の境界を表現できること（[ADR-0004](0004-split-services-incrementally.md)）
- 個人で保守できる複雑さに収まること

## 検討した選択肢

### 選択肢 A: Spring Data JPA (Hibernate)

実務で最も使われており、情報量が圧倒的に多い。学習の価値も高い。

一方で、本プロジェクトの設計とは噛み合わない点が多い。

- **1 次キャッシュが RLS と衝突する。** 同一トランザクション内で取得済みのエンティティはキャッシュから返るため、
  DB のポリシーを通らない経路ができる。テナント分離の検証がしにくい
- **論理削除の実装が Hibernate 固有の機能に寄る。** `@SQLRestriction` や `@SQLDelete` を使うことになり、
  フレームワークへの依存が深まる
- **発行される SQL が読みにくい。** 遅延ロードと N+1 が絡むと、どのクエリがいつ飛ぶのか追いにくい。
  RLS で「行が返らない」不具合が起きたとき、原因の切り分けが難しくなる

### 選択肢 B: Spring Data JDBC

集約単位で永続化する。集約ルートを保存すると、配下の子エンティティもまとめて書き込まれる。

- クイズと選択肢のように「一体で扱うもの」を集約として表現できる。ADR-0004 の境界の考え方と一致する
- **遅延ロードも 1 次キャッシュもない。** 呼んだときに呼んだ分だけ SQL が飛ぶため、挙動が予測できる
- JPA より仕組みが単純で、フレームワークの内部を追いやすい

代償として、論理削除やテナント絞り込みを自動で差し込む仕組みがない。自分で共通化する必要がある。
ただし**この設計では、それらを暗黙に効かせないほうがよい**。
削除済みを含めて取得したい場面（復活機能）が実際にあり、自動適用だと抜け道を作ることになる。

### 選択肢 C: JdbcClient で手書きする

SQL を完全に制御できる。DB 機能をそのまま使える。
ただし、集約の読み書きとマッピングをすべて自分で書くことになり、量が多い。
Spring Data JDBC でも `@Query` で手書き SQL は書けるため、最初から全部を手書きにする理由は薄い。

### 選択肢 D: jOOQ

型安全に SQL を組み立てられる。スキーマからのコード生成も魅力的。
しかしコード生成をビルドに組み込む手間があり、Flyway との実行順序も設計が要る。
Phase 1 の規模に対して仕掛けが大きい。

## 決定

**選択肢 B（Spring Data JDBC）を採用する。**

- 集約ルート単位でリポジトリを定義する
- クイズと選択肢は 1 つの集約として扱う
- テナント絞り込みと論理削除は、**明示的に書く**。暗黙に差し込まない
- 複雑な検索は `@Query` で SQL を書く

「フレームワークが賢くやってくれる」ことよりも、**何が起きるか分かること**を優先する。
テナント境界を越えた参照が情報漏洩になる以上、挙動が読めることに価値がある。

## 結果

### 良い影響

- 発行される SQL が予測でき、RLS が絡む不具合を切り分けやすい
- 集約の境界がコードに現れる
- フレームワーク固有の回避策を積み上げずに済む

### 悪い影響・受け入れるリスク

- **テナント条件と削除条件を書き忘れうる。** JPA なら `@SQLRestriction` で一律に効かせられるが、その道を選ばない
- JPA に比べて情報が少ない。とくに Spring Boot 4 との組み合わせは事例が乏しい
- 関連の解決を自分で書く場面が出る。素朴に書くと N+1 になる

### 緩和策

- **RLS を最後の砦にする。** アプリケーション側でテナント条件を書き忘れても、DB が行を返さない。
  この二重化があるため、明示的に書く方式を選べる
- 削除条件の書き忘れは、リポジトリの基底インターフェースと命名規約で防ぐ。
  削除済みを含める操作は名前で区別する（`findAll` と `findAllIncludingDeleted` など）
- テナント越えアクセスの検証を全エンドポイントで行う（DEV-27）

## 検証事項

- 集約（クイズ + 選択肢 4 件）の更新で発行される SQL の本数。全削除・全挿入になる場合の是非
- 一覧取得でカテゴリと難易度を結合して返すときの書き方。`@Query` で足りるか
- Spring Data JDBC の監査機能（`@CreatedDate` など）と、DB トリガーによる `updated_at` 更新の重複
