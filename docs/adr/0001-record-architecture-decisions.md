# ADR-0001: アーキテクチャ決定記録を採用する

- ステータス: Accepted
- 決定日: 2026-09-21

## 背景と課題

本プロジェクトでは、コスト・学習効果・完成までの速度といった複数の軸がぶつかる判断が繰り返し発生する。
例えば「Aurora を min 0 ACU で一時停止させる」という選択は、コストでは有利だが復帰に時間がかかるという代償を伴う。

こうした判断はコードには現れない。コードから読み取れるのは「何をしたか」だけで、
「なぜそれを選び、何を捨てたか」は残らない。結果として次の 2 つが起きる。

- 時間が経つと、自分自身が決定理由を再構成できなくなり、同じ検討を繰り返す
- 第三者がリポジトリを読んでも、設計の意図が伝わらず、単なる実装の集合に見える

## 判断基準

- 決定理由が、実装から独立した形で残ること
- 記述コストが低く、開発の速度を落とさないこと
- 形式が標準的で、他者が読み方を学ばなくて済むこと

## 検討した選択肢

### 選択肢 A: ADR を `docs/adr/` に Markdown で残す

軽量な標準形式。リポジトリ内にあるためコードと一緒にレビューでき、変更履歴も Git に残る。

### 選択肢 B: Jira のチケットに決定理由を書く

タスクと決定が同じ場所にまとまる。一方で、チケットは完了すると参照されなくなり、
リポジトリ単体を見る第三者には届かない。

### 選択肢 C: 記録しない

記述コストはゼロ。ただし前述の課題がそのまま残る。

## 決定

**選択肢 A を採用する。** [MADR](https://adr.github.io/madr/) 形式で `docs/adr/` に記録する。

記録対象は「後から変更するのが高くつく決定」に限定する。具体的には、技術スタックの選定、
アーキテクチャの分割方針、認証方式、データストアの選定、インフラ構成の方針など。
ライブラリの細かな選択やコーディングスタイルは対象外とし、開発ガイドラインに記載する。

## 結果

### 良い影響

- 決定とその理由がコードと同じリポジトリに残り、PR でレビューできる
- 検討して見送った選択肢が残るため、後から再検討する際の出発点になる
- ADR に書いた比較検討は、そのままクイズの解説コンテンツとして再利用できる

### 悪い影響・受け入れるリスク

- 決定のたびに文書を書くコストが発生する
- 記録対象の線引きが曖昧だと、書くべきものが書かれなかったり、逆に些末な記録が増える

### 緩和策

- 記録対象を「後から変更するのが高くつく決定」に限定する
- テンプレート（`0000-template.md`）を用意し、書き始めのコストを下げる
- 一度 Accepted にした ADR は書き換えず、決定を変える場合は新しい ADR で上書きする。
  これにより「いつ考えが変わったか」も記録として残る
