# ADR-0010: OpenAPI 定義はコードから生成し、スナップショットを固定する

- ステータス: Accepted
- 決定日: 2026-09-23

## 背景と課題

フロントエンドの型を API 定義から生成する方針を立てている（[開発ガイドライン](../development-guidelines.md)）。
そのためには「API 定義とは何か」を先に決める必要がある。

**定義と実装が食い違ったとき、壊れるのはフロントエンドである。**
サーバーは動き続け、型だけが実態からずれる。コンパイルは通るのに実行時に落ちる、という形で現れる。

Phase 1 の API は短期間に 2 度作り直している（DEV-21 の出題 API は DEV-22 で挑戦ベースに、
管理 API は DEV-24 でパスが変わった）。**定義の維持コストが低いこと**が現実的な要件になる。

## 判断基準

- 定義と実装がずれないこと。ずれたら気づけること
- 変更が差分として現れ、レビューできること
- 1 人で維持できる手間に収まること

## 検討した選択肢

### 選択肢 A: スキーマファースト（定義を手で書く）

`docs/api/openapi.yaml` を先に書き、実装をそれに合わせる。

契約が先に決まるため、フロントとバックを並行して進められる。定義そのものがレビュー対象になる。

一方で、**定義と実装が一致している保証はどこにもない。** 一致させるには契約テストを別に書くことになり、
検証の仕組みをもう 1 つ維持することになる。
API がまだ動いている段階では、手で書いた定義が実装に追従できず、古い定義が残りやすい。

### 選択肢 B: コードファースト（実装から生成する）

springdoc がコントローラを走査して定義を出力する。

**定義が実装からずれない。** 定義は実装の写像なので、一致の検証そのものが不要になる。
維持の手間はほぼゼロで、注釈を足せば説明も持たせられる。

ただし生成物が実行時にしか得られないため、そのままでは**変更が差分に現れない。**
API が変わってもプルリクエストには型の変更しか出ず、レビューで気づけない。

### 選択肢 C: コードファースト + スナップショットの固定

B に加えて、生成した定義を `docs/api/openapi.yaml` に固定してリポジトリに置く。
テストが毎回生成して固定物と比較し、**差があれば落とす**。

定義の変更がプルリクエストの差分に現れる。実装とのずれは原理的に起きない。
代償は、API を変えたときに定義を再生成してコミットする一手間。

## 決定

**選択肢 C を採用する。**

- 定義は springdoc がコードから生成する
- 生成物を `docs/api/openapi.yaml` に固定し、リポジトリで持つ
- `OpenApiSnapshotTest` が生成結果と固定物を比較し、差があれば失敗する
- フロントの型は**固定物から**生成する（`openapi-typescript`）

「OpenAPI を単一の真実とする」という当初の言い方は改める。
**真実はコードであり、定義はその写像である。** 写像が古くならないことをテストで保証する。

契約を先に決める価値は認めるが、それは**フロントとバックを別の人が並行して作る**状況で効く。
1 人で、かつバックエンドを先に作っている現状では、維持コストに見合わない。

## 結果

### 良い影響

- 定義と実装がずれない。ずれの検出という問題自体が消える
- API の変更がプルリクエストの差分に現れ、レビューできる
- フロントの型が定義に追従する。追従していなければテストが落ちる

### 悪い影響・受け入れるリスク

- **API を変えたら定義を再生成する手間がかかる。** 忘れるとテストが落ちる（落ちること自体は意図どおり）
- 定義の質が springdoc の推論に依存する。注釈がないと `operationId` が `create_1` のような名前になり、
  生成したクライアントが読みにくくなる
- **Kotlin の型が Java の規約で読まれる。** `isCorrect` は getter 規約で `correct` と解釈されるが、
  Jackson は Kotlin のプロパティ名で出力するため、放置すると定義と実際の JSON がずれる
- フロントとバックを並行して作れない。契約が実装より先に決まらない

### 緩和策

- `operationId` と `summary`、タグを明示する。生成したクライアントの読みやすさは注釈で作る
- **定義に現れる名前が実際の JSON と一致することをテストする。** `isCorrect` の件は実際に踏んだ
- **参照先のないスキーマが無いことをテストする。** `OpenAPI` の Bean に載せたスキーマは
  springdoc が走査結果で置き換えるため消える。これも実際に踏んだ
- 出題の型に正解と解説が現れないことを定義に対しても検証する。
  型で防いでいる不変条件（[ADR-0004](0004-split-services-incrementally.md)）が、
  生成したクライアントの型まで届いていることを確かめる

## 検証事項

- フロントの実装が始まったとき（DEV-25 / DEV-26）、生成した型で足りるか。
  クライアント本体まで生成する必要が出るか
- 契約を先に決めたくなる場面が出るか。出たなら、そのエンドポイントだけ定義を先に書く運用もありうる
