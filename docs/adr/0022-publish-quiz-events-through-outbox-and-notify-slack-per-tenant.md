# ADR-0022: クイズの変更を Outbox から EventBridge に送り、テナントごとの Slack へ Lambda が知らせる

- ステータス: Accepted
- 決定日: 2026-09-30

## 背景と課題

Phase 5 で、クイズを追加・更新したときに Slack へ知らせる。通知は `notification-service`（Lambda）として、最初から別のサービスにすると決めている（[ADR-0004](0004-split-services-incrementally.md)）。
quiz-service は状態の変化をドメインイベントとして送り、notification-service はそれを受けて Slack に送る。

ADR-0004 は「Phase 1 ではインメモリのイベントバスで実装し、Phase 5 で EventBridge に差し替える」としていたが、**インメモリのバスは作っていない。**
モジュール間（quiz と answer）の呼び出しは、呼ぶ側が持つインターフェースで足りた（ADR-0004 の検証事項）。
イベントを送る仕組みは、ここで初めて作る。

決めること。

- どの操作で、どんなイベントを送るか
- **イベントを確実に送る方法。** クイズの変更だけが残ってイベントが失われる、またはその逆を起こさない
- 同じイベントが 2 回届いたときの扱い
- 通知の送り先と、Webhook の URL の置き場所
- notification-service の言語と、イベントの形を 2 つのサービスで合わせる方法
- 送れなかったイベントの行き先

守らなければならないこと。

- **Aurora の自動一時停止を妨げない**（min 0 ACU。dev は最後の接続から 30 分）。利用者が開いた接続が 1 本でもあると、Aurora は一時停止しない。
  論理レプリケーションを有効にしたときと、RDS Proxy を置いたときも止まらない（AWS のドキュメント）
- **テナントの境界を越えない。** あるテナントのクイズの内容を、別のテナントや運用者に届けない（[ADR-0006](0006-row-level-multi-tenancy.md)）
- NAT Gateway も VPC Endpoint も置かない（[ADR-0013](0013-run-ecs-tasks-in-public-subnets.md)）。Aurora はプライベートサブネットにあり、外へは出られない

## 判断基準

- クイズの操作が、EventBridge や Slack の障害で失敗したり遅くなったりしないこと
- イベントを黙って失わないこと。遅れるのは受け入れる（通知は急がない）
- 常時の費用を増やさないこと。予算は月 30 ドル
- イベントの形のずれを、デプロイの前に見つけられること

## 検討した選択肢

### 送り方

#### A: コミットの後に、直接 EventBridge へ送る

- 最も簡単。表も、送り直す仕組みも要らない
- **送る前にタスクが落ちたり、EventBridge が失敗を返したりすると、イベントが失われる。** 失われたことにも気づけない

#### B: Outbox に書き、別の処理が定期的に読んで送る

クイズの変更と同じトランザクションで Outbox の表に書く。定期的に Outbox を読み、送れていないものを送る。Outbox パターンのよく知られた形。

- 変更とイベントが、どちらも残るか、どちらも残らない
- **定期的に読むたびに Aurora に接続するため、一時停止しなくなる。** アプリの中で読んでも、EventBridge Scheduler と Lambda（Data API）で読んでも同じ。
  最小の 0.5 ACU で起き続けたとしても、ECS のタスクが動く 1 日 18 時間で月に約 40 ドル（0.5 ACU × 0.15 ドル × 18 時間 × 30 日）。予算をこれ 1 つで超える

#### C: Outbox に書き、コミットの直後に送る。送れなかったものは、DB が起きている間だけ拾い直す

B と同じく Outbox に書く。送るのは、コミットの直後に、その操作を受けた quiz-service 自身。
送れなかったもの（EventBridge の失敗、送る前にタスクが落ちたもの）は、**利用者の要求で DB を使った直後の数分間だけ**拾い直す。

- 変更とイベントの関係は B と同じ
- 拾い直すのは DB が起きているときだけなので、一時停止を妨げない。起きている時間が、1 回の利用ごとに数分延びるだけ
- **送れなかったものは、次に誰かが使うまで遅れる。** タスクが落ちたあと誰も使わなければ、何日でも遅れる
- 送る部分と拾い直す部分を、自分で書いて保守する

#### D: DB の変更を AWS のサービスで拾う（変更データキャプチャ）

DMS や Aurora の論理レプリケーションで Outbox への書き込みを拾い、EventBridge へ流す。

- アプリは Outbox に書くだけで、送る処理を持たない
- **論理レプリケーションを有効にすると、Aurora は一時停止しない。** DMS は、レプリケーションのインスタンスの費用もかかる

#### E: Aurora から Lambda を呼ぶ（`aws_lambda` 拡張）

Outbox のトリガーから Lambda を呼び、Lambda が EventBridge へ送る。

- **プライベートサブネットの Aurora から Lambda を呼ぶには、NAT Gateway か Lambda の VPC Endpoint が要る**（AWS のドキュメント）。ADR-0013 で避けた費用がかかる
- トリガーの中で呼ぶと、Lambda の失敗がクイズの操作の失敗になる。トランザクションの外で呼ぶと、A と同じく失われうる

### 重複を捨てる場所

EventBridge の配送は「少なくとも 1 回」で、Outbox から送り直したものも重なりうる。受け手が、イベントの ID で重複を捨てる。

- **DynamoDB**: 条件付きの書き込みで「初めて見る ID か」を確かめ、TTL で消す。オンデマンドなら、この量ではほぼ 0 ドル。Lambda を VPC に入れずに使える
- **Aurora**: Lambda を VPC に入れることになる。通知のたびに Aurora を起こし、Slack へ出るのに NAT Gateway も要る
- **Powertools for AWS Lambda の冪等性の機能**: DynamoDB を使う同じ仕組みを、ライブラリが持つ。書く量は減るが、手順がライブラリの中に隠れる

### Webhook の URL の置き場所

Webhook の URL は、知っていれば誰でもそのチャンネルに投稿できる。secret として扱う。

- **SSM Parameter Store（SecureString）**: 標準のパラメータは無料で、1 万個まで置ける。テナントの ID をパスに入れ、IAM でパスごとに読み書きを分けられる
- **Secrets Manager**: 1 つ月 0.4 ドルで、テナントの数だけ増える。ローテーションの機能は、Webhook では使わない
- **Aurora**: Lambda が DB を読むことになる（重複と同じ理由で避ける）。暗号化も自分で持つ
- **イベントに載せる**: バス、アーカイブ、ログに secret が流れる

### notification-service の言語

- **Kotlin**: イベントの型を quiz-service と共有でき、形のずれをコンパイルで見つけられる。ビルドとテストは Gradle のまま。JVM は起動に数秒かかる
- **TypeScript**: 起動が速く、成果物が小さい。イベントの形は、JSON Schema などを介して quiz-service と合わせる

## 決定

**送り方は C を採用する。** 重複は DynamoDB で捨て、Webhook の URL はテナントごとに SSM Parameter Store に置く。notification-service は Kotlin で書く。

A はイベントを黙って失う。B と D は Aurora を止めなくなり、費用が予算を超える。E は ADR-0013 で避けた経路の費用がかかる。
C の弱み（送れなかったものが遅れる）は、通知が急がないことで受け入れる。
Kotlin の起動の遅さは、非同期の通知では利用者を待たせない。

```
管理者 → quiz-service ─┬─ クイズの変更 ─┐ 同じトランザクション
                       └─ quiz.outbox ──┘
           │ コミットの直後に送る（別のスレッド）
           │ 送れなかったものは、DB を使った直後の数分間に拾い直す
           ▼
       EventBridge（カスタムバス。アーカイブ 7 日）
           │ ルール（通知するイベントだけ）
           ▼
       notification-service（Lambda、Kotlin、VPC の外）
           ├ DynamoDB: イベントの ID で重複を捨てる
           ├ SSM Parameter Store: テナントの Webhook の URL を読む（無ければ何もしない）
           └ Slack（Incoming Webhook、Block Kit）

       送れなかったもの → SQS（DLQ）→ CloudWatch のアラーム → メール
```

### 1. 送るイベント

**1 回の操作で送るイベントは 1 つ。** 同じ操作の通知が 2 回届かないようにする。

| イベント | いつ |
| --- | --- |
| `QuizCreated` | クイズを作った（下書きでも公開でも。状態を含む） |
| `QuizUpdated` | 状態を変えずに、中身を変えた（状態を含む） |
| `QuizPublished` | 下書きを公開した |
| `QuizUnpublished` | 公開を下書きに戻した |
| `QuizzesImported` | 一括インポートで取り込んだ（件数だけ） |

- 状態が変わった保存は、`QuizUpdated` ではなく `QuizPublished` / `QuizUnpublished` だけを送る
- **一括インポートは 1 つにまとめる。** 1 件ずつ送ると、最大 500 件の通知が並ぶ
- 削除と復活は、いまは送らない。カテゴリを消すと配下のクイズがまとめて消え（[ADR-0007](0007-soft-delete-master-data.md)）、受け手もいない。受け手ができたら足す
- **何を通知するかは、受け手のルールが決める。** いまは公開中のクイズに関わるものを通知する（公開の状態の `QuizCreated` と `QuizUpdated`、`QuizPublished`、`QuizzesImported`）。
  下書きの編集は通知しない。送る側は、受け手の都合でイベントを減らさない

### 2. イベントの形

EventBridge の `source` は `quiz-app.quiz-service`、`detail-type` はイベントの名前。`detail` の例。

```json
{
  "eventId": "0192f3c4-…",
  "version": 1,
  "occurredAt": "2026-09-30T09:00:00Z",
  "tenant": { "id": "…", "slug": "demo", "name": "デモ" },
  "quiz": {
    "id": "…",
    "status": "PUBLISHED",
    "category": { "id": "…", "name": "AWS / インフラ" },
    "question": "問題文の冒頭（100 文字まで）"
  }
}
```

- **`eventId` は Outbox の行の ID。** 何度送り直しても変わらない。EventBridge が付ける `id` は送るたびに変わるため、重複を捨てる鍵には使えない
- **正解、選択肢、解説は載せない。** バス、アーカイブ、ログは quiz-service の外にある。通知に要るのは、どのクイズかが分かることと、画面へのリンクを作れること
- 操作した人は載せない。いまの受け手が使わない
- 順番は保証しない。受け手は `occurredAt` を見る
- **項目を足すだけなら、版を上げない。** 受け手は知らない項目を無視する。消す・意味を変えるときは版を上げ、受け手が新旧どちらも読めるようにしてから、送る側を替える

イベントの型は Gradle のモジュール（`libs/quiz-events`）に置き、2 つのサービスで共有する。共有するのは型だけで、JSON の読み書きはそれぞれが持つ。
2 つのサービスは別々にデプロイされるため、送る側と受ける側の版は一時的にずれる。そこで、**イベントごとの JSON の見本を `docs/events/` に固定する。**
送る側は書き出したものが見本と同じであることを、受ける側は見本を読めることを、それぞれのテストで確かめる（OpenAPI と同じ考え方。[ADR-0010](0010-generate-openapi-from-code.md)）。

### 3. Outbox と拾い直し

- Outbox は `quiz` スキーマの表（`quiz.outbox`）。テナント配下の表と同じく、`tenant_id` と行レベルセキュリティを付ける
- クイズの変更と同じトランザクションで書く。**送るのはコミットの後。** コミットの前に送ると、ロールバックしたのにイベントだけが届く
- コミットの直後に、quiz-service が別のスレッドで送り、送れたら印（`published_at`）を付ける。**操作の応答は、送れたかどうかを待たない。** 送れなくても、操作は成功のまま
- 送れなかったものは、**利用者の要求で DB を使ってから 5 分の間だけ**、1 分ごとに拾い直す。拾い直し自身は「DB を使った」に数えない
  - 1 分より新しい行は拾わない。コミットの直後の送信と重ならないようにする
  - **起動したときには拾わない。** 夜間の停止が明けてタスクが起動するたび（8:00）に、毎朝 Aurora を起こすことになる
  - 送れなかったものは、次に誰かが使うまで待つ。デプロイの最後のスモークテストも「使う」に数える
- 拾い直しだけは、テナントをまたいで読む。**セッション変数 `app.outbox_relay` を立てたときだけ、ポリシーがテナントをまたいで読ませる。**
  立てるのは拾い直しの 1 か所だけ。ほかのコードが絞り込みを書き漏らしても、別のテナントの行は返らない（RLS の役割は変わらない）
  - テナントごとに順に読む形は、テナントの数だけ問い合わせることになる。RLS を付けない別のスキーマに置く形は、書き漏らしたときに止めるものがない
- タスクが 2 つあるとき（デプロイの入れ替え中）に同じ行を拾わないよう、`FOR UPDATE SKIP LOCKED` で読む。それでも重なったものは、受け手が捨てる
- 送れた行は 7 日で消す

### 4. 受け手と重複

- notification-service は **VPC の外**で動かす。Slack、DynamoDB、SSM へ、NAT なしで直接出る。Aurora には触れないため、通知が DB を起こさない
- EventBridge のルールから、Lambda を非同期で呼ぶ
- 重複は DynamoDB で捨てる。手順は自分で書く（Powertools の冪等性の機能と同じ考え方）。短く、何が起きるかをコードで読める
  1. `eventId` を「処理中」（期限 5 分）として書く。**まだ無いか、処理中の期限が切れているときだけ**書ける。書けなければ、処理済みか処理中なので何もしない
  2. Slack に送る。失敗したら記録を消し、例外で終わる（Lambda が再試行する）
  3. 送れたら「済み」にする。記録は TTL で 7 日後に消える（アーカイブの保持期間と揃える）
- 2 と 3 の間で落ちると、期限が切れたあとの再試行で、同じ通知がもう一度届く。まれなので受け入れる

### 5. 通知の送り先

**テナントの管理者が、自分のテナントの Slack の Webhook を設定する。** 運用者の 1 か所に集めると、全テナントのクイズの内容が運用者に届く。

- URL は SSM Parameter Store の SecureString に、テナントごとに置く（`/quiz-app/{環境}/tenants/{テナントの ID}/slack-webhook-url`）
  - quiz-service は書くことと消すことだけができ、読めない。画面は「設定済みかどうか」だけを出し、URL は二度と表示しない
  - notification-service は読むことだけができる
- **URL は `https://hooks.slack.com/` で始まるものだけを受け付ける。** 保存するときに quiz-service が、送る前に notification-service が確かめる。
  任意の URL を許すと、管理者が指定した先へ Lambda が要求を送る踏み台になる
- 設定のないテナントのイベントは、Lambda が何もせずに終わる。quiz-service は、通知の設定によってイベントを送るかどうかを変えない
- URL は Terraform を通らないため、state にも残らない

### 6. 送れなかったもの

- Slack が 5xx や 429 を返したとき、通信に失敗したときは、例外で終わる。Lambda の非同期呼び出しが 2 回まで再試行する
- 4xx（Webhook が消された、など）は、再試行しても直らない。ログに残して終わる
- 再試行しても送れなかったものと、Lambda まで届かなかったもの（EventBridge のターゲットの失敗）は、同じ SQS の DLQ に入る
- **DLQ に 1 件でも入ったら、CloudWatch のアラームからメールで知らせる。** 監視の作り込みは Phase 6 だが、黙って捨てない。
  通知先のアドレスは公開のリポジトリに載せず、`terraform.tfvars` で渡す
- バスのアーカイブ（7 日）から、同じイベントを流し直せる。受け手が重複を捨てるため、流し直しても二重には届かない

## 結果

### 良い影響

- クイズの操作は、EventBridge や Slack の障害で失敗も遅延もしない
- Aurora の自動一時停止は保たれる。起きている時間は、1 回の利用ごとに最大 5 分ほど延びるだけ
- テナントのクイズの内容は、そのテナントが設定した Slack にだけ届く。Webhook の URL は、DB、イベント、ログ、Terraform の state のどこにも残らない
- 同じイベントが何度届いても、通知は 1 回。アーカイブから流し直せる
- 増える費用は月に 1 ドルに満たない。EventBridge は 100 万件あたり 1 ドル、DynamoDB・Lambda・SQS はこの量ではほぼ 0、アラームは 1 つ 0.1 ドル、SSM の標準のパラメータは無料

### 悪い影響・受け入れるリスク

- **送れなかったイベントは、次に誰かが使うまで届かない。** 通知が数日遅れることがありうる
- 送る部分と拾い直す部分を、自分で書いて保守する。Aurora を止めるという制約のもとでは、マネージドのサービスに任せられなかった
- Outbox の表だけ、RLS のポリシーにテナントをまたぐ条件（`app.outbox_relay`）がある
- まれに、同じ通知が 2 回届く（4 の手順の 2 と 3 の間で落ちたとき）
- 一括インポートは件数だけを送る。取り込んだクイズを 1 件ずつ知りたい受け手が現れたら、イベントを足す
- notification-service は JVM のため、起動に数秒かかる
- `libs/quiz-events` を変えると、2 つのサービスが同時に変わる。形の互換は、見本のテストで守る

### 緩和策

- Outbox に残っている最も古い行の経過時間を、ログに出す。Phase 6 の監視で閾値を決め、アラームにする
- 拾い直しの間隔と、DB を使ってから拾い直す時間（5 分）は、設定で変えられるようにする
- JVM の起動が問題になったら、SnapStart を使う（Java では追加の費用がかからない）

## 検証事項

- 拾い直しを入れたあとも、使っていない間に Aurora が 30 分で一時停止すること（`DatabaseConnections` と RDS のイベント）
- LocalStack で、EventBridge のルールから Kotlin の Lambda を呼び、DynamoDB と SSM を使えること
- Kotlin の Lambda の起動時間とメモリ（512 MB で足りるか）
- ルールの絞り込み（`detail.quiz.status`）で、下書きの編集が通知されないこと
- モジュール間（quiz と answer）の呼び出しをイベントにするか、同期の呼び出しのままにするかは、DEV-100 で決める
