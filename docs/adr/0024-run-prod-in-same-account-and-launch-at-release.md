# ADR-0024: prod は同じアカウントに環境として置き、常時動かすのは公開のときから。main へのマージと承認で載せる

- ステータス: Accepted
- 決定日: 2026-10-03

## 背景と課題

`envs/prod` は backend と provider だけで、リソースを持たない（[ADR-0011](0011-terraform-state-and-environments.md)）。
Phase 6 の終わりに prod を作り、リリースの手順を確立する（DEV-119）。その前に、dev と何を変えるかを決める。

**prod を作ると、常時の費用がほぼ倍になる。** 予算は月 30 ドルで、dev だけで約 20 ドル使う（[コスト方針](../development-guidelines.md#8-コスト方針)）。

| prod の費用（東京、1 か月 730 時間） | 月額 |
| --- | --- |
| ECS のタスク（0.5 vCPU / 1 GB）を 24 時間 | 約 18 ドル |
| タスクのパブリック IPv4 | 約 3.7 ドル |
| Cloud Map、Secrets Manager（Aurora のマスター） | 約 1 ドル |
| Aurora の ACU（min 0。起きている間は 0.5 ACU で 1 時間 0.075 ドル） | 使った分。1 日 2 時間で約 4.5 ドル |
| Aurora を min 0.5 ACU で常に起こしておく場合 | **約 55 ドル**（上の行の代わり） |
| API Gateway、CloudFront、S3、Cognito、アラーム、ダッシュボード | ほぼ 0（無料枠と従量） |

決めること。

- Aurora の最小容量、バックアップ、削除保護
- ECS を夜間に止めるか、タスクをいくつにするか
- ドメイン、Cognito、解説図のバケット、イベントのバスを、dev と分けるか
- AWS のアカウントを分けるか
- 予算の中で prod をどう持つか
- デプロイの経路（何をきっかけに、誰の承認で載せるか）

## 判断基準

- 予算（月 30 ドル）を、公開の前に超えない
- **prod の事故の範囲を、dev から切り離す。** dev の作業（apply、デプロイ、訓練）で prod の利用者のデータに触れない
- dev と prod で、手順とコードを分けない。違いは `envs/` の値の差として読める（ADR-0011 の D-1）
- 1 人で運用できる量に収める

## 検討した選択肢

### アカウント

**A-1: 同じアカウントに置き、名前とタグ（`Env`）で分ける。** 管理するものが増えない。
dev の作業者は prod にも触れられる。権限では分けられず、手順で防ぐ。

**A-2: prod のアカウントを分ける（AWS Organizations）。** 事故の範囲を最も小さくでき、設計としては標準的。
アカウント、Identity Center の割り当て、state の置き場所、ドメインの委任、予算、OIDC のプロバイダが、それぞれもう 1 つずつ要る。

### 予算と prod の持ち方

**B-1: 公開（Phase 7）のときから常時動かす。** DEV-119 では、コードと手順を作り、一度立てて確かめる。そのあとは公開まで動かさない。
公開のときに、予算を上げるか、dev を縮める（コストの最終調整）。

**B-2: 予算を月 60 ドルほどに上げ、いまから常時動かす。** 使う人がいない prod に、公開までの間ずっと払う。

**B-3: dev を縮めて 30 ドルに収める。** dev のタスクを使うときだけ起動するなどで、prod の分を空ける。
開発のたびに起動を待つ。

### Aurora の最小容量

**C-1: min 0 ACU（dev と同じ）。** 使われなければ止まる。止まったあとの最初の操作は 15〜20 秒待つ。
画面は 3 秒で案内を出し、5xx と通信の失敗を再試行する。

**C-2: min 0.5 ACU。** 待ちがなくなる。これだけで月に約 55 ドルかかり、予算を超える。

### デプロイの経路

**D-1: develop から main への PR をリリースとし、マージでデプロイが始まり、GitHub の Environment `prod` の承認を待って載せる。**
dev と同じスクリプトとワークフローを使う。承認の画面で、載せるコミットを確かめてから進められる。

**D-2: main へのマージで、承認なしに載せる。** PR のマージを承認とみなす。手順は最も少ない。

**D-3: main にタグ（`v1.2.3`）を打ったときに載せる。** 版を数えやすい。タグを打つ手順と、タグとコミットの対応の管理が増える。

## 決定

**A-1、B-1、C-1、D-1 を採る。** prod は同じアカウントに環境として置く。常時動かすのは公開のときから。
Aurora は min 0 のまま。リリースは develop から main への PR で、マージのあとに承認して載せる。

アカウントを分けない（A-1）のは、1 人で運用する規模では、分けて得る隔たりより、増える管理（アカウント、SSO、state、ドメイン、予算）の重さが勝つため。
代わりに、次の「dev と prod の違い」で、dev の作業が prod に届かないようにする。

prod の常時の費用（約 25 ドル）は、公開して見てもらえるようになってから払う（B-1）。それまでの間は、使う人がいない。
min 0.5 ACU（C-2）は、それだけで予算を超える。待ちは画面の案内と再試行で受け止める（C-1）。

承認を挟む（D-1）のは、prod には利用者のデータがあるため。main へのマージと載せる瞬間を分け、載せるコミットを確かめてから進める。

### dev と prod の違い

| 項目 | dev | prod | 理由 |
| --- | --- | --- | --- |
| Aurora の最小容量 | 0 ACU | 0 ACU | C-1 |
| 止まるまでの時間 | 30 分 | 60 分 | 見に来た人が、読んでいる間に止めない。起きている時間が延びる分は、1 回あたり数セント |
| バックアップの保持 | 1 日 | 7 日 | 気づくのが遅れても戻せる。DB の大きさまでのバックアップは無料 |
| 削除保護と最終スナップショット | なし | あり | 誤った apply や destroy で消さない |
| 消した図を残す日数 | 7 日 | 14 日 | Aurora のバックアップの保持より長くする（DEV-117） |
| ECS の夜間の停止 | 2:00〜8:00 | しない | 見に来る時間を選べない |
| タスクの数 | 1 | 1 | ステートレスで、落ちても ECS が起動し直す。2 つにすると費用が倍になる。2 つのサブネット（AZ）のどちらにも置ける |
| ログの保持 | 14 日 | 30 日 | 障害のあとに遡れる |
| ドメイン | `dev.<ドメイン>` | `quiz.<ドメイン>` | apex には、このアプリ以外の既存のレコードがある（触らない） |
| Cognito の User Pool | dev 用 | prod 用（分ける） | 利用者を混ぜない。E2E の利用者は prod に作らない。スモークテストの利用者は作る |
| 解説図のバケット、イベントのバス、アラームの送り先、ダッシュボード | dev 用 | prod 用（分ける） | 同じモジュールを、名前（`quiz-app-prod`）を替えて使う |
| デモのシード | 入れる（`dev` プロファイル） | 入れない | `SeedDataGuard` が止める。公開のときのデモは Phase 7 で用意する |
| スモークテストのテナント | シードで入れる | 入れる | prod でもスモークテストを流す。シードを、デモと分けて入れられるようにする（DEV-119） |
| デプロイ | develop へのマージで載る | main へのマージのあと、承認で載る | D-1 |
| デプロイのロール | Environment `dev`（develop からだけ） | Environment `prod`（main からだけ）。別のロール | dev のジョブが prod のロールを引き受けられない |
| `terraform apply` | 最新の develop から | **main から** | prod には、リリースしたものと同じ形だけを流す |

- 環境ごとの違いは `envs/prod` の値で表し、モジュールは dev と共有する。モジュールに足した変数（夜間の停止、削除保護など）は、すでに環境ごとに変えられる
- 予算の通知と OIDC のプロバイダは、アカウントに 1 つ（`infra/terraform/account`）のまま、両方の環境が使う

## 結果

### 良い影響

- 公開までの間、予算を超えない
- dev と prod が同じモジュール、同じデプロイのスクリプトで動く。dev で確かめた手順（Runbook、訓練）が、そのまま prod に当てはまる
- prod に載せるものを、承認の前に確かめられる

### 悪い影響・受け入れるリスク

- **アカウントが同じため、dev の作業者は prod にも触れられる。** 誤って prod に apply する、prod の DB に Data API でつなぐ、といった事故を権限では防げない
- **prod でも、止まったあとの最初の操作は 15〜20 秒待つ。** 初めて見に来た人の最初の印象が、待ちになりうる
- prod のタスクは 1 つで、デプロイの入れ替え中と、落ちてから起動し直すまで（数分）は 503 になる
- 公開のときに、予算を上げるか dev を縮めるかを、改めて決める必要がある

### 緩和策

- 削除保護と最終スナップショット、7 日のバックアップで、prod の DB を消しても戻せる（手順は Runbook。DEV-117 で dev で確かめた）
- prod のデプロイのロールは、Environment `prod`（main からだけ）でしか引き受けられない。dev のジョブから prod に載せられない
- prod の apply は main から流すと決めておく。`envs/prod` は dev と別のディレクトリと state で、うっかり dev のつもりで prod を変えることはない
- 待ちは、画面の案内（3 秒）と再試行で受け止める。止まるまでの時間を 60 分にして、見ている間には止めない
- 公開のときに、待ちと 503 の頻度をダッシュボードで見て、min 0.5 ACU やタスク 2 つを改めて検討する

## 検証事項

- prod の構築とリリースの手順（DEV-119）: 承認の待ち、main からの apply、最初のデプロイ（`backend=deploy`、`migration=run`）が手順どおりに通るか
- スモークテストのテナントを、デモのシードと分けて prod に入れる方法
- prod を一度立てて確かめたあと、公開まで動かさない方法。タスクを 0 にして置く（月 2 ドルほど。Aurora のストレージ、Cloud Map、シークレット）か、消して公開のときに作り直すか
- アラームの数。dev の 5 つと合わせて 10 個で、無料枠（10 個）の上限に届く。足すと 1 つ 0.1 ドルかかる
