# ADR-0013: ECS のタスクはパブリックサブネットに置き、NAT Gateway も VPC Endpoint も使わない

- ステータス: Accepted
- 決定日: 2026-09-24

## 背景と課題

ECS のタスク（quiz-service と、マイグレーションの単発タスク）は、起動と実行のために AWS の API へ出ていく必要がある。

- ECR からイメージを取得する（レイヤーの実体は S3 にある）
- CloudWatch Logs へログを送る
- Secrets Manager から DB の認証情報を受け取る

当初の方針は「NAT Gateway は使わず VPC Endpoint で代替」だった（[開発ガイドライン](../development-guidelines.md) のコスト方針）。
NAT Gateway は通信量に関わらず月額が固定でかかるためである。

ところが、**インターフェイス型の VPC Endpoint も 1 本・1 AZ ごとに時間課金される。**
上の 3 つだけで 4 本（ECR api / ECR dkr / Logs / Secrets Manager）が要り、本数と AZ の数によっては NAT Gateway より高くなる。
ALB と Aurora が 2 つの AZ を要求するため、サブネットは 2 AZ に作る。

Aurora は外へ出る必要がない。問題は ECS のタスクの出口だけである。

## 判断基準

- 常時かかる費用。dev の ECS を夜間に止めたとき（DEV-51）、一緒に下がるか
- 外からタスクに直接届かないこと
- 自分で面倒を見るものが増えないこと
- 後から別の方式へ移れること

## 検討した選択肢

東京リージョンの公開価格（AWS Price List API で確認）から、1 か月 730 時間で概算した。
ALB のパブリック IP（2 AZ で月 約 7 ドル）はどの案でも同じなので含めない。
常時動くタスクは quiz-service の 1 つとした。web は Amplify Hosting で配り、ECS には載らない（ADR-0012）。

| 案 | 月額の目安 | 夜間停止で下がるか |
| --- | --- | --- |
| A: プライベート + VPC Endpoint 4 本 × 2 AZ | 約 82 ドル + 0.01 ドル/GB | 下がらない |
| A': A を 1 AZ に絞る | 約 41 ドル + 0.01 ドル/GB | 下がらない |
| B: プライベート + NAT Gateway 1 台 | 約 45 ドル + 0.062 ドル/GB | 下がらない |
| C: プライベート + NAT インスタンス（t4g.nano） | 約 8 ドル | 下がらない |
| D: パブリック + タスクにパブリック IP | 約 4 ドル（夜間停止で約 2 ドル） | 下がる |

単価: Endpoint 0.014 ドル/時、NAT Gateway 0.062 ドル/時、t4g.nano 0.0054 ドル/時、パブリック IPv4 0.005 ドル/時、gp3 0.096 ドル/GB 月。

### A: プライベートサブネット + インターフェイス型の VPC Endpoint

教科書どおりの構成。タスクはインターネットへの経路を持たない。

- 費用が最も高い。Endpoint はタスクを止めても課金が続く
- 使う AWS のサービスが増えるたびに Endpoint も増える（Phase 5 の EventBridge など）
- A' のように 1 AZ に絞ると半額になるが、その AZ が落ちると、もう一方の AZ のタスクも外へ出られない

### B: プライベートサブネット + NAT Gateway

マネージドで、使うサービスが増えても構成は変わらない。

- 1 台で月 約 45 ドル。AZ の障害に備えて 2 台にすると倍になる
- 当初の方針で避けたかった固定費そのもの

### C: プライベートサブネット + NAT インスタンス

EC2 に NAT の役割を持たせる（fck-nat などのイメージがある）。

- B の 5 分の 1 以下で済む
- OS の更新、インスタンスの障害時の切り替えを自分で持つ。止まると全タスクが外へ出られなくなる
- 夜間にタスクを止めても、インスタンスは動き続ける（止めるなら、その仕組みも要る）

### D: パブリックサブネット + タスクにパブリック IP

タスク自身がパブリック IP を持ち、Internet Gateway から直接出る。Aurora だけをプライベートに置く。

- 課金はパブリック IP の分だけで、タスクが止まれば一緒に止まる
- 追加の構成要素がない
- **タスクがインターネットから到達可能なアドレスを持つ。** 守りは SecurityGroup だけになる
- タスクの送信元 IP は起動のたびに変わる。外部のサービスに送信元を登録する使い方はできない

## 決定

**D を採用する。** ECS のタスクはパブリックサブネットに置いてパブリック IP を付け、Aurora はプライベートサブネットに置く。

費用が最も小さく、夜間停止がそのまま効く。A・B・C はいずれも、タスクを止めても出口の費用が残る。

- A・B は D より月 35〜80 ドル高い。タスクに届く経路は SecurityGroup で ALB 経由に限れる（下の緩和策）ため、
  タスクがプライベートサブネットにいることの差は、この額に見合わない
- C は費用では D に近い（差は月 4 ドルほど）。ただし NAT インスタンスの更新と障害時の切り替えを自分で持つことになり、
  止まると全タスクが外へ出られなくなる。面倒を見るものを増やしてまで得るものがない

サブネットの構成。

| サブネット | 置くもの | インターネットへの経路 |
| --- | --- | --- |
| public × 2 AZ | ALB、ECS のタスク | Internet Gateway |
| private × 2 AZ | Aurora | なし |

## 結果

### 良い影響

- 出口の費用が月 数ドルに収まり、夜間停止で半分になる
- NAT も Endpoint も持たないので、面倒を見るものが増えない
- 使う AWS のサービスが増えても、ネットワークの構成を変えずに済む

### 悪い影響・受け入れるリスク

- タスクがパブリック IP を持つ。SecurityGroup の設定を誤ると、ALB を通らずにタスクへ直接届く
- タスクから外への通信は、HTTPS であればどこへでも出られる（B・C でも同じ）
- 「アプリはプライベートサブネットに置く」という定石から外れる。構成図だけを見た人には、理由の説明が要る

### 緩和策

- タスクへの受信は SecurityGroup の参照だけで許し、CIDR では開けない（`modules/network/security_groups.tf`）
  - 外からの入口は ALB だけにし、そこから先は 1 段ずつ隣からの受信だけを許す
  - ALB の受信は、dev へのアクセス制限（DEV-46）が決まるまで開けない
- Aurora のサブネットには Internet Gateway への経路がない。仮に `publicly_accessible` を誤って有効にしても、外からは届かない
- VPC の既定の SecurityGroup からルールを外す。SG を指定し忘れたリソースが、既定の「全許可」に乗らないようにする
- prod で要件が変われば B へ移れる。NAT Gateway とルートを足し、ECS のサービスのサブネットと `assign_public_ip` を替えるだけで、
  アプリにも他のリソースにも手を入れずに済む

## 検証事項

- パブリック IP を付けた Fargate のタスクが、Endpoint なしで ECR からイメージを取得し、Secrets Manager の値を受け取れること（DEV-45）
- quiz-service を ALB で公開する構成（ADR-0012）でも、タスクへの受信を ALB からだけに限れていること（DEV-45）
- 実際の請求額が試算と合うこと（DEV-51）
