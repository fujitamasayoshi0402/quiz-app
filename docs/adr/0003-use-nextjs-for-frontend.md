# ADR-0003: フロントエンドに Next.js を採用する

- ステータス: Accepted
- 決定日: 2026-09-21

## 背景と課題

一般ユーザー向けの出題・回答画面と、管理者向けのクイズ管理画面を実装する必要がある。
管理画面では draw.io の埋め込みエディタを扱うため、クライアントサイドの実装が一定量発生する。

本プロジェクトにおいてフロントエンドは主たる学習対象ではない。
そのため「調べながら書く時間」を最小化できることを重視する。

## 判断基準

- 情報量とエコシステムの大きさ。詰まったときに解決までが速いこと
- UI コンポーネントが揃っており、管理画面を短時間で形にできること
- 将来のモバイル展開（React Native）に知識が転用できること
- AWS 上で配信する手段があること

## 検討した選択肢

### 選択肢 A: Next.js (App Router) + TypeScript

React のデファクト。Server Components によりデータ取得をサーバー側に寄せられる。
shadcn/ui など管理画面向けのコンポーネント資産が豊富。

### 選択肢 B: React Router (旧 Remix) + TypeScript

Web 標準に寄せた設計で、フォーム処理が素直。ただし Next.js に比べると情報量が少なく、
詰まったときの調査コストが高い。

### 選択肢 C: SvelteKit

記述量が少なく学習曲線が緩やか。ただし React の知識が蓄積しないため、
React Native への転用が効かない。

### 選択肢 D: Vue + Nuxt

同じく成熟しているが、上記と同様にモバイル展開時の知識転用の面で不利。

## 決定

**選択肢 A（Next.js App Router + TypeScript）を採用する。**

UI は Tailwind CSS + shadcn/ui、サーバー状態の管理は TanStack Query、
入力値の検証は Zod を用いる。API の型は OpenAPI 定義から生成し、手書きしない。

決め手は、フロントエンドを学習対象としていない以上、**実装時間あたりの成果が最大になる選択**が
合理的である点。加えて、将来 React Native (Expo) でモバイル版を作る際に React の知識がそのまま活きる。

## 結果

### 良い影響

- 管理画面のテーブル・フォーム・ダイアログを shadcn/ui でほぼ組み立てられる
- OpenAPI から型を生成するため、バックエンドの変更がフロント側の型エラーとして検出される
- モバイル展開時に React の知識を再利用できる

### 悪い影響・受け入れるリスク

- App Router は Server Components / Client Components の境界を意識する必要があり、
  慣れるまでは判断に迷う場面がある
- SSR を使う場合、静的ホスティングでは配信できず、実行環境が必要になる（コストに影響）

### 緩和策

- 認証が絡む画面は Client Components に寄せ、境界の判断を単純化する
- 配信方式は Phase 2 で決定する。SSR が不要と判断できれば静的書き出しに寄せ、
  CloudFront + S3 で配信してコストを抑える

## 検証事項

- 配信方式の決定（Amplify Hosting / CloudFront + S3 / ECS）。Phase 2 で別 ADR として起票する
- draw.io の埋め込み（embed.diagrams.net）が Client Components で問題なく動作するか
