# ADR-0015: dev へのデプロイは GitHub Actions がタスク定義のリビジョンを登録して行い、Terraform はタスク定義の形だけを持つ

- ステータス: Accepted
- 決定日: 2026-09-25

## 背景と課題

develop へのマージで、dev に自動でデプロイされる状態にする（DEV-48）。AWS の認証は OIDC で行い、アクセスキーは発行しない。

これまでの手順（DEV-45）では、**デプロイは `terraform apply` だった。**
イメージを push し、`terraform.tfvars` のイメージのタグを書き換え、マイグレーションのタスク定義だけを `-target` で先に更新して流し、
最後に `terraform apply` でサービスを入れ替える。

これを CI に移すとき、**「どのイメージを動かすか」を Terraform と CI のどちらが持つか**を決める必要がある。
両方が同じ属性を書き換えると、片方の実行がもう片方の結果を巻き戻す。
たとえば CI がデプロイしたあとに手元で `terraform apply` すると、tfvars に残っている古いタグに戻る。

あわせて、次も決める。

- CI のロールを、どの条件で引き受けさせるか
- イメージをどこで作るか。CI（PR のチェック）で作ったものを使い回すか

## 判断基準

- CI のロールの権限を、デプロイに要るものだけに絞れること
- Terraform と CI が同じ属性を奪い合わないこと。どちらを実行しても、デプロイ済みのイメージが巻き戻らないこと
- マイグレーションが失敗したら、サービスが更新されないこと
- 起動に失敗して前のリビジョンに戻ったとき、デプロイが失敗として扱われること
- 手順を読んで、何が起きているかを追えること

## 検討した選択肢

### A: CI が `terraform apply` する

イメージのタグを変数で渡し、これまでの手順をそのまま CI で流す。

- 何が動いているかは、Terraform の state を見れば分かる
- **CI のロールが、state にあるすべてのリソースを読み書きできる必要がある**（IAM、VPC、Aurora など）。実質的に管理者になる
- 手元の apply と state のロックを奪い合う。手元で作業している間は、マージしてもデプロイが止まる
- マイグレーションを先に流すために `-target` を使う。`-target` は依存をたどって想定外のものを巻き込むことがある

### B: CI がタスク定義の新しいリビジョンを登録する。Terraform は形だけを持つ

Terraform は、タスク定義の形（環境変数、ロール、CPU とメモリ、ログの出し先）を持つ。
CI は、そのファミリーの最新のリビジョンを読み、イメージだけを差し替えて登録し直し、サービスを更新する。
Terraform は、サービスが参照するリビジョンの変化を無視する（`ignore_changes`）。

- CI のロールに要るのは、ECR への push、タスク定義の登録、マイグレーションの起動、サービスの更新だけ。Terraform の state には触れない
- 最新のリビジョンを元にするため、Terraform で形を変えれば、次のデプロイで新しいイメージとともに反映される
- **動いているリビジョンは Terraform の state にない。** `terraform plan` からは、どのイメージが動いているかが分からない
- Terraform で形を変えても、次のデプロイまで動いているタスクには反映されない

### C: タスク定義を JSON でリポジトリに持ち、デプロイツール（ecspresso など）が登録する

タスク定義は Terraform の管理から外す。

- タスク定義の変更も、アプリの変更と同じ PR で流れてデプロイされる
- ロールの ARN、ロググループ、DB の接続先など、Terraform が作る値を JSON に渡す仕組みが要る
- ツールが 1 つ増え、Terraform とデプロイツールの両方を読まないと構成が分からない

### D: CodePipeline / CodeDeploy

マネージドのパイプラインに任せる。

- CI（GitHub Actions）とデプロイの画面が分かれ、同じことを 2 か所で設定する
- パイプラインの料金がかかる
- ECS の単発タスク（マイグレーション）を流すには、結局 CodeBuild などでスクリプトを書く

## 決定

**B を採用する。** 手順は AWS CLI のスクリプトで書く（`.github/scripts/deploy-quiz-service.sh`）。

A はロールの権限が大きすぎる。C は、Terraform が作る値をタスク定義へ渡す仕組みと、ツールの学習が増えるわりに、
「タスク定義の変更も自動で流れる」以外の得がない。D は GitHub Actions と役割が重なる。

デプロイの流れ（`.github/workflows/deploy-dev.yml`）。

1. arm64 のランナーでイメージを作り、コミットの SHA（先頭 12 桁）をタグにして ECR に push する
2. マイグレーションのタスク定義の最新リビジョンから、イメージだけを差し替えて登録する。単発のタスクとして流し、終了コードが 0 でなければ止める
3. アプリのタスク定義も同じように登録し、サービスを更新する。入れ替えの完了を待ち、サーキットブレーカーで前のリビジョンに戻ったら失敗にする
4. Amplify のビルドを起動する（同じコミット）。新しい画面が古い API を呼ばないよう、quiz-service の後に流す
5. スモークテスト（`tests/api`）を、画面と同じ経路（Amplify のベーシック認証と proxy）で流す

### 関連して決めたこと

- **ロールの信頼は、リポジトリと Environment で絞る。**
  トークンの `sub` が `repo:<owner>/<name>:environment:dev` と完全に一致するときだけ引き受けられる。
  Environment `dev` は develop からしか使えないよう、GitHub 側で制限する。
  ブランチ（`ref`）で絞るのではなく Environment にしたのは、デプロイの履歴が GitHub に残り、手で流すときも同じ条件がかかるため
- **イメージはデプロイのときに作る。** CI のイメージは PR のチェックのためのもので、x86 で作って push していない。
  使い回すには PR のジョブに ECR の権限を渡すことになる。GitHub の arm64 ランナーは Public リポジトリなら無料で、エミュレーションも要らない
- **公式のアクション（amazon-ecs-deploy-task-definition）は使わない。**
  マイグレーションは別のタスク定義・別のロールで流すため、どのみち CLI で書く部分が残る。
  前のリビジョンに戻ったときに失敗として扱うかを、アクションの挙動に預けたくない
- **失敗の通知は、GitHub の通知（ワークフローの失敗）にする。** Slack への通知は、通知の仕組み（notification-service）ができてから検討する
- CI から `terraform plan` / `apply` はしない。apply はこれまでどおり手元から行う

## 結果

### 良い影響

- CI のロールは、このアプリの ECR・ECS と、決まったロールを ECS に渡すことしかできない
- マージから dev に載るまで、人の操作が要らない。マイグレーションが失敗すれば、サービスは古いまま残る
- 手元の Terraform の作業と、デプロイがぶつからない
- 同じスクリプトを手元からも流せる。CI が使えないときの手順が別にならない

### 悪い影響・受け入れるリスク

- 動いているイメージは、Terraform の state ではなく ECS（とデプロイの履歴）を見ないと分からない
- Terraform でタスク定義の形を変えても、次のデプロイまで動いているタスクには反映されない
- Terraform のイメージのタグ（`quiz_service_image_tag`）は、サービスを作るときにしか効かない。変えても何も起きない
- CI が登録したリビジョンは Terraform の管理外で、溜まり続ける（料金はかからない）
- ECR には直近 10 個のイメージしか残さない。マージのたびに 1 つ増えるため、戻せるのは直近 10 回まで

### 緩和策

- 形を変えたあとは、デプロイのワークフローを手で流す（Actions の画面から `deploy-dev` を実行する）
- イメージのタグの変数には、サービスの作成時にしか使わないことを説明に書く
- デプロイの概要（流したリビジョン、Amplify のジョブ）をワークフローのサマリーに残す

## 検証事項

- develop へのマージから、dev に新しいイメージが載り、スモークテストが通ること
- マイグレーションが失敗したとき、サービスが更新されずにデプロイが失敗すること
- アプリが起動できずに前のリビジョンへ戻ったとき、デプロイが失敗すること
- Environment `dev` を使わないジョブ（PR や他のブランチ）から、ロールを引き受けられないこと
