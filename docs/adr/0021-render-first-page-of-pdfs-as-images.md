# ADR-0021: PDF の 1 ページ目を置くときに画像にし、解説の中に出す

- ステータス: Accepted
- 決定日: 2026-09-29

## 背景と課題

PDF の資料は、解説の本文から `[文字](figure:<図の ID>)` のリンクで指し、ブラウザの PDF ビューアで新しいタブに開く形にした
（[ADR-0020](0020-reference-figures-from-explanations-and-add-images-and-pdfs.md)、DEV-82）。
ページを画像にする変換や、画面の中に描く部品は持たないと決めていた。

使ってみると、**解説の画面では資料の中身が見えず、リンクしかない。** 開かないと、何の資料かが分からない。
スマホでも同じで、解説を読む流れの中で資料の見た目をつかめない。

この ADR は、ADR-0020 のうち PDF の見せ方だけを置き換える。受け取り方、検査、配り方、本文での指し方は ADR-0020 のまま。

守らなければならないこと（ADR-0020 と同じ）。

- **管理者が置いたもので、利用者の画面にスクリプトを動かさない。** 管理者を信頼できる相手とは扱わない
- **テナントの図は、そのテナントの利用者にだけ見せる**（[ADR-0017](0017-deliver-figures-with-cloudfront-signed-urls.md)）

## 判断基準

- 解説の中で、資料の見た目が分かること。スマホ（幅 360px）でも同じに見えること
- 上げられた PDF を、アプリのオリジン（画面）で解析しないこと
- 今の配り方（CloudFront の署名付き URL、図の応答ヘッダ）と、本文の書き方（`figure:`）をそのまま使えること
- 常駐する部品や、画面に送る大きなライブラリを増やさないこと

## 検討した選択肢

### A: `<iframe>` で、ブラウザの PDF ビューアを解説の中に埋め込む

- 作るものは画面だけ。全ページをめくれる
- **スマホで揃わない。** iPhone の Safari は埋め込んだ PDF の 1 ページ目しか出さず、Android の Chrome は埋め込みを描かない。結局リンクを残すことになる
- 図の配信に付けている CSP（`sandbox`）の下で、埋め込んだ PDF をブラウザが描くかは確かめていない。描かなければ、`pdf/` にだけ別の応答ヘッダが要る

### B: 置くときに、quiz-service が 1 ページ目を画像にする

完了を受けたとき（ADR-0020 の検査と同じ場所）、PDFBox で 1 ページ目を描いて画像として置く。解説の中にはその画像を出し、押すと PDF を開く。

- どの端末でも同じに見える。画像の配り方（`img/`、押すと新しいタブで開く）にそのまま乗る
- 画面に送るものは増えない
- **上げられた PDF を、quiz-service が解析する。** 壊れた PDF や、描くのに重い PDF でメモリと時間を使う
- 見えるのは 1 ページ目だけ。2 ページ目からは開いて見る
- フォントを埋め込んでいない PDF は、コンテナに代わりのフォントがなければ文字が欠ける

### C: PDF.js で、画面の中に描く

- 全ページを、どの端末でも同じに描ける
- **上げられた PDF を、アプリのオリジンで解析する。** PDF.js には、細工した PDF でスクリプトを動かせる脆弱性があった（CVE-2024-4367）。
  ADR-0018 で生の HTML を通さないと決めたのと同じ理由で避けたい
- 数百 KB のライブラリを画面に送る。PDF 本体をスクリプトで取るため、CloudFront に CORS の設定も要る

### D: B の変換を、S3 のイベントで動く Lambda で行う

- ECS のタスク（0.5 vCPU / 1 GB）の CPU とメモリを使わない
- 変換が終わるまで、画像のない状態を画面に出す必要がある。画像の検査を quiz-service で行うと決めた DEV-81 と、置き場所が分かれる

## 決定

**B を採用する。**

A はスマホで揃わない。C はアプリのオリジンで PDF を解析する。D は、今の上げる量（管理者が解説に付ける資料）に対して、作るものが多い。
B の弱み（quiz-service が PDF を解析する）は、上限と、失敗を 400 で返すことで抑える。上げられるのは、テナントの管理者だけ。

```
管理者 → ブラウザ → S3 の incoming/（ADR-0020 のとおり）
       → quiz-service（完了を受ける）
           ├ 1 ページ目を PDFBox で描く → JPEG → img/{テナントの ID}/{図の ID}
           └ 本体をバケットの中で写す → pdf/{テナントの ID}/{図の ID}
       → quiz.figures（行。種類は pdf）

利用者 → <img src="/api/t/{slug}/play/figures/{id}/preview">（1 ページ目の画像へ送る）
       → 押すと /api/t/{slug}/play/figures/{id}（PDF へ送る）を新しいタブで開く
```

### 1. 画像にするもの

- **1 ページ目だけ。** 長い辺を 2,000 px（画像と同じ上限）に合わせて描き、JPEG にする。資料は写真を含むことが多く、PNG では大きさが中身によって大きく変わる
- 埋め込まれた大きな画像は、描く大きさまで間引いて読む（PDFBox の subsampling）。メモリに原寸の画像を持たない
- **開くのにパスワードが要る PDF は受け付けない。** 画像にできず、解説を見る人も開けない。印刷や編集の制限だけのものは受け付ける
- 読めない PDF、ページのない PDF は受け付けない。どちらも 400 で、上げたものは消える（ADR-0020 と同じ）
- 画像にしてから、本体を写す。画像にできない PDF は、配る場所に何も残さない

### 2. 置き場所と配り方

- 1 ページ目の画像は、**同じ図の ID で `img/` に置く。** CloudFront は `img/` をすでに読めるため、インフラは変わらない。消すときは本体と一緒に消える
- `GET /api/t/{slug}/play/figures/{id}/preview` を足す。本文の中に出す画像へ送る。PDF は 1 ページ目の画像、ほかの図は図そのもの
- `GET /api/t/{slug}/play/figures/{id}` は今までどおり図そのもの（PDF なら PDF）へ送る
- 画面は、画像の記法（`![代替テキスト](figure:<図の ID>)`）を `/preview` の画像として出し、押すと図そのものを開く。
  **画面は図の種類を知らなくてよい。** 種類の違いは API の送り先で吸収する

### 3. 本文での指し方

- ADR-0020 の記法をそのまま使う。PDF にも画像の記法が使えるようになる
- 管理画面で PDF を上げると、1 ページ目の画像と、その下に開くリンク（`[ファイル名（PDF）](figure:<図の ID>)`）を入れる。
  画像だけでは、押すと何ページもある資料が開くことが、読む人に伝わらない
- すでにリンクの記法で書いた PDF は、リンクのまま開ける

### 4. フォント

- PDF に埋め込まれていない日本語のフォントは、コンテナに入れた IPAex ゴシック（約 4 MB）で代わりに描く。
  入れないと、その文字が描かれない。Noto Sans CJK（数十 MB）は、イメージが大きくなるため入れない
- 欧文の標準のフォント（Helvetica など）は、PDFBox が持つ代わりのフォントで描く

## 結果

### 良い影響

- 解説の中で、資料の 1 ページ目が見える。スマホでも同じに見える
- 画面は、図の種類で出し分けない。draw.io の図、画像、PDF を同じ部品で出す
- インフラ（CloudFront、バケットのポリシー、IAM）は変わらない

### 悪い影響・受け入れるリスク

- **quiz-service が、上げられた PDF を解析する。** 20 MB の PDF を読み、1 ページ目を描く間、メモリと CPU を使う。
  描くのに時間の上限はない。細工した PDF で長く止まると、その要求を受けたスレッドが占有される。上げられるのはテナントの管理者だけで、この危険を受け入れる
- PDFBox の脆弱性が、quiz-service に及ぶ。描いた結果は画像として置くため、利用者の画面には及ばない
- 見えるのは 1 ページ目だけ
- DEV-84 より前に置いた PDF には、1 ページ目の画像がない。画像の記法で指すと、代わりの文字が出る。リンクの記法なら、今までどおり開ける
- コンテナのイメージが、フォントの分だけ大きくなる

### 緩和策

- PDF の大きさは 20 MB まで（ADR-0020）。描く大きさは長い辺 2,000 px までで、描いた画像のメモリは一定
- 描くのに時間がかかる PDF が問題になったら、別のスレッドで時間を区切るか、D（Lambda）へ移す。置き場所と API の形は変わらない
- PDFBox のバージョンは Gradle で固定し、上げるときに脆弱性の情報を確かめる

## 検証事項

- dev のコンテナ（ECS、0.5 vCPU / 1 GB）で、PDF の 1 ページ目を描けること。スモークテストで確かめる
- 実際の資料（スライドを書き出した PDF、スキャンした PDF）で、描く時間とメモリの使い方
