# ADR-0019: API の入口を ALB から API Gateway（HTTP API）に替え、秘密のヘッダをやめる

- ステータス: Accepted
- 決定日: 2026-09-27

## 背景と課題

quiz-service は ALB で公開している（[ADR-0012](0012-serve-frontend-on-amplify-hosting.md)）。ALB が担っていることは次の 3 つ。

- TLS の終端（`api.dev.<ドメイン>`、ACM の証明書）
- 秘密のヘッダ（`X-Origin-Verify`）を持たない要求を、アプリに届く前に 403 で返す
- タスクのヘルスチェック。デプロイの入れ替えと、失敗したときの自動の戻し（サーキットブレーカー）もこの結果で決まる

**dev の止められない費用の大半が ALB である。** ALB 本体が月に約 17.7 ドル、2 つの AZ に 1 つずつ置くパブリック IPv4 が約 7.3 ドル。
夜間にタスクを止めても（DEV-51）減らない。dev の月額の見積もりは予算（30 ドル）を超えている。

秘密のヘッダは、スタブ認証の間になりすましを防ぐために置いた（ADR-0012）。
[ADR-0016](0016-authenticate-with-cognito-managed-login.md) では「API を web の proxy 以外から呼ばせない役割は残る」として残し、見直しを ALB をやめるときに持ち越した。
JWT を API Gateway で検証するかどうかも、同じく持ち越している。

## 判断基準

- 使っていない時間にかかる費用
- 移る間に、web から API へ届かない時間を作らない
- 夜間の停止、デプロイの入れ替え、失敗したときの自動の戻しが、今と同じに動く
- 認証を自前の実装に替えるとき（DEV-59）に直す場所を増やさない

## 検討した選択肢

### 入口

| 案 | 減る額（月） | 概要 |
| --- | --- | --- |
| A: API Gateway（HTTP API）+ VPC リンク + Cloud Map | 約 24 ドル | HTTP API はリクエストの数で課金される（東京で 100 万回あたり約 1.3 ドル）。VPC リンクに料金はない。Cloud Map は、プライベートのホストゾーン（0.5 ドル）と登録したタスク（1 つ 0.1 ドル）、引いた回数（100 万回あたり 1 ドル）だけ |
| B: CloudFront の VPC オリジン + 内部の ALB | 約 7 ドル | パブリック IPv4 の分だけ減る。ALB は残る |
| C: API Gateway（REST API）+ VPC リンク | ほぼ 0 | REST API の VPC リンクは、送り先にロードバランサー（NLB か ALB）を要する |
| D: 予算を上げる | 0 | 構成はそのまま |

A の制約。

- **統合のタイムアウトは最大 30 秒。** 止まっている Aurora への最初の要求は約 19 秒かかる（DEV-50）。24 時間を超えて止まっていると 30 秒を超えうる
- **TLS のポリシーは `TLS_1_2` しか選べない。** TLS 1.2 と 1.3 を受けるが、ALB で絞っていた暗号スイート（CBC を外し、耐量子の鍵交換を優先する）までは絞れない
- ロードバランサーのヘルスチェックがなくなる。コンテナのヘルスチェックに移す
- ECS のタスクを Cloud Map で引くには、SRV レコードで登録する（API Gateway がポートを知るため）

### 秘密のヘッダ

**web の proxy は、ログインのセッションが無い要求の `Authorization` をそのまま中継する**（スモークテストのため、ADR-0016）。
有効なアクセストークンを持つ者は、ヘッダの値を知らなくても、web を通して API を呼べる。
ヘッダが止めているのは、トークンを持たない要求がアプリに届くことだけで、それはアプリが 401 で返す。

| 案 | 概要 |
| --- | --- |
| **やめる** | 認可はアプリがトークンで行う。ADR-0012 の「Phase 3 で JWT を検証するようになったら外せる」に当たる |
| アプリで確かめる | HTTP API には、ヘッダの値で 403 を返す機能がない。値をタスクに渡し、フィルタで比べる。守れるものは上のとおりほぼない |
| Lambda のオーソライザーで確かめる | 要求ごとに Lambda が動く。費用と遅延が増える |

### JWT を検証する場所

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **アプリだけ** | いまのまま。ローカルとテストも同じ経路を通り、検証が 1 か所にある | トークンを持たない要求もタスクまで届く |
| API Gateway の JWT オーソライザーも置く | 無効なトークンを、タスクに届く前に落とせる。料金はかからない | ローカルに API Gateway はないので、アプリの検証も残り、2 か所になる。`token_use` を見ないため ID トークンも通す。自前の認証に替えるとき、発行者と JWKS の公開をあわせて直す |

## 決定

**A で公開し、秘密のヘッダはやめる。JWT はアプリだけで検証する。**

- 入口: API Gateway の HTTP API。独自ドメイン（`api.<環境>.<ドメイン>`）で受け、既定のエンドポイント（`*.execute-api.amazonaws.com`）は閉じる。証明書は ALB と同じもの
- 経路: `/api/{proxy+}` だけを、VPC リンクで quiz-service に送る。ほか（アクチュエータなど）は API Gateway が 404 を返す
- タスクの見つけ方: ECS が Cloud Map（プライベート DNS の名前空間、SRV レコード）にタスクを登録する。
  コンテナのヘルスチェックが通るまで UNHEALTHY のままで、API Gateway は要求を送らない
- ヘルスチェック: ALB から、コンテナのヘルスチェック（中から `curl` でアクチュエータを叩く）に移す。デプロイの入れ替えとサーキットブレーカーも、この結果で判断する
- スロットリング: 10 件/秒、バースト 30。叩かれ続けたときの費用に上限を付ける
- アクセスログ: CloudWatch Logs に JSON で出す。**パスは残さない。** 招待を受け入れる API のパスにはトークンが入る

JWT のオーソライザーを置かないのは、検証を 1 か所に保ち、DEV-59 で直す場所を増やさないため。
サービスを分けて、入口の後ろに複数のバックエンドが並んだら考え直す。

移行は 2 段で行う。

1. ALB を残したまま、API Gateway・VPC リンク・Cloud Map を足す。API のドメインは ALB を指したままにし、API Gateway を通して届くことを確かめる
2. API のドメインを API Gateway に向け直す。DNS の TTL が過ぎてから、ALB と秘密のヘッダを消す

どちらの段でも、web から見た API の URL は変わらない。ALB が残っている間は web がヘッダを付け続けるため、web をビルドし直す順番を気にしなくてよい。

## 結果

### 良い影響

- 月に約 24 ドル減る。止められない費用は、Aurora のストレージなどの数ドルになる
- アクチュエータなど、`/api` の外は外から届かない
- 要求の数と遅延、送り先の失敗がアクセスログに残る。ALB のアクセスログは出していなかった

### 悪い影響・受け入れるリスク

- 統合のタイムアウトが 30 秒。長く止まっていた Aurora の復帰が間に合わないと、504 が返る
- TLS の暗号スイートを選べない
- トークンを持たない要求もタスクまで届く。アプリは DB に触れずに 401 を返す
- ヘルスチェックはコンテナの中から行う。API Gateway から VPC リンクを通ってタスクに届くかは、デプロイの最後のスモークテストが確かめる
- API Gateway が自分で返す応答（404、429、503、504）は `{"message": ...}` の JSON で、ProblemDetail ではない。
  web はこれをバックエンドのエラーとして読まないよう、`application/problem+json` の応答だけを読む（`apps/web/src/lib/api/fetcher.ts`）。
  読むと、夜間の停止中に「サーバーが止まっているか、起動の途中です」の案内が出なくなる

### 緩和策

- 504 は、画面が 5xx として 2 回まで再試行する（`apps/web/src/app/providers.tsx`）。止まったあとの最初の操作は、たいてい読み込み
- 使う人が増えたら、JWT のオーソライザーで入口から落とすことを考え直す

## 検証事項

1 段目（ALB と並べた状態）で、API のドメインの名前を API Gateway に向けて解決させ、dev で確かめた。

| 確かめたこと | 結果 |
| --- | --- |
| API Gateway から VPC リンクを通って、アプリまで届く | 通った。トークンなしは 401（アプリの ProblemDetail）、スモークテストの利用者は 200。`/actuator/health` と `/api` は API Gateway が 404（`{"message":"Not Found"}`）を返す |
| 止まっている Aurora への最初の要求が、30 秒に収まる | 約 22 秒で 200 が返った |
| デプロイの入れ替えの間に、要求が失敗しない | 入れ替えの間に 2〜3 秒おきに 123 回呼び、すべて 200。新しいタスクがヘルスチェックを通って HEALTHY になってから、古いタスクが止まった |
| タスクがないとき（夜間の停止中）に、API Gateway が何を返すか | （確認中） |

月額の実績で ALB の分が減ったかは、切り替えた次の月に確かめる。
