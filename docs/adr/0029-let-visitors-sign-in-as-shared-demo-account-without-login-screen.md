# ADR-0029: 見に来た人は、ログインの画面を通さずに共有のデモのアカウントで入れる。web のサーバーがトークンを取って使い回す

- ステータス: Accepted
- 決定日: 2026-10-14

## 背景と課題

見に来た人がデモを試すには、README にある共有のデモのアカウント（`demo@example.com`。DEV-104）のメールアドレスとパスワードを、
ログインの画面（Cognito の Managed Login。[ADR-0016](0016-authenticate-with-cognito-managed-login.md)）に打ち込む必要がある。
README と画面を行き来する手間で、試さずに帰る人がいる。

ログインの画面に「デモとして入る」を置き、押すだけで共有のデモのアカウントとして入れるようにする。決めること。

- **入り方。** 誰が Cognito にログインし、どうやってセッションを作るか
- **連打への備え。** 押されるたびに Cognito へログインしに行くと、連打されたときに Cognito の上限に当たる。
  ログインの回数の上限（`UserAuthentication`）は 120 件/秒で、アカウントのユーザープールすべてで共有している。使い切ると、ほかの人もログインできない
- **ログアウト、セッションの延長、ログインしている人が押したとき**の扱い

## 判断基準

- **できることを増やさない。** パスワードはすでに公開している。その範囲を超える入口にしない
- 認証の経路を増やさない。バックエンドが確かめるのは、いまと同じ Cognito のアクセストークンだけにする
- 連打されても、ほかの人のログインを止めない
- 費用を増やさない（予算は月 30 ドル。開発ガイドライン「コスト方針」）

## 検討した選択肢

### 入り方

#### A. web のサーバーが、デモのアカウントのパスワードで Cognito にログインする

web のサーバーが Cognito の `InitiateAuth`（`USER_AUTH`、パスワード）を呼び、取ったトークンで、通常のログインと同じ暗号化した Cookie のセッションを作る。
web のクライアントはこの方式をすでに許している（スモークテストがトークンを取るのに使っている）。

- 利点: バックエンドから見ると、通常のログインと区別がつかない。Cognito の設定も変えない
- 欠点: パスワードを web のサーバーに持たせる。連打への備えが要る

#### B. ログインの画面に、メールアドレスだけを渡す

Managed Login を開くときに、メールアドレスを入れた状態にする。

- 利点: 作るものがほとんどない
- 欠点: パスワードの入力は残る。手間はほとんど減らない

#### C. バックエンドに、デモ専用の認証を足す

デモ用の印（固定のトークンなど）を受け付け、デモのアカウントとして扱う。

- 利点: Cognito を呼ばない
- 欠点: 認証の経路が 2 つになり、その検証の漏れがそのまま穴になる。バックエンドが Cognito 以外の何かを信じることになる

### 連打への備え

#### A. 取ったトークンを、web のサーバーが使い回す

デモのアカウントで取ったトークンを、web のサーバーのメモリに期限まで持ち、押した人みんなのセッションに入れる。

- 利点: Cognito を呼ぶのは、サーバー 1 台につき 1 時間に 1 回ほど。連打されても Cognito まで届かない。費用はかからない
- 欠点: 同じトークンを、押した人みんなで共有する。1 人のログアウトでリフレッシュトークンを失効させると、全員のセッションが延ばせなくなる

#### B. AWS WAF で、IP ごとの回数を制限する

Amplify に WAF を付け、`/auth/demo` への要求を IP ごとに制限する。

- 利点: マネージドで、サイトのほかの入口も同じ仕組みで守れる
- 欠点: 月 6〜7 ドル増える（Web ACL、ルール、要求の数）。IP を替えながら叩かれると効かない

#### C. 押すたびにログインし、上限に当たるのは受け入れる

- 利点: 作るものがいちばん少ない
- 欠点: 連打されている間、ほかの人もログインできない

## 決定

**入り方は A（web のサーバーがパスワードでログインする）、連打への備えは A（トークンを使い回す）を採用する。**

| 項目 | 決めたこと |
| --- | --- |
| 入口 | ログインの画面（`/login`）の「デモとして入る」。`POST /auth/demo` を送る |
| 受ける要求 | 同じオリジンからの POST だけ（web の proxy の `isSameOriginRequest`）。ほかのサイトから、見た人を勝手にデモのアカウントでログインさせない |
| パスワード | web のサーバーだけが環境変数で持つ（`NEXT_PUBLIC_` を付けない）。Terraform の `modules/web` から Amplify に渡す。設定がなければボタンを出さず、`/auth/demo` は 404 |
| トークン | サーバーのメモリに持ち、押した人みんなのセッションに入れる。アクセストークンの残りが 15 分を切ったら、次に押されたときに取り直す。同時に押されても、取りに行くのは 1 回 |
| 入ったあと | `/` へ移す。デモのアカウントの所属は 1 つなので、そのテナントへ自動で移る（要件定義「テナント未指定のとき」）。slug をコードに書かない |
| セッションの延長 | 通常のログインと同じく、web の proxy がリフレッシュトークンで延ばす。`InitiateAuth` で取ったリフレッシュトークンも、トークンエンドポイントで使えることを dev で確かめた |
| ログアウト | 共有のセッションでは、リフレッシュトークンを失効させない。Cookie を消すだけにする。セッションに共有の印を持たせて見分ける |
| ログインしている人が押したとき | いまのセッションを捨てて、デモのアカウントで入り直す。捨てるのが共有でないセッションなら、ログアウトと同じくリフレッシュトークンを失効させる |
| ボタンを出さないとき | 招待のリンクから来たとき。招待されたアドレスでログインしてもらう |
| 失敗したとき | ログインの画面に戻し、デモに入れなかったことだけを示す。Cognito のエラーの中身は出さない |

- 押す前に、共有のアカウントであること（回答の履歴とランキングを、見た人どうしで共有すること）を示す
- デモのアカウントは一般ユーザーで、テナントを作れない（[ADR-0028](0028-let-signed-in-users-create-their-own-tenant.md)）。この入口で、できることは増えない

## 結果

### 良い影響

- 見に来た人が、ボタン 1 つでデモのクイズを解き始められる
- バックエンドと Cognito の設定は変わらない。認証の経路は 1 つのまま
- 連打されても、Cognito を呼ぶ回数はサーバーの台数で決まる

### 悪い影響・受け入れるリスク

- **デモのセッションは、みんな同じトークンを持つ。** パスワードを公開しているので、トークンを持てる人の範囲は変わらない
- **共有のリフレッシュトークンが失効すると、デモのセッションはすべて、アクセストークンの期限（最長 1 時間）で切れる。** Terraform でパスワードを替えたときなど。見た人は、もう一度押せば入れる
- web のサーバーが Cognito を呼ぶ回数は、サーバーの台数に比例する。Amplify の SSR が何台に増えるかは、こちらで決められない
- パスワードが、Amplify の環境変数とビルドの中（`.env.production`）にも置かれる。もともと公開しているもので、守る値ではない

### 緩和策

- 共有のリフレッシュトークンを失効させる操作を、アプリの中に作らない（ログアウトで失効させない）
- 取り直しに失敗したときは、持っているトークンをすぐには捨てず、期限までは使う

## 検証事項

- Amplify の SSR のサーバーの台数と、Cognito を呼んだ回数。CloudTrail の `InitiateAuth` で見る
- ほかの入口（ログインの画面）も叩かれるようになったら、WAF（連打への備えの B）を改めて考える
