# ADR-0005: 認証に Amazon Cognito のパスキーを採用する

- ステータス: Superseded by [ADR-0016](0016-authenticate-with-cognito-managed-login.md)
- 決定日: 2026-09-21

## 背景と課題

一般ユーザーと管理者の登録・ログインを実装する。認証方式にはパスキー（WebAuthn）を採用したい。
パスワードを保持しないため漏洩時の被害がなく、フィッシング耐性がある。

問題は実装方針である。WebAuthn は登録（Attestation）と認証（Assertion）の 2 つのフローを持ち、
チャレンジの生成と検証、公開鍵の保管、認証器の管理（複数デバイス、紛失時の再登録）を正しく扱う必要がある。
これを自前で実装するか、マネージドサービスに委ねるかで、かかる時間と得られる理解が大きく変わる。

## 判断基準

- 認証という、誤ると被害が大きい領域で、実装の正しさを担保できること
- ユーザー・管理者のロール分離を表現できること
- 本筋であるドメイン実装の時間を圧迫しないこと
- AWS 上の構成に収まり、追加のコストが小さいこと

## 検討した選択肢

### 選択肢 A: Amazon Cognito User Pool のパスキー機能

AWS 内で完結し、Terraform で管理できる。User Pool の Group でロールを表現でき、
発行される JWT を Spring Security で検証すればよい。
認証器の管理・チャレンジの検証は Cognito 側が担う。

### 選択肢 B: webauthn4j による自前実装

WebAuthn の仕様に踏み込んで理解できる。認証器の管理方針やアカウント復旧フローを自分で設計できる。
一方で、セキュリティ上の責任をすべて負う。登録・認証フローに加え、
チャレンジの一意性・有効期限、Origin と RP ID の検証、署名カウンタの扱いなどを正しく実装する必要がある。

### 選択肢 C: Auth0 / Clerk などの外部 SaaS

実装量は最も少なく、管理画面も付属する。ただし AWS 外に依存が増え、
無料枠を超えた場合のコストが読みにくい。Terraform による一元管理からも外れる。

## 決定

**選択肢 A（Cognito のパスキー機能）を採用する。**

- User Pool をひとつ作成し、Group で `user` / `admin` を分離する。
  User Pool を分けない理由は、管理者も同じ認証フローを通るため、
  Pool を分けると設定とインフラが二重になるだけで得るものが少ないため
- バックエンドは発行された JWT を検証し、Group に基づいて認可する
- ユーザー・管理者の属性やスコアなどのアプリケーション固有のデータは、Cognito ではなく自前の DB に持つ。
  Cognito には認証に必要な最小限の情報のみ置き、依存を認証に限定する

### 学習面の扱い

自前実装（選択肢 B）は WebAuthn の理解という点では優れているが、
認証は誤りが直接的な脆弱性になる領域であり、本プロジェクトの主目的ではない。
仕様の理解は次の方法で補う。

- 本 ADR および Phase 3 の実装時に、WebAuthn の登録・認証フローを図解して `docs/architecture/` に残す
- その内容をクイズのコンテンツ（認証認可カテゴリ）として登録する

「マネージドを使ったため理解していない」のではなく、
**仕様を理解した上でマネージドに委ねた**という状態を目指す。

## 結果

### 良い影響

- 認証器の管理、チャレンジ検証、複数デバイス対応を自前で実装せずに済む
- Terraform で認証基盤までコード化でき、環境の再現性が保てる
- JWT の検証は Spring Security の標準機能で完結する

### 悪い影響・受け入れるリスク

- Cognito の仕様上できないことは回避できない。UI やフローのカスタマイズに制約がある
- 認証基盤が AWS に固定される
- ローカル開発時に Cognito へ接続できないと開発が止まる

### 緩和策

- Phase 1 はスタブ認証（ヘッダでロールを切り替える）で実装し、Phase 3 で差し替える。
  このとき、認可の判定をドメイン層に漏らさず、インターフェースの裏に閉じ込める
- ローカル開発では、JWT 検証をスタブに差し替えられる構成にする
- アプリケーション固有のデータを Cognito に置かないことで、移行が必要になった場合の影響を認証部分に限定する

## 検証事項

Phase 3 の着手時に、以下を実装前に確認する。

- パスキー（WebAuthn）の利用に必要な Cognito の機能階層と、その料金体系
- マネージドログイン画面を使うか、自前 UI から API を呼ぶか。自前 UI の場合のパスキー対応可否
- 認証器を紛失した場合の復旧フローとして、何が提供されているか
- Terraform（AWS Provider）でパスキー関連の設定が管理できるか。できない場合の回避策
