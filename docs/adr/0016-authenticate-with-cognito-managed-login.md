# ADR-0016: 認証は Cognito の Managed Login とパスキーで作り、利用者の ID を Cognito から切り離す

- ステータス: Accepted
- 決定日: 2026-09-26
- [ADR-0005](0005-use-cognito-passkeys.md) を置き換える

## 背景と課題

[ADR-0005](0005-use-cognito-passkeys.md) で、認証に Cognito のパスキーを使うと決めた。
Phase 3 に着手するにあたり、次の 2 点が ADR-0005 の時点から変わった。

- **ロールは Cognito の Group ではなく、アプリのデータで持っている。**
  テナントごとに所属とロールが違う（[ADR-0006](0006-row-level-multi-tenancy.md)）ため、Phase 1 で `core.tenant_members` に置いた。
  ADR-0005 の「Group で `user` / `admin` を分離する」は、いまの設計と合わない
- **Cognito で動かしたあと、パスキーを自前で実装して差し替える。** ADR-0005 は、自前実装を目的としないとしていた。
  先に Cognito で動く状態を作り、そのうえで ADR-0005 が悪い影響に挙げた「認証基盤が AWS に固定される」を解く。
  差し替えるなら、そのとき作り直す範囲を、最初の設計で小さくしておく必要がある

あわせて、ADR-0005 が実装前に確かめるとしていた事項を確かめ、構成を具体的に決める。

- 利用者の ID をどう持つか
- ログインの画面を Cognito に任せるか、自分で作るか
- 最初のサインインと、パスキーをなくしたときの復旧に何を使うか
- トークンをどこに置き、どこで検証するか
- 招待をどう届けるか
- ローカル開発とテストで、認証をどう扱うか

## 確かめたこと

ADR-0005 の検証事項への答え。

| 事項 | 結果 |
| --- | --- |
| パスキーに要る機能のプランと料金 | **Essentials 以上。** 月間アクティブユーザー 10,000 人までは無料 |
| Managed Login か、自前の画面から API を呼ぶか | どちらもパスキーに対応する。Managed Login では、登録を勧める画面も Cognito が出す |
| パスキーを登録できる条件 | **一度ほかの方法（パスワードかワンタイムパスワード）でサインインした利用者だけ。** 管理者が作った利用者には、登録は勧められない |
| 認証器をなくしたときの復旧 | ほかの方法でサインインし、新しいパスキーを登録する。専用の復旧の仕組みはない |
| メールのワンタイムパスワード | **Amazon SES の設定が要る。** Cognito の既定のメール（1 日 50 通まで）では送れない。SES は、任意の宛先へ送るのに sandbox の解除の申請が要る |
| RP ID | 既定では Managed Login のドメイン。一度決めて変えると、利用者はパスキーを登録し直す |
| Terraform での管理 | AWS プロバイダ 6.66 で、プラン、サインインの方式、パスキーの設定、Managed Login の見た目まで書ける |

## 判断基準

- 「動かせるアプリ」に早く届くこと。第三者に使ってもらえる状態にする
- 自前実装に差し替えるとき、作り直すのがログインの画面と認証の実装だけで済むこと。回答の履歴と所属が残ること
- トークンがブラウザの JavaScript から読めないこと
- 手作業（Terraform の外の申請など）を増やさないこと
- 追加の費用が小さいこと

## 検討した選択肢

### 最初のサインインと復旧の方法

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **パスワード + パスキー** | Cognito の既定のメールで済み、SES が要らない | パスワードが残る。パスキーを登録しない利用者は、パスワードだけで入れる |
| メールのワンタイムパスワード + パスキー | パスワードを持たない | SES のドメインの検証と、sandbox の解除の申請（AWS の審査）が要る |

### ログインの画面

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **Managed Login** | 登録、パスキーの登録、パスワードの再設定を Cognito が持つ。作る量が最も少ない | 画面の自由度が低い。Cognito のドメインへ移る |
| 自前の画面 + SDK | WebAuthn のブラウザの API を自分で呼ぶので、自前実装に近い | 登録、確認コード、パスキーの登録、再設定の画面をすべて作る。自前実装で作り直す |

自前実装に差し替えるときは、どちらの案でも画面を作り直す。いま作り込む意味は薄い。

### ロールの持ち方

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **アプリのデータ（`core.tenant_members`）** | テナントごとのロールを表せる。認証の方式を替えても変わらない | JWT だけでは認可できず、DB を引く |
| Cognito の Group | JWT に載る | テナントごとのロールを表せない。自前実装で作り直す |

### JWT を検証する場所

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **バックエンド（Spring Security）** | ALB の構成のままで済む。ローカルとテストでも同じ経路を通る | すべての要求がバックエンドまで届く |
| API Gateway のオーソライザー | バックエンドに届く前に落とせる | ALB をやめる（DEV-56）ことが前提になる |

## 決定

### 1. 認証は Cognito の Managed Login で行う

- User Pool は 1 つ。プランは Essentials
- サインインの方式は**パスワードとパスキー**。サインアップのあと、Managed Login がパスキーの登録を勧める
- ドメインは Cognito のプレフィックスドメイン（`*.auth.ap-northeast-1.amazoncognito.com`）。独自ドメインにすると、us-east-1 の証明書が要る
- RP ID はそのプレフィックスドメイン。パスキーは Cognito のドメインで作られ、アプリのドメインとは結び付かない
- 利用者の検証（生体認証や PIN）は「推奨」。必須にすると、対応していない認証器で登録できない
- メールは Cognito の既定の設定で送る。SES は使わない

### 2. 利用者の ID は Cognito から切り離す

- **アプリの利用者の ID は `core.users.id` のまま。** Cognito の `sub` は `external_id` に入れる
- 初めて認証された要求で、利用者を作る。そのとき、確認済みのメールアドレスを Cognito から取り、`core.users` に持つ
- **所属とロールは `core.tenant_members` から引く。** Cognito の Group は使わない
- 自前実装に差し替えるときは、確認済みのメールアドレスで既存の利用者に結び直す。パスキーは Cognito から持ち出せないため、利用者は登録し直す

### 3. トークンはブラウザに渡さない

- Next.js のサーバーが、認可コードフロー（PKCE つき）でトークンを受け取る。アプリのクライアントはシークレットを持つ
- トークンは暗号化して、`HttpOnly` の Cookie に置く。ブラウザの JavaScript からは読めない
- web の proxy（`src/proxy.ts`）が、Cookie からアクセストークンを取り出して `Authorization` に付ける。期限が切れていれば更新する。
  いまの `X-User-Id` を付ける処理を、これに置き換える
- クライアントのシークレットと Cookie の暗号鍵は、秘密のヘッダと同じくビルドの中で `.env.production` に書き出す（[ADR-0012](0012-serve-frontend-on-amplify-hosting.md)）

### 4. JWT はバックエンドで検証する

- Spring Security のリソースサーバーで、署名（JWKS）、発行者、有効期限、`token_use`、`client_id` を確かめる
- `Authenticator` に Cognito 版の実装を足し、スタブ（`StubAuthenticator` と `StubAuthenticatorGuard`）を消す。認可の仕組みは変えない
- API Gateway のオーソライザーは、ALB をやめるとき（DEV-56）にあわせて考える

### 5. 招待はリンクを画面に出して渡す

- 管理者が招待を作ると、招待のリンクが画面に出る。管理者がコピーして相手に渡す。**メールの送信は作らない**
- 招待を受け入れるとき、招待したメールアドレスと、ログインした利用者の確認済みのメールアドレスが一致するかを確かめる。
  リンクが漏れても、別の人は受け入れられない
- サインアップは誰でもできる。所属がなければ、どのテナントのデータも見えない（`/` は「招待を受けていない」と出す）
- 最初の管理者（どのテナントにも管理者がいない状態）は、運用の手順で招待を作って入る

### 6. ローカル開発も dev の User Pool を使う

- ローカルの web のコールバック（`http://localhost:3000`）を、dev のアプリのクライアントに許す
- スタブは残さない。認証の経路を 1 つにする
- テストは、Spring Security のテスト支援で JWT を作って呼ぶ。Cognito には接続しない

### 7. アクセスの制限を見直す

- **画面のベーシック認証は外す。** 誰でもサインアップできるが、データは所属で守られる
- ALB の秘密のヘッダ（`X-Origin-Verify`）は残す。`X-User-Id` でなりすます経路はなくなるが、API を web の proxy 以外から呼ばせない役割は残る。
  ALB をやめる（DEV-56）ときに見直す

## 結果

### 良い影響

- 登録、パスキーの登録、パスワードの再設定の画面を作らずに済む
- 自前実装に差し替えるとき、作り直すのはログインの画面、proxy のトークンの扱い、`Authenticator` の実装だけで済む。回答の履歴と所属は残る
- トークンがブラウザに渡らない。画面のコードは、これまでどおり認証を意識せずに API を呼べる
- SES も独自ドメインの証明書も要らず、Terraform の外の手作業が増えない
- 月間アクティブユーザー 10,000 人までは費用がかからない

### 悪い影響・受け入れるリスク

- **パスワードが残る。** パスキーの登録は勧められるだけで、登録しない利用者はパスワードだけで入れる
- Cognito の既定のメールは 1 日 50 通まで。確認コードとパスワードの再設定が、この範囲に収まる規模に限られる
- ログインのたびに Cognito のドメインへ移る。画面の見た目は Managed Login の範囲でしか変えられない
- ローカル開発も、インターネットにつながっていないとログインできない
- 誰でもサインアップできるため、所属のない利用者が増えうる
- 自前実装に差し替えると、登録済みのパスキーは使えなくなる

### 緩和策

- パスワードの条件は Cognito の既定より強くする。メールのワンタイムパスワードに移るときは、SES を用意して方式を足す
- 所属のない利用者は、データに触れない。数が問題になったら、サインアップの前に招待を確かめる（Lambda のトリガー）ことを考える

## 検証事項

- Managed Login で、サインアップからパスキーの登録、パスキーでのサインインまでが、主なブラウザ（Chrome、Safari）と iPhone で通るか
- アクセストークンで取れる情報（確認済みのメールアドレス）を、バックエンドからどう取るか（`GetUser` を呼ぶか、トークンに載せるか）
- 暗号化したトークンが Cookie の大きさの上限（4 KB）に収まるか。収まらなければ分けるか、リフレッシュトークンだけを置く
- Amplify の SSR から Cognito のトークンのエンドポイントへ届き、更新が間に合うか
