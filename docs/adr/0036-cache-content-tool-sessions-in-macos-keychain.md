# ADR-0036: コンテンツ投入用のログイン状態をmacOSキーチェーンに保存する

- ステータス: Accepted
- 決定日: 2026-10-31

## 背景と課題

[ADR-0034](0034-keep-quiz-content-as-packs-and-load-through-api.md)の投入ツールは、実行するたびに管理者のパスワードを入力してアクセストークンを取得する。devとprodは別のUser Poolで、両方に投入すると入力も2回必要になる。

APIキーのように保存した認証情報を使い回せるようにし、コンテンツの更新のたびにログインする手間を減らす。見直すのはADR-0034のトークンの保管方法だけで、投入APIとテナントの権限判定は維持する。

## 判断基準

- パスワードを保存せず、2回目以降の入力を省けること
- devとprodの認証情報と接続先を混同しないこと
- 管理者の所属とロールをアプリで確認し続けること
- 秘密をリポジトリ、平文の設定ファイル、コマンドの引数、ログに残さないこと

## 検討した選択肢

| 選択肢 | 利点 | 欠点 |
| --- | --- | --- |
| **Cognitoの更新トークンをOSのキーチェーンに保存する（採用）** | マネージドの認証を再利用でき、APIやDBを変更しない。期限と失効をCognitoに任せられる | 現在の期限は初回ログインから30日。OSの保管先を使うため、今回の実装はmacOS向け |
| テナント単位のAPIキーを自前実装する | 期限、操作範囲、発行者、監査を用途に合わせて設計できる | 発行・ハッシュ保管・照合・失効・権限確認・管理画面を持つ必要がある |
| パスワードを保存して毎回ログインする | 認証APIは今のまま使える | 保存する秘密がアカウントのパスワードになり、セッション単位で失効できない |

## 決定

`auth.ts login`でCognitoに一度ログインし、アクセストークンと更新トークンをmacOSのログインキーチェーンに保存する。パスワードは入力時だけメモリ上で扱う。Cognitoの既存の公開クライアント（`auth_mobile_client_id`）を使う。

プロファイル名をキーにし、認証情報とAPIの接続先を一緒に保存する。`load.ts --profile dev`のように指定すると、有効なアクセストークンを使い、期限が近ければ`GetTokensFromRefreshToken`で更新する。`--profile`と`--api` / `ACCESS_TOKEN`の併用は拒否する。

更新トークンが期限切れ・失効していれば、そのプロファイルを削除して再ログインを求める。通信の失敗、流量制限、サーバーエラーでは状態を残す。ログアウトはCognitoで更新トークンを失効させてからキーチェーンの項目を消し、通信に失敗した場合は再試行できるよう残す。

キーチェーンへの入出力は小さなSwiftツールでSecurity APIを呼び、Nodeとの間ではstdin / stdoutのパイプだけで秘密を渡す。生成する実行ファイルとコンパイルキャッシュは無視対象の`tools/content/tmp/`に置き、秘密を含めない。既存の`ACCESS_TOKEN`方式はCIやmacOS以外からの利用向けに残す。

## 結果

### 良い影響

- 日々の投入ではパスワードの入力とトークンのコピーが不要になる
- サーバーの認証経路と権限を増やさず、Cognitoのセッションを利用できる

### 悪い影響・受け入れるリスク

- キーチェーンを読める権限を奪われると、保存したトークンを使われる可能性がある
- トークンはその利用者の権限を持つ。コンテンツ投入だけに限定したAPIキーではない
- 更新トークンの期限はログインから30日で、更新しても延長されない。パスワード入力が永久に不要になるわけではない
- ログアウト後も、署名と期限だけを確認するAPIでは発行済みアクセストークンが最大1時間有効になりうる
- 初回の実行にはXcode Command Line Toolsが必要。macOSがキーチェーンのアクセス許可を求める場合がある

### 緩和策

- 環境ごとにプロファイルを分け、保存した接続先だけにアクセストークンを渡す
- 状態表示にはトークンを出さず、エラーにも外部応答や子プロセスの出力をそのまま載せない
- キーチェーン項目を全アプリに許可する設定や、iCloud同期の設定を追加しない

## 検証

- トークンの有効期間、自動更新、更新トークンの入れ替え、環境の分離、失効、通信失敗時の状態維持を単体テストで確かめる
- macOSではダミーデータを使い、キーチェーンへの保存・別プロセスでの読出し・更新・削除を確かめる
- 実際の管理者で初回登録したあと、パスワードを再入力せずにdry-runできることを確かめる
