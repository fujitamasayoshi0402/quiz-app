# ADR-0024: 公開テナントには、ログインした人が承認なしで自分で参加する。一覧と参加の API はテナントの外の `/api/me` に置く

- ステータス: Accepted
- 決定日: 2026-10-02

## 背景と課題

[ADR-0006](0006-row-level-multi-tenancy.md) は、テナントに `private` / `public` の公開設定を持たせた。
いまは `private` だけを扱い、テナントへの所属は管理者の招待でしか増えない（[要件定義の招待フロー](../requirements.md#招待フローphase-3)）。
`public` のテナントを、招待なしで見つけて参加できるようにする。

決めること。

- **参加の仕方。** 誰でも自分で参加できるか。管理者の承認を挟むか。参加した人のロール
- **見える範囲。** ログインしていない相手に、公開テナントの一覧やクイズを見せるか
- **非公開に戻したとき。** 招待なしで参加した人をどうするか
- **テナントの境界。** 一覧と参加の API は、どのテナントにも所属していない人が呼ぶ。テナント配下（`/api/t/{slug}/...`）には置けない

いまの境界は次のとおり。

- `/api` の下は、例外なく認証を要求する。認証していない相手には、テナントがあってもなくても同じ 401 を返す
- テナント配下の API は、パスで「所属しているか」「管理者か」を判定する（`TenantAccessInterceptor`）。既定が「所属が必要」
- テナントの外に置く API は `/api/me` だけで、`TenantBoundaryApiTest` の許可リストに理由とともに載る（所属の一覧、招待の確認と受け入れ）
- テナント配下の表は、行レベルセキュリティ（RLS）で `app.tenant_id` のテナントの行しか返さない

## 判断基準

- **テナントの境界を広げすぎないこと。** テナントの外の API は、増やすほど境界の外が広がる（開発ガイドライン「API の URL」）
- 公開テナントでも、クイズを読む経路は所属したあとのいまの経路だけにする。RLS とテナント配下の判定を、公開のために緩めない
- 招待と自分での参加を、同じ所属の仕組み（`core.tenant_members`）に乗せる
- 作る量を抑える。デモで見せたいのは「見つけて、参加して、解ける」ことで、参加の管理の作り込みではない

## 検討した選択肢

### 参加の仕方

#### A. ログインした人が、承認なしで自分で参加する（ロールは一般ユーザー）

一覧から「参加する」を押すと、一般ユーザーとして所属する。

- 利点: 所属の行を 1 つ足すだけで済む。招待の受け入れと同じ仕組みに乗る
- 欠点: 管理者は、誰が入ってくるかを選べない

#### B. 参加を申請し、管理者が承認する

- 利点: 管理者が参加者を選べる
- 欠点: 申請の状態（待ち・承認・却下）の表と、管理者の承認の画面が要る。承認されるまで解けないため、見に来た人がすぐに試せない

### 見える範囲

#### A. 一覧も参加も、ログインした人だけ

- 利点: 「`/api` の下はすべて認証が要る」という決まりを崩さない。認証の検査（`AuthenticationRequiredInterceptor`）に例外を作らない
- 欠点: 見に来た人は、ログインしてからでないと何があるかが分からない

#### B. 一覧だけ、ログインしていなくても見せる

- 利点: ログインの前に中身を想像できる
- 欠点: 認証の要らない API を初めて作ることになる。パスで認証を要求する仕組みに穴を開け、その穴が広がらないことを別に確かめ続ける必要がある

### 非公開に戻したとき

#### A. 参加した人を残す

- 利点: 所属を経路（招待か、自分での参加か）で区別しない。新しく参加できなくなるだけで、表も処理も増えない
- 欠点: 公開していた間に入った人を外すには、別の手段が要る

#### B. 招待なしで参加した人を外す

- 利点: 非公開に戻すと、招待した人だけの状態に戻る
- 欠点: 所属に経路の列が要り、戻したときに外す処理と、外された人の挑戦や履歴の扱いを決める必要がある。公開と非公開を切り替えるたびに、所属が増えたり減ったりする

## 決定

**参加は A（承認なし、一般ユーザー）、見える範囲は A（ログインした人だけ）、非公開に戻したときは A（残す）を採用する。**

### API

| API | 中身 |
| --- | --- |
| `GET /api/me/public-tenants` | 公開テナントの一覧。名前、slug、自分が参加済みか |
| `POST /api/me/public-tenants/{slug}/join` | 一般ユーザーとして所属する |
| `GET` / `PUT /api/t/{slug}/admin/settings` | 公開設定を読む・変える。テナント配下の管理者の API |

- 一覧と参加は、テナントの外の `/api/me` に置く。どのテナントにも所属していない人が呼ぶため、テナント配下には置けない。
  `TenantBoundaryApiTest` の許可リストに理由とともに載せ、境界は専用のテストで確かめる（所属の一覧の `MyTenantsApiTest` と同じ扱い）
- 一覧と参加が読むのは、RLS の対象外の `core`（`tenants`、`tenant_members`）だけ。カテゴリやクイズは返さない
- **非公開のテナントと、存在しないテナントは、参加で同じ 404 を返す。** 非公開のテナントがあることを明かさない
- すでに所属していれば、参加しても何も変えない。管理者が参加を押しても、ロールは一般ユーザーに下がらない
- 公開設定の切り替えは、テナント配下の管理者の API に置く。いまの判定（パスの `admin`）がそのまま効き、許可リストは増えない

### クイズを読む経路は変えない

公開テナントのクイズも、所属してからいまの出題の API（`/api/t/{slug}/play/...`）で読む。
公開であることを理由に、所属していない人にテナント配下の API を開けない。
ADR-0006 は「公開機能を追加するときの変更は、認可の判定に条件を 1 つ足すことに限定される」としていたが、
条件を足すのは所属の判定ではなく、**所属を作る入口（参加の API）**にした。判定そのものは変えない。

## 結果

### 良い影響

- 境界の外に足すのは、`core` だけを読み書きする 2 つの API に限られる。テナント配下の判定と RLS は変わらない
- 招待で入った人と自分で入った人が、同じ所属として扱われる。画面も API も区別しない
- 見に来た人が、招待を待たずにデモのテナントで試せる

### 悪い影響・受け入れるリスク

- **公開テナントには、アカウントを作れる人なら誰でも入れる。** Cognito のサインアップは誰にでも開いている（[ADR-0016](0016-authenticate-with-cognito-managed-login.md)）。
  公開テナントのクイズと解説は、実質的に公開された情報として扱う
- **管理者は、参加した人を画面から外せない。** 所属を外す機能は、まだない。困る参加者が出たときは、非公開に戻して新しい参加を止め、
  所属は Data API で外す（運用の手順）
- 一覧は、ログインしてからでないと見られない。デモでは、共有のデモのアカウント（`demo@example.com`）でログインしてもらう

### 緩和策

- 公開設定の画面で、`public` にすると誰でも一般ユーザーとして参加できることを、切り替える前に示す
- 一覧と参加の API は、許可リストに理由を残し、専用のテストで「非公開のテナントは一覧に出ず、参加できない」「既存の所属のロールを変えない」を確かめる
- ランキングに載るのは、参加を選んで名前を決めた人だけ（いまのまま）。公開テナントに入っただけでは、名前は誰にも見えない

## 検証事項

- 公開テナントの一覧は、`core.tenants` を公開設定で絞って読む。テナントは数件のため、いまは索引を足さない。
  ADR-0006 の「公開テナントを横断して検索する際のインデックス設計」は、テナントの名前やクイズを横断して探す機能を作るときに見直す
- 参加した人を外す機能が要るかは、公開テナントを使い始めてから決める
