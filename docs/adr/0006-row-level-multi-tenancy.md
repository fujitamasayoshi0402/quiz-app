# ADR-0006: マルチテナントをロウ単位の分離で実現する

- ステータス: Accepted
- 決定日: 2026-09-22

## 背景と課題

本アプリは、管理者ごとに独立したクイズ空間を持つ。
管理者 A が作ったクイズ空間には A が登録したカテゴリとクイズだけが存在し、管理者 B のそれとは互いに見えない。
以降、この空間の単位を **テナント** と呼ぶ。

将来的には、テナント単位で「所属していない人でも解ける」公開設定を提供したい。
ただし最初に必要なのは閉じた利用のほうであり、公開機能は後から追加する。

この決定を先送りできない理由は、テナント識別子がほぼすべてのテーブルに影響するためである。
DB 設計の後に方式を変えると、スキーマ変更に加えて既存データの移行が必要になる。
一方、この段階ではまだテーブルが 1 つも存在しないため、いま決めれば追加コストはゼロである。

制約は次のとおり。

- Aurora PostgreSQL Serverless v2 を 1 台、min 0 ACU で運用する（[コスト方針](../development-guidelines.md#8-コスト方針)）
- 管理者は招待制で増えるため、テナント数は当面少数にとどまる
- **テナント境界を越えた参照は、機能不全ではなく情報漏洩である**。他の障害とは扱いが異なる

## 判断基準

- テナント境界を越えた参照が、規律ではなく構造によって防がれること
- 運用コストがテナント数に比例して増えないこと
- 後から「テナント単位の公開」を追加できること
- 個人で運用しきれる複雑さに収まること

## 検討した選択肢

### 選択肢 A: テナントごとに DB を分ける

分離としては最も強く、取り違えが起こり得ない。
しかしテナントを増やすたびに DB インスタンスまたは接続先が増え、コストがテナント数に比例する。
マイグレーションも全 DB に適用する必要があり、1 台の Aurora を min 0 ACU で運用する方針と両立しない。

### 選択肢 B: テナントごとに PostgreSQL スキーマを分ける

DB は 1 台で済むため、コストは A ほど増えない。
ただしテナント追加のたびにスキーマ作成と Flyway の適用が必要になり、テナント数に比例して実行時間が伸びる。

より問題なのは、[ADR-0004](0004-split-services-incrementally.md) でスキーマを**サービス境界**の表現として使っていることである。
ここでスキーマをテナント境界にも使うと、`quiz` / `answer` というサービス境界と、
テナントごとの境界が同じ仕組みの上で交差する。将来サービスを分割する際、
どちらの軸で分かれているのかが読み取りにくくなる。

### 選択肢 C: 単一スキーマ + `tenant_id` 列によるロウ単位の分離

全テーブルに `tenant_id` を持たせ、クエリで絞り込む。
テナント追加はロウの挿入のみで完結し、マイグレーションは 1 回で済む。
スキーマはサービス境界の表現として残るため、ADR-0004 と衝突しない。

代償として、**`WHERE tenant_id = ?` の書き漏れがそのまま情報漏洩になる**。
分離がアプリケーションコードの正しさに依存する点が、A・B との決定的な違いである。

## 決定

**選択肢 C を採用する。ただし分離をアプリケーションコードだけに委ねず、PostgreSQL の行レベルセキュリティ（RLS）を併用する。**

### データモデル

- テナント配下のすべてのテーブルに `tenant_id` を持たせる
- `tenants`: テナント本体。`slug`（URL 用）、`name`、`visibility` を持つ
- `tenant_members`: ユーザーのテナント所属。ロール（管理者 / 一般ユーザー）もここで持つ

### 公開範囲

`visibility` は `private` / `public` の 2 値とし、**テナント単位**で持つ。
「管理者 A のクイズアプリ」という括りがそのまま公開単位になるため、利用者にとっての意味が明快である。
カテゴリ単位やクイズ単位の公開は柔軟だが、認可の判定が組み合わせで増える割に用途が想像しにくい。

Phase 1〜3 では `private` のみを扱い、`public` の導線は作らない。
カラムと判定の分岐点だけを先に用意しておく。

### 認可

「そのユーザーがテナントのメンバーか」ではなく、**「そのユーザーがこのクイズにアクセスできるか」**という問いに集約する。
公開機能を追加するときの変更は、この判定の中に条件を 1 つ足すことに限定される。

### テナントの識別

URL のパスで表現する（`/t/{slug}/...`）。
サブドメイン方式は分離が明快だが、ワイルドカード証明書と DNS の設定が増え、dev 環境の構築も重くなる。
パス方式なら追加のインフラコストが発生しない。

### 管理者の増やし方

招待制とする。既存の管理者が招待したメールアドレスのみが管理者になれる。
セルフサービス登録は、スパム対策と 1 テナントあたりのリソース上限の設計が必要になり、
個人で運用する規模に対して割に合わない。

## 結果

### 良い影響

- テナントの追加がロウの挿入だけで完結し、運用コストが増えない
- マイグレーションの対象が常に 1 つで、テナント数に依存しない
- 公開機能の追加が、認可判定への条件追加で済む
- スキーマがサービス境界の表現のまま残り、ADR-0004 の方針と整合する

### 悪い影響・受け入れるリスク

- **絞り込みの書き漏れが情報漏洩に直結する。** 通常のバグより影響が大きい
- RLS を使う場合、接続ごとにセッション変数でテナントを設定する必要がある。
  コネクションプールは接続を使い回すため、**前のリクエストのテナントが残ると別テナントのデータが見える**
- 全テナントのデータが同じテーブルに入るため、特定テナントのデータ削除やエクスポートが
  テーブル単位の操作ではなく条件付きの操作になる

### 緩和策

- テナント配下のテーブルすべてに RLS ポリシーを設定する。
  アプリケーション側で絞り込みを書き漏らしても、DB が行を返さない状態にする
- リポジトリ層の共通機構でテナントを条件に含める。個々の実装者の記憶に依存させない
- 接続をプールへ返却する際にセッション変数をリセットする
- 統合テストで「別テナントの ID を指定したアクセスが結果を返さないこと」を検証する。
  この検証は機能テストではなくセキュリティテストとして、テナント配下の全エンドポイントに対して行う

## 検証事項

- HikariCP と RLS のセッション変数の組み合わせ。接続の使い回しで前のテナントの値が残らないこと（Phase 1 で確認する）
- min 0 ACU からの復帰時に、セッション変数の設定が確実に行われること
- 公開テナントを横断して検索する際のインデックス設計。`tenant_id` が先頭にある複合インデックスは横断検索で効かないため、
  公開機能を追加する時点で再検討が必要になる
- テナントあたりのデータ量が偏った場合のクエリプラン。少数の巨大テナントと多数の小規模テナントが混在したときの挙動
