# ADR-0028: ログインした人が、自分のテナントを 1 つ作れるようにする。作ったテナントは非公開に限り、量に上限を掛ける

- ステータス: Accepted
- 決定日: 2026-10-10

## 背景と課題

テナントは、シードと運用の手順（最初の管理者の事前登録。開発ガイドライン「最初の管理者」）でしか作れない。
要件定義の未確定事項にも「テナントの作成方法」が残っている。

見に来た人は、デモのテナントの一般ユーザーにしかなれない（共有のデモのアカウント、公開テナントへの参加。[ADR-0025](0025-let-signed-in-users-join-public-tenants.md)）。
クイズの作成、draw.io の図、取り込み、招待といった管理の画面には触れられない。

ログインした人が自分のテナントを作り、その管理者になれるようにする。決めること。

- **誰が作れるか。** ログインした人すべてか。共有のデモのアカウント（パスワードを公開している）も含めるか
- **量の上限。** Cognito のサインアップは誰にでも開いている（[ADR-0016](0016-authenticate-with-cognito-managed-login.md)）。上限がなければ、S3 と DB の費用にも上限がなくなる
- **公開できるか。** 公開テナントは、ログインした全員の一覧に名前が出て、誰でも参加できる
- **作った直後の中身と、テナントの消し方**
- **テナントの境界。** 作る人は、まだそのテナントに所属していない。テナント配下（`/api/t/{slug}/...`）には置けない

## 判断基準

- **費用に上限があること。** 個人で運用する規模で、予算は月 30 ドル（開発ガイドライン「コスト方針」）
- **見知らぬ人が作ったものを、ほかの人に見せないこと。** 中身を見張る運用は持たない
- テナントの境界を広げすぎないこと。テナントの外の API は、増やすほど境界の外が広がる（開発ガイドライン「API の URL」）
- 作る量を抑える。見せたいのは「自分のテナントで、管理の画面を一通り触れる」ことで、テナントの運用の作り込みではない

## 検討した選択肢

### 誰が作れるか

#### A. ログインした人。共有のアカウントは除く

- 利点: 見に来た人が、サインアップすればすぐに試せる
- 欠点: 共有のアカウントを見分ける印が要る

#### B. ログインした人すべて（共有のデモのアカウントを含む）

- 利点: サインアップせずに管理を試せる
- 欠点: 共有のアカウントで作ったテナントは、パスワードを知る全員の共有の管理画面になる。最初の 1 人が数の上限を使い切り、ほかの人が書いたものを全員が見る。作り直す仕組みも要る

#### C. 運用者が許した人だけ（申請）

- 利点: 誰が作るかを選べる
- 欠点: 申請の状態と、許す手順が要る。許されるまで試せない

### 量の上限

#### A. 利用者が作ったテナントにだけ、数と量の上限を掛ける

1 人が作れるテナントの数と、テナントのクイズと図の数に上限を掛ける。運用者が作ったテナント（デモなど）には掛けない。

- 利点: 1 人が使える量に上限がつく。デモのテナントの使い方は変わらない
- 欠点: クイズと図を作る API に、数を確かめる処理が加わる

#### B. 上限を設けない

- 利点: 作るものが少ない
- 欠点: 流量の上限（DEV-125）は時間あたりの量しか抑えない。時間をかければ、いくらでも置ける

### 公開できるか

#### A. 利用者が作ったテナントは、非公開に限る

- 利点: 見知らぬ人が付けた名前や書いた中身が、ほかの人に見えない。所属できるのは、作った人が招待した人だけ
- 欠点: 公開の切り替え（DEV-129）は、画面を見られても試せない

#### B. 公開できる

- 利点: 管理の機能を残らず試せる
- 欠点: 公開テナントの一覧が試しのテナントで埋まり、不適切な名前や中身もほかの人に見える。見張る運用が要る

### 作った直後の中身

#### A. 空にする

- 利点: 作る処理がテナントと所属の 2 行で済む。上限の数え方も素直になる
- 欠点: 解けるようになるまでに、カテゴリ、難易度、クイズを作る手間がある

#### B. 見本のカテゴリ、難易度、クイズを入れる

- 利点: 作ってすぐに解ける
- 欠点: 見本の中身を持ち続け、作るたびに写す処理が要る

## 決定

**作れる人は A（共有のアカウントを除くログインした人）、量の上限は A（利用者が作ったテナントにだけ）、公開は A（非公開に限る）、作った直後は A（空）を採用する。**

| 項目 | 決めたこと |
| --- | --- |
| 作れる人 | ログインした人。共有のアカウント（`demo@example.com`）は作れない |
| 作れる数 | 1 人 1 つ。作ったテナントが残っている間は、新しく作れない |
| テナントの上限 | クイズ 100（ゴミ箱のものを含む）、図 50。利用者が作ったテナントにだけ掛ける |
| 公開設定 | 非公開のまま。公開への切り替えを拒む |
| slug と名前 | 作る人が決める。slug の形式は、いまの DB の制約（小文字・数字・ハイフン、3〜32 文字）。ほかと重なれば作れない |
| 作った人 | そのテナントの管理者として所属する |
| 作った直後 | 空。カテゴリもクイズもない |
| 消す | 今回は作らない |

### データ

- `core.tenants` に、作った人（`created_by`）を足す。運用者が作ったテナントは空のまま。**空でないことが「利用者が作ったテナント」の印になる**
- 1 人 1 つは、`created_by` の部分一意索引（削除されていないもの）で DB に守らせる。同時に 2 つ作る要求が来ても、片方は失敗する
- クイズと図の上限は、`core.tenants` の列に作るときに入れる（空なら上限なし）。数値を変えるのは、運用者が列を書き換えるだけで済む
- 共有のアカウントは、`core.users` の印で見分ける。シードが付ける。メールアドレスをコードに書かない

### API

| API | 中身 |
| --- | --- |
| `GET /api/me/tenant-creation` | 作れるかどうかと、作れない理由（共有のアカウント、すでに作った） |
| `POST /api/me/tenants` | テナントを作り、作った人を管理者として所属させる。応答は所属の一覧と同じ形 |

- どちらも、テナントの外の `/api/me` に置く。作る人はまだ所属していないため。`TenantBoundaryApiTest` の許可リストに理由とともに載せる
- 読み書きするのは、RLS の対象外の `core`（`tenants`、`tenant_members`、`users`）だけ
- 作る API は重い操作（`@HeavyOperation`）にする。利用者ごとの流量の上限が、ほかの操作より厳しく掛かる
- slug が重なったときは 409 を返す。削除されていないテナントと重なるかだけを見る。非公開のテナントの slug があることは、この応答で分かってしまうが、slug は URL に出るもので、中身は見えない
- クイズと図の上限は、作る API（クイズの作成と取り込み、draw.io の図の作成、画像と PDF のアップロードの完了）で確かめる。超えたら 409 と理由を返す。
  クイズはゴミ箱のものも数えるため、復活では確かめない。
  **数えてから入れるため、同時に来た要求で数件超えることは許す。** 費用に上限を付けるのが目的で、厳密な数は求めない

### 公開設定

- 利用者が作ったテナントは、公開設定の API が `public` への切り替えを拒む（409）。設定の画面は見られるが、切り替えは理由とともに止める
- 運用者が作ったテナントの扱いは変えない

## 結果

### 良い影響

- 見に来た人が、自分のテナントで管理の画面を一通り触れる（公開の切り替えを除く）
- 1 人が使える量に上限がつく。最悪でも、図 50 個（1 つ最大 20 MB）で 1 テナント 1 GB ほど
- 要件定義の未確定事項「テナントの作成方法」が埋まる。最初の管理者の事前登録は、運用者がテナントを作るときの手順として残る

### 悪い影響・受け入れるリスク

- **使われなくなったテナントが残り続ける。** 消す機能も、放置されたものを片付ける仕組みもない。1 人 1 つのため、増え方はサインアップした人の数までに収まる
- **作ったテナントを消して作り直すことができない。** 試し直したい人は、中身を自分で消す
- 共有のデモのアカウントでは管理を試せない。サインアップ（メールアドレスの確認）を求める
- 作ったテナントに招待した人も、上限の中で使う

### 緩和策

- 作る画面で、作れない理由（共有のアカウント、すでに作った）を先に示す。押してから失敗させない
- 上限に達したときは、何が上限に達したかを画面に出す

## 検証事項

- 放置されたテナントを片付ける仕組み（最後に使われた日で消す、など）は、作られた数を見てから決める
- 利用者が作ったテナントを公開したくなったときの手順（運用者が許す、など）は、求められてから決める
- 上限の数値（クイズ 100、図 50）は、使われ方を見て見直す
