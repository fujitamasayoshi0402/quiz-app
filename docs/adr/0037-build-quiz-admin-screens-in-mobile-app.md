# ADR-0037: モバイルアプリに、クイズの管理の画面だけを作る。ほかの管理は web に任せる

- ステータス: Accepted
- 決定日: 2026-11-05

## 背景と課題

[ADR-0032](0032-build-mobile-app-with-expo-and-sign-in-through-system-browser.md) で、アプリには一般ユーザーの画面だけを作り、管理の画面は作らないと決めた。
その後 DEV-215 で、管理者に web の管理画面を開くボタンを足した（ADR-0032 の追記）。

自分の端末にアプリを入れて使うと（DEV-210）、アプリでもクイズを編集したくなった。
ボタンで web へ移ると、ブラウザでのログインが別に要り、アプリを行き来することになる。

web の管理画面は広い。クイズのほか、カテゴリと難易度、draw.io の図、画像と PDF、招待、通知の設定、取り込みがある。決めることは次のとおり。

- **どこまで作るか**
- **誰に入口を出すか**
- **web と同じ規則（生成した Zod スキーマ、公開の条件）をどう揃えるか**

## 判断基準

- 認可はバックエンドのままにする。画面の出し分けは見た目のため（ADR-0032 の追記、DEV-215 と同じ）
- アプリでしたいこと（クイズを作る、直す、公開する）を先に満たす
- API を増やさない。いまの管理の API をそのまま使う
- 依存を増やしすぎない。アプリの配布と版の更新の手間を増やさない

## 検討した選択肢

### どこまで作るか

#### A. クイズだけ（一覧、絞り込み、削除、作成、編集、公開）

- 利点: アプリでしたいことを満たし、1 週間ほどで作れる。入らないものは、いまのボタンで web を開ける
- 欠点: 新しいカテゴリや図が要る題材は、web で準備することになる

#### B. A に、画像と PDF を端末から上げる機能を足す

- 利点: 写真を解説図にできる
- 欠点: 数日増える。端末のファイルの権限と、S3 への直接の送信を作る

#### C. A に、カテゴリと難易度の作成と編集を足す

- 利点: 新しい題材をアプリだけで始められる
- 欠点: 数日増える。端末で新しい題材を一から始めることは多くない

#### D. web の管理画面をすべて作る

- 利点: アプリだけで完結する
- 欠点: draw.io は WebView に `embed.diagrams.net` を埋め込むことになり、いちばん重い。1〜2 週間を超える

### 誰に入口を出すか

#### A. 管理者（`admin`）だけ

- 利点: DEV-215 のボタンと同じ条件で、説明が 1 つで済む
- 欠点: 見学者（`viewer`、[ADR-0035](0035-let-shared-demo-account-view-admin-screens-read-only.md)）は、アプリでは管理の画面を見られない

#### B. 管理者と見学者

- 利点: web の管理画面と同じ
- 欠点: 見学中である旨の案内を、アプリにも作ることになる。見学者のデモのアカウントは、アプリに入口がない（ADR-0032）

### 規則の揃え方

#### A. web の `lib/admin/quiz-form.ts` などを、アプリに写す

生成物はアプリごとに作る（ADR-0032）。写した先も、アプリの生成物を土台にする。

- 利点: すでにある形（`lib/wake.ts`、`lib/slow-requests.ts`）と同じ。文字数の上限などは定義から来るので、作り直しで追従する
- 欠点: 定義に表れない規則（公開の条件）が 2 か所になり、片方だけ直すおそれがある

#### B. 共有のパッケージに切り出す

- 利点: 規則が 1 か所になる
- 欠点: 土台の生成物もアプリごとなので、共有するには生成物の扱いから変えることになる。規則は 40 行ほどで、切り出す費用に合わない

## 決定

**どこまで作るかは A（クイズだけ）、入口は A（管理者だけ）、規則は A（アプリに写す）を採用する。**

| 項目 | 決めたこと |
| --- | --- |
| 作るもの | クイズの一覧、絞り込み（カテゴリ、難易度、状態、作成元）、正答率の低い順、削除、作成、編集、下書きと公開 |
| 作らないもの | カテゴリと難易度の作成と編集、解説図の作成と選択、削除済み一覧からの復活、招待、通知の設定、取り込み |
| web のボタン | 残す。作らないものは web で行う |
| 入口 | テナントのトップに、管理者だけ「クイズを管理する」を出す。ロールは `/api/me/tenants` から取る |
| 解説の `figure:` | 文字のまま編集でき、保存しても壊さない。図を選んだり足したりはしない |
| 規則 | web の `lib/admin/` のうち要るものをアプリの `lib/admin/` に写す。最終的な判定はバックエンド |

この決定は、ADR-0032 の決定の表の「置き場所」にある「管理の画面は作らない」を置き換える。

## 結果

### 良い影響

- クイズを、アプリを離れずに作り、直せる
- バックエンドと API は変わらない

### 悪い影響・受け入れるリスク

- **公開の条件などが web とアプリの 2 か所になる。** 片方だけ直すと、画面の案内が分かれる。バックエンドが最終的に判定するので、不正なクイズは保存されない
- 管理の画面を足すたびに、web とアプリのどちらに作るかを考えることになる
- 画面の部品はテストの枠組みがなく、判定だけをテストする。見た目は実機で確かめる

### 緩和策

- 写したファイルの先頭に、写し元を書く
- 作らないものは、web のボタンで開ける

## 検証事項

- 端末で本当に編集するか。使わなければ、作成と編集（DEV-227）の優先を下げる
- 解説の Markdown を端末で書けるか。下見がなくても足りるか
- クイズが 300 問あるテナントで、一覧が重くならないか
