# ADR-0027: パスキーを自前で実装するときの設計を決め、いまは Cognito を使い続ける

- ステータス: Accepted
- 決定日: 2026-10-07
- [ADR-0016](0016-authenticate-with-cognito-managed-login.md) の「Cognito で動かしたあと、パスキーを自前で実装して差し替える」を見直す

## 背景と課題

ADR-0016 は、Cognito で一通り動かしたあと、パスキーを自前で実装して差し替えるとしていた。
悪い影響に挙げた「認証基盤が AWS に固定される」を解き、マネージドのサービスが隠している部分（WebAuthn の登録と認証の検証）を理解するため。

Cognito での認証（登録、ログイン、招待、スタブの撤去）は動いている。差し替えに入る前に、次の 2 つを決める。

1. 自前で作るなら、どう作るか。チャレンジ、クレデンシャル、セッション、メールの確認、復旧、移り方
2. いま差し替えるか

## 判断基準

- 利用者から見て、得るものがあること。画面とログインの体験が良くなるか
- 認証の安全性の責任を、どこまで自分で持つか。持つなら、それを確かめる手段があるか
- 手作業（Terraform の外の申請）と費用を増やさないこと
- いまの境界を保つこと。web の proxy だけが `Authorization` を付け、トークンはブラウザに渡らない（ADR-0016）。
  アプリの利用者の ID は認証基盤から独立している
- スモークテストと E2E が、人の操作なしにログインできること

## 自前で作るときの設計

差し替えるかどうかとは別に、作るならこうする、を先に決めておく。DEV-120〜122 は、この設計から始める。

### 検証は quiz-service で行い、部品は Spring Security の `webAuthn()` を使う

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **quiz-service で、Spring Security の `webAuthn()`（中は webauthn4j）** | 検証の中身（署名、オリジン、RP ID、カウンタ）は webauthn4j が持つ。FIDO2 の適合性が確かめられた部品で、Keycloak も使う。クレデンシャルを DB に置ける | Spring Security のフィルタを前に立てていない（ADR-0016 の 4）。既定のチャレンジの置き場所が HttpSession で、そのままでは使えない |
| quiz-service で、webauthn4j を直接使う | 要求の流れを自分で書けるので、いまのインターセプタの作りに合わせやすい | 登録と認証の手順（オプションを作る、チャレンジを照合する）を自分で書く |
| web（Next.js）で、SimpleWebAuthn を使う | ブラウザに近いところで完結する | web は DB を持たない。クレデンシャルを読み書きするたびに quiz-service を呼ぶ。認証が 2 か所に分かれる |

**webauthn4j を直接使う。** `webAuthn()` は、既定でチャレンジとログインの結果を HttpSession に置く。いまの「web の proxy がトークンを付け、quiz-service はステートレス」に合わない。
チャレンジの置き場所とセッションの発行を差し替えると、使うのは検証の部品だけになる。それなら webauthn4j を直接呼ぶほうが、何をしているかがコードに表れる。
検証そのもの（`WebAuthnManager`）は webauthn4j に任せ、自分では書かない。

### チャレンジは DB に置き、1 回で消す

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **DB（`core.webauthn_challenges`）** | 使った時点で消せるので、同じチャレンジを 2 回使えない。タスクが 2 つあっても同じものを見る | ログインの開始のたびに書く |
| 暗号化した Cookie | 書き込みがない | 期限の間は何度でも出せる。使い回しを防ぐには、結局どこかに使った記録が要る |

- チャレンジは 32 バイトの乱数。期限は 5 分。認証に成功しても失敗しても、照合した時点で消す
- 目的（登録か認証か）と、登録なら利用者の ID を一緒に持つ。別の目的に流用させない
- ログインは利用者の操作なので、DB を使っても Aurora の一時停止は妨げない（DB を起こすのは、もともと利用者の要求）

### クレデンシャルは `core.passkeys` に置く

```
core.passkeys
  id               uuid（主キー）
  user_id          uuid（core.users）
  credential_id    bytea（一意）
  public_key       bytea（COSE）
  sign_count       bigint
  transports       text[]
  aaguid           uuid
  name             text（利用者が付ける名前。「iPhone」など）
  created_at / last_used_at
```

- 利用者 1 人に何個でも持てる。端末を替えても、なくしても、別のパスキーで入れる
- テナントには属さないので `core` に置き、RLS は付けない（`core.users` と同じ）
- 消すのは本人だけ。最後の 1 個は消せない（入れなくなる）
- 認証のたびに `sign_count` を確かめて更新する。同期されるパスキー（iCloud キーチェーン、Google パスワードマネージャー）は 0 のまま返すので、0 は許す
- アテステーション（認証器の種類の証明）は求めない（`none`）。どの認証器でも登録できるようにする

### RP ID は環境ごとに分ける

| 環境 | RP ID | 許すオリジン |
| --- | --- | --- |
| ローカル | `localhost` | `http://localhost:3000` |
| dev | `dev.<ドメイン>` | `https://dev.<ドメイン>` |
| prod | `quiz.<ドメイン>` | `https://quiz.<ドメイン>` |

- RP ID を apex（`<ドメイン>`）にすると、環境をまたいで同じパスキーが使える。環境ごとに分け、dev で作ったパスキーで prod に入れないようにする
- **Cognito で作ったパスキーは移せない。** RP ID が Cognito のドメインで、秘密鍵は利用者の端末にしかない。全員が登録し直す

### セッションは quiz-service が出すトークンで持ち、いまの境界を保つ

- 認証に成功したら、quiz-service がアクセストークン（JWT、15 分）とリフレッシュトークン（不透明な乱数、30 日）を出す
- web のサーバーが受け取り、いまと同じく暗号化して `HttpOnly` の Cookie に置く。proxy が `Authorization` を付ける形は変えない
- アクセストークンの署名鍵（ES256）は SSM Parameter Store（SecureString）に置き、quiz-service だけが読む（解説図の署名鍵と同じ置き方）。
  検証は `Authenticator` の新しい実装が行う。差し替えるのはこの 1 つ（ADR-0016 の 4 で狭めておいた範囲）
- リフレッシュトークンは、ハッシュだけを DB（`core.refresh_tokens`）に持ち、使うたびに新しいものに替える。古いものが 2 回使われたら、その系列をすべて無効にする（盗まれたとみなす）
- ログアウトは、リフレッシュトークンを消す。アクセストークンは期限（15 分）まで残る

### メールの確認と、パスキーをなくしたときの復旧は SES で送るコードで行う

いまは Cognito が確認コードを送り、招待の受け入れは確認済みのメールアドレスが前提になっている（ADR-0016 の 5）。

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| **SES で確認コードを送る** | いまと同じく「招待したアドレスを、本人が持っている」ことを確かめられる。復旧にも同じ仕組みが使える | SES のドメインの検証と、sandbox の解除の申請（AWS の審査、Terraform の外）が要る。1,000 通あたり 0.1 ドル |
| 招待のリンクで確認とみなす | メールを送らない | リンクが漏れると、別の人が受け入れられる。いまの守り（リンクとアドレスの両方が要る）より弱くなる。招待なしで作るアカウント（公開テナント、ADR-0025）は確認できない |
| メールを確認しない | 何も要らない | 招待の受け入れで、本人かどうかを確かめられない |

- 確認コードは 6 桁、期限 10 分、5 回まで。ハッシュだけを持つ
- **パスキーをなくしたら、メールのコードで入り、新しいパスキーを登録する。** パスワードは持たない。
  メールを読める人は入れることになるが、Cognito のパスワードの再設定と同じ強さ
- 登録のときに、2 個目のパスキー（別の端末か、同期されるパスキー）を勧める

### スモークテストと E2E は、ソフトウェアの認証器でログインする

人の操作なしに、本物のパスキーの手順を通す。テスト専用の裏口（決まった値でトークンを出す API など）は作らない。

- **E2E（Playwright）**: Chrome の仮想の認証器（DevTools Protocol の `WebAuthn.addVirtualAuthenticator`）で、登録とログインを画面から行う。`support/sign-in.ts` を書き換える
- **スモークテスト**: 鍵の組をスクリプトで持ち、チャレンジに自分で署名して認証の応答を作る（`smoke-token.sh` を置き換える）。
  公開鍵は、スモークテストの利用者のパスキーとして、Terraform か初回の手順で登録しておく。秘密鍵は GitHub の secret に置く

### 移り方: しばらく両方を受け付け、ログインしている人がパスキーを足す

1. `Authenticator` を 2 つの実装の組にし、Cognito のトークンと自前のトークンのどちらも受け付ける
2. Cognito でログインしている人が、設定の画面から自前のパスキーを登録する。**結び付けは、ログインしている `core.users.id` で行う。** メールアドレスでは結ばない
3. ログインの画面を自前のものにする。Cognito のログインは「前の方法で入る」として残す
4. 全員が移ったら（または期限を決めて）、Cognito のログインと `CognitoAuthenticator` を消す。`core.users.external_id` は使われなくなる

一気に替えると、パスキーを登録し直す前の人が入れなくなる。

### 比べる観点（DEV-122 で結果を書き足す）

- 作った量（コード、テーブル、Terraform）と、Cognito で書かずに済んでいた量
- 運用（鍵の入れ替え、SES の送信の失敗と苦情、確認コードの総当たりへの備え）
- セキュリティの責任。Cognito が持っていたもの（総当たりの検知、漏れたパスワードの検査、トークンの失効）のうち、何を作り、何を持たなくなったか
- ログインの体験（Cognito のドメインへ移らない、パスワードがない）

## 決定

**設計は上のとおりとする。そのうえで、いまは差し替えず、Cognito を使い続ける。** DEV-120〜122 は保留にする。

| 理由 | 中身 |
| --- | --- |
| 利用者から見た違いが小さい | いまも Cognito でパスキーが使える。差し替えて変わるのは、ログインのたびに Cognito のドメインへ移らないことと、パスワードがなくなることくらい |
| 安全性の責任が増える | 総当たりの検知、トークンの失効、確認コードの扱いを自分で持つ。どれも作るより、正しいことを確かめ続けるほうが重い |
| Terraform の外の手作業が増える | SES の sandbox の解除の申請（AWS の審査）が要る。ADR-0016 が避けたもの |
| 利用者が全員、登録し直す | パスキーは Cognito から持ち出せない |
| 費用は理由にならない | Cognito は月 1 万人まで無料で、いまの規模では差がない |

ADR-0016 の悪い影響「認証基盤が AWS に固定される」は、残るリスクとして受け入れる。
利用者の ID と所属はアプリのデータにあり（ADR-0016 の 2）、移るときに作り直すのはログインと `Authenticator` に限られる。固定の度合いは小さい。

### 見直す条件

次のどれかに当たったら、この設計で DEV-120 から始める。

- Cognito の月間アクティブユーザーが無料枠（1 万人）に近づく
- Cognito の画面（Managed Login）では足りないログインの体験が要る。アプリのドメインのまま入りたい、パスワードをなくしたい、など
- AWS の外へ移す
- Cognito の Essentials の料金や、パスキーの扱いが変わる

## 結果

### 良い影響

- 作るなら何をどう作るかが決まっている。見直す条件に当たったら、DEV-120〜122 を迷わず始められる
- 認証の安全性の多くを、Cognito に任せたままにできる。SES の申請も要らない
- 見る人が触れる機能に時間を回せる

### 悪い影響・受け入れるリスク

- WebAuthn の登録と認証の検証を、手を動かして理解する機会はなくなる
- パスワードが残る（ADR-0016 の悪い影響のまま）
- ログインのたびに Cognito のドメインへ移る

### 緩和策

- 開発ガイドライン、E2E のサインインの部品、セキュリティレビューが「自前の実装に替えたら」と指している箇所は、この ADR を指すように直す
- Cognito の月間アクティブユーザーは、Cognito のコンソールの利用状況と、月の予算の通知で気づける

## 検証事項

- Spring Security の `webAuthn()` が、HttpSession を使わない構成（チャレンジの置き場所とセッションの発行を差し替える）に向くようになったら、webauthn4j を直接使う判断を見直す
- 同期されるパスキーで `sign_count` が 0 のままのときの扱い（許す）が、webauthn4j の既定の検証と食い違わないか。DEV-120 で確かめる
